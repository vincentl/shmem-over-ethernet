# v0.2 step 1: the single-node build - `OSOE_SINGLE_NODE` for a desktop running Rocky Linux 9

**Status: written on 2026-10-05 from the author's decisions for v0.2
(`docs/decisions/2026-10-05-v0.2.md`, items 1 to 5) and a static audit of
the tree at the 0.1.0 tag against Rocky Linux 9's kernel and toolchain. It is
the first step of `docs/prompts/task-v0.2.md`. Nothing later depends on it;
it goes first because it is what the talk's audience asked for.**

What this step changes, in one sentence: a builder who wants osoe on one
machine - a desktop with many cores, for developing and testing programs at
small PE counts - can configure with `-DOSOE_SINGLE_NODE=ON` and get a
library and tools that need no liburing, no io_uring and no kernel newer than
Rocky Linux 9's, that refuse a job of more than one node by name, and that
pass every one-node test the full build passes; the full build is unchanged.

The audience's words, as the author reported them: people were excited about
`osoe-launch` and the library *for single-node use*, to install on a beefy
desktop and test small-PE-count jobs. The author's decisions: an opt-in, not
an opt-out ("we want the builder to opt in to this, not out of the full
build"); Rocky Linux 9 is the goal; the classic futex only in this build; the
multi-node build keeps its io_uring requirements; development and testing
stay aarch64-first.

It is written for a session that starts cold, in this repository, with the
VMs below. Nothing in it needs the conversation that wrote it.

The author's goals, the axes to judge the work by:

- **One tree, two builds, no drift**: a change to the library is built and
  tested in both, and nothing a one-node job does differs between them but
  the wait syscall.
- **The seam holds**: the internode backend is replaced behind design §4.10's
  boundary, not carved out with `#ifdef`s through the files that use it. A
  second backend, even one that refuses everything, is the first exercise of
  the seam the RoCE constraint exists for.
- **The README true at every commit**, with two requirement lists where
  there was one.

## The audit's findings

What the static audit found newer than Rocky 9 outside the io_uring
transport, so that the session need not look again - but verify the first
build on Rocky, since a static read misses what a compiler finds:

- **The kernel.** Only futex2. Everything else the one-node path uses is
  old: `MAP_FIXED_NOREPLACE` (4.17), `pidfd_open` (5.3, raw syscall with a
  `kill` fallback), `sched_setattr` (3.14), `getrandom`, `prctl`
  `PR_SET_PDEATHSIG`, `MADV_DONTDUMP`, `SYS_mmap` with `MAP_FIXED`,
  `shm_open`. `MAP_HUGETLB` and every TCP option are the transport's.
- **glibc 2.34**: nothing newer is called. **GCC 11**: gnu11, the attributes
  `alias`, `format`, `may_alias`, `no_sanitize_address`, `section`,
  `visibility`, `weak`, the builtins `ctz`, `ctzll`, `clzll`; no C23.
  **binutils 2.35**: the linker script's `INSERT BEFORE` and
  `CONSTANT(MAXPAGESIZE)` are old. **Python 3.9**: all 42 files under
  `tools/` parse at its grammar; nothing from 3.10 is imported.
- **CMake.** Nothing in the scripts needs more than 3.20 but the presets
  file, version 6 for its workflow presets (3.25), and `cmake --workflow` in
  the README. Rocky 9.0 to 9.2 ship CMake 3.20; 9.3 and later ship 3.26.
  **Keep 3.25**: the presets are how the project is built and tested, and
  the honest target is Rocky 9.3 or later, with CMake from EPEL or `pip` for
  an older point release - the README says so.
- **The tests.** A configure in the VM registers 748 tests; about 248 span
  more than one logical node and about 500 do not (14 with a one-node map,
  373 launched with no map, 117 with no launcher). The README says "about
  340" fail where io_uring is refused: find the right number while labelling
  and make the README's sentence true.

## How to work

- **A branch and a worktree a part** (`build/scratch/wt/<branch>`); never
  edit a worktree a verification is building from.
- **The full build first, at every commit**: the four presets with the floor
  pins on, `tier3`, `models`, and `osoe-pacer`'s smoke tests in the `osoe`
  VM. A refactor that moves code behind the seam changes no behaviour, and
  the full suite says so before the single-node build is attempted.
- **Then the single-node build**, in the `osoe` VM (which has liburing and
  must not need it when the option is on - configure with it hidden:
  `PKG_CONFIG_PATH=/nonexistent`, or `CMAKE_DISABLE_FIND_PACKAGE_PkgConfig=ON`)
  and then in `osoe-rocky`. Its suite is every test not labelled
  `internode`, in the four presets.
- **Merge into `main` at green checkpoints**: each part when it is green in
  both builds. The README is true of the tree at every commit.
- **An adversarial read before every merge**, by a fresh agent given the
  diff and the rule "a one-node job on the full build and on the single-node
  build runs the same code but the wait syscall", asked to find a behaviour
  that differs, or a path on which the single-node build reaches the
  internode backend's state.
- **Subagents** (CLAUDE.md): Sonnet for the sweeps (every caller of a futex
  function; every link of liburing; every test's node count), the labelling,
  the preset runs in both VMs, the README's line-by-line check, the probe's
  split. The seam work - the split of `transport-am.c`, the refusing backend,
  the classic futex file - stays in the main session.
- **Names.** *Full build* and *single-node build*; *refusing backend*
  (`transport-single-node.c`); *classic futex* (`futex-classic.c`) and
  *futex2* (`futex-futex2.c`); the label `internode`; the option
  `OSOE_SINGLE_NODE`.

## Part 1: the seam - the internode backend behind one file boundary

A refactor of the full build with no behaviour change, verified by the full
suite before Part 2 starts.

1. **Split `transport-am.c`** into the part every job uses - the node-local
   operations, the contexts and their counters, quiet and fence on the local
   side, the agent's boundary calls when the job is one node - and the part
   only a job of more than one node uses, which goes to a file of its own
   (`transport-internode.c`, or into `internode-am.c` where it belongs
   there). The guard `osoe_am.internode` stays where the two parts meet; a
   call into the internode part is a function call across the file boundary,
   so the single-node build can replace the file. Do the same for
   `progress-host.c`'s eight guarded sites if any of them is reachable on one
   node: list which are and which are not, in the record. `am-state.h` must
   stop including `ring.h` for the state every job has; the ring's state
   moves with the ring.
2. **Name the internode backend's entry points** that the common part calls
   - start (open the listener, run the rendezvous, build the mesh), the
   agent's pass, wait and exit, the issue of an operation toward a remote PE,
   the collective seam's internode calls, abort and close, the metrics it
   exports - in one header, `internode-backend.h`, and check with
   `cmake/CheckBoundary.cmake`'s method that nothing in the common part
   reaches past it. Every entry point is one a backend on RDMA would also
   provide; say in the header which of design §4.10's calls each is.
3. **Verify** the full build whole, the four presets, `tier3`, `models`, the
   pacer's smoke tests, and the `shmem.boundary` or equivalent check, and
   merge. The README does not change in Part 1.

## Part 2: the option, the refusing backend, the classic futex

1. **`OSOE_SINGLE_NODE`**, `option(... OFF)` in the top-level
   `CMakeLists.txt`, shown in the configure summary and in every tool's
   `--version` (`osoe-launch --version`, `oshcc --showme:version`, the
   library's `SHMEM_INFO` text: "single-node build" after the version). On:
   - no `find_package(PkgConfig)`, no `pkg_check_modules(LIBURING)`, no
     liburing link anywhere (`base/`, `shmem/`, `tools/probe`, the tests,
     `CheckStaticLink.cmake`'s `URING_LIBRARIES`); `tools/echo-uring` is not
     built; `ring-check.c` is not built;
   - `futex-classic.c` is built in place of `futex-futex2.c` (below);
   - `transport-single-node.c` is built in place of the internode backend's
     files, none of which is compiled;
   - the tests labelled `internode` are not registered (a configure-time
     `if`, so `ctest` sees only what can run; a `ctest -L internode` on the
     full build runs exactly the tests the single-node build lacks);
   - `tools/probe` builds without its io_uring checks, and gains the classic
     futex check in place of the futex2 one.
   Off, nothing changes: the same files, the same links, the same tests as
   the tag.
2. **The refusing backend**, `transport-single-node.c`: every entry point of
   `internode-backend.h`, each either unreachable on one node - then it
   aborts by name, since reaching it is a bug in the common part - or
   reachable at start-up, where `shmem_init` on a job whose `node_count > 1`
   ends the job before it creates anything in `/dev/shm`, with one line:
   that this is the single-node build of osoe, the job spans N nodes, and the
   full build is what runs it (the start-up-is-loud rule: every PE checks
   before its node joins, `docs/decisions/README.md`). The existing
   `osoe-launch -m` path produces such a job on one machine: the test of the
   refusal is `osoe-launch -n 2 -m 0,1` under the single-node build ending by
   name with status 1, in the form of the `osoe_refusal_test` tests.
3. **The classic futex**, `base/futex-classic.c`: the six functions of
   `futex.h`, over `syscall(SYS_futex, word, FUTEX_WAIT_BITSET | flag,
   expected, deadline, NULL, bitset)` and `FUTEX_WAKE_BITSET`, where `flag`
   is `FUTEX_PRIVATE_FLAG` for `OSOE_FUTEX_PRIVATE` and nothing for the
   shared scope - `FUTEX_WAIT_BITSET` takes an absolute `CLOCK_MONOTONIC`
   deadline, which is `osoe_deadline`'s form, and `FUTEX_BITSET_MATCH_ANY`
   is the bitset the plain calls pass. `EAGAIN`, `EINTR` and `ETIMEDOUT`
   handled as `futex-futex2.c` handles them, the timeouts counted the same.
   `osoe_futex_check` makes the same two checks against the classic calls.
   The two files share nothing but the header, and a test in `base/`'s
   tests - run in both builds, so it runs against whichever file is built -
   pins the contract: a wake across two processes on a shared mapping; a
   private wait woken from another thread; the deadline honoured within the
   scheduler's slack; a wait on a word that already differs returning at
   once; the bitset forms matching only their bits. The design §3.10 note
   that a relative value passed as a deadline "silently becomes a busy loop"
   holds for the classic call too: keep the single deadline helper the only
   way to make one.
4. **The init check** reads "osoe needs Linux 6.7 or later" today; the
   single-node build's reads what it checks - the classic futex, present
   since 2.6.25 - so a Rocky 9 kernel passes and a refusal there would name a
   real cause (a seccomp sandbox denying `futex`, which the after-release
   list's Q6 already wants named as one).
5. **The label `internode`** on every test that runs a job of more than one
   logical node: the ones `osoe_tier2_map_test` registers, the hand-written
   `-m` lines, the six inside `sh -c` strings, `test-floor.c`'s and every
   test that includes `<liburing.h>` or links it, the seccomp tests
   `deny-io-uring` and `deny-futex2` (the latter is moot where there is no
   futex2 to deny; say so beside its registration), and `tier3`'s nine.
   Audit the labelling two ways before believing it: `ctest -N -LE internode`
   on the full build must list no test that passes `-m` or a map, and the
   single-node build's suite must contain no test that fails for want of
   the backend. Then fix the README's "about 340" to the number found.
6. **Verify**: the full build whole in `osoe` as in Part 1 - nothing about
   it has changed but a label and a file split - and the single-node build in
   `osoe` with liburing hidden, then in `osoe-rocky`, the four presets each
   (TSan and ASan with GCC 11 on Rocky), the pacer's smoke tests, `oshcc`
   compiling and running the statics test program and an example from
   `corpus/openshmem-examples` at 8 and 32 PEs on the VM's four cores
   (oversubscribed, which a desktop user will do), and `cmake --install`
   into a prefix with `oshcc` and `osoe-launch` run from it. Record what the
   first Rocky build found that the audit did not.

## Part 3: the README and the desktop

1. **Requirements** become two lists with one preamble: the full build's as
   today (Linux 6.7, liburing 2.6, CMake 3.25, GCC or Clang, pkg-config,
   Python optional), and the single-node build's (any kernel with the classic
   futex and `MAP_FIXED_NOREPLACE`, so 4.17 or later, and in practice any
   distribution's; CMake 3.25; GCC or Clang; no liburing, no pkg-config). The
   sentence declaring Rocky 9, Debian 12 and Ubuntu 24.04 unsupported says
   instead that they run the single-node build, and that the full build needs
   Debian 13 or Raspberry Pi OS Trixie or any distribution with both a 6.7
   kernel and liburing 2.6 - Fedora, Arch, Ubuntu 24.10 and later.
2. **A section for the desktop**, after the quick start: configure with the
   option, install, compile with `oshcc`, run with `osoe-launch -n 8`; what
   `/dev/shm` must hold (about 300 MiB a PE at the default heap, and
   `SHMEM_SYMMETRIC_SIZE` to shrink it, the container note already there);
   that a job of more than one node is refused by name and the full build is
   what runs it; that `OSOE_AGENT_CPUS` and the slice matter when PEs
   outnumber cores (the pacer's `--cpu-bind=none` numbers are the evidence);
   that `osoe-launch -m` still makes logical nodes but this build refuses
   them. One paragraph, not a page.
3. **Limits, Launching**: the single-node build has run on Rocky 9 aarch64
   in a VM and nowhere else yet; x86-64 as the full build's sentence says.
   The probe's paragraph (199-222) says which checks each build makes.
4. **The repository table** gains `transport-single-node.c`,
   `futex-classic.c`, `futex-futex2.c`, `internode-backend.h`.
5. **Design §1** takes an "as built" note under the requirements: the
   single-node build and what it drops, with the author's reason - an
   opt-in for the desktop, the full build's floor unchanged. §4.10 notes the
   second backend. `docs/decisions/README.md`'s "Dependencies" line gains the
   single-node build's.

## The merge point

With all three parts on `main`: the full build's four presets, `tier3` and
`models` whole in `osoe`; the single-node build's four presets whole in
`osoe` with liburing hidden and in `osoe-rocky`; the pacer's smoke tests in
both; `cmake --install` from both. Record the numbers and the Rocky VM's
versions. Then the full adversarial review (`docs/reviews/adversarial-review-prompt.md`,
its deliverables named `v0.2-step1-*`), and its fixes: this is the first of
the arc's two review points (`task-v0.2.md`), since what it produces is what
desktop users install.

## Not in this step

- Any change to the one-node data path, the heaps, the statics, the
  collectives, the agents' waits beyond the syscall behind them.
- An x86-64 build or run: gated on hardware (`task-v0.2.md`, the gated
  items). The Rocky VM is aarch64.
- Packaging (`.deb`, `.rpm`): `cmake --install` is the install; a note in
  the record if a user asks.
- Bundling liburing, in either build: decided against in design §1.
- The after-release list's Q6 (a sandbox's refusal of futex2 named as one)
  beyond what item 4 of Part 2 gives it for free.

## Stop and ask

- Any point where the split of `transport-am.c` needs a change to the seam's
  shape - a new upcall, a changed signature in `transport.h` or
  `internode.h` - put it to the author before building it.
- A one-node test that passes on the full build and fails on the single-node
  build for a reason other than a missing label: that is a behaviour
  difference, and the rule says there is none.
- Rocky 9 refusing anything the audit called old, or its GCC 11 refusing a
  construct: fix it if the fix is local, and put it to the author if it
  would change the floor the README states for the full build.
- CMake 3.25 proving a real obstacle on the Rocky VM - EPEL's or `pip`'s
  CMake not working - before lowering the floor: the presets would have to
  go, and that is the author's call.
