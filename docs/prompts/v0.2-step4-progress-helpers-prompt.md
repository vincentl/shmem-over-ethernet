# v0.2 step 4: progress helpers - the control plane on the lead's agent, data planes on helper threads

**Status: written on 2026-10-05 from `docs/design/progress-helpers-proposal.md`
(the proposal) and the author's decisions for v0.2
(`docs/decisions/2026-10-05-v0.2.md`, items 1, 5, 7 and 8). It is the fourth
and last step of `docs/prompts/task-v0.2.md`, built after steps 1 to 3 have
merged. It is the proposal's build plan, not a new design: build from it
without waiting, and put any point where the build must depart from the
proposal to the author before building that point. The proposal's §8 - the
control wire, always or only when helped, the default, the zero-copy rung -
is answered by the author before Part 1 begins; until it is, Part 0 can run.**

What this step changes, in one sentence: the one thread a node that moves
every message between nodes becomes a lead's agent that keeps the control
plane on a wire of its own to every peer, and zero or more helper threads
that each own a ring and a disjoint set of the data wires and move the bytes,
so that a node's rate to other nodes is as many threads' as its link needs
and a barrier never waits behind a put.

The author's premise, settled: one thread is not enough to drive an HPC link.
The constraint: no hardware above a gigabit is in hand, so this step is
tested for correctness locally, on oversubscribed logical nodes, and tuned for
performance when an x86-64 pair with a fast link exists (`task-v0.2.md`, the
gated items). A count of zero helpers is today's thread with today's work,
and the Pi pays nothing.

It is written for a session that starts cold, in this repository, with the
VMs and the Pi cluster below. Nothing in it needs the conversation that wrote
it.

The author's goals, the axes to judge the work by:

- **A node's rate to other nodes grows with the threads it gives the
  transport**, and ordering stays free: every peer's stream on one thread.
- **Nothing between threads is a queue.** A wake, a request word, a counter
  read with acquire: that is all. Every structure has one owner.
- **Nothing may spin** (§3.11), helpers included.
- **A path to RoCE at ~10⁶ PEs that no interface blocks**: an owner's ring
  and wires are what a backend's queue pairs would be; the control wire is
  the control queue pair every RDMA transport has.

## How to work

- **A branch and a worktree a part**; never edit a worktree a verification
  is building from.
- **Part 0 before anything**: the profile and the one-thread ladder are what
  tell the helpers where the time goes, and each rung is a measured change
  that merges on its own.
- **Models first** for every protocol the proposal names (§7): the owner's
  wake, stop and abort, the two goodbyes.
- **Verification of a part**: the four presets with the floor pins on,
  `tier3`, `models`, the SOS suite at 4 × 2, `osoe-pacer` `mix` and
  `mailbox`, at `OSOE_PROGRESS_HELPERS=0` - every existing test unchanged -
  and again at 2 and 3 helpers on 3 to 16 logical nodes under TSan and ASan.
- **A speed claim is simulated and timed before it merges**; where it cannot
  be timed for want of a link, the README says it is untimed and names the
  simulation.
- **Merge into `main` at green checkpoints**; the README true at every
  commit.
- **An adversarial read before every merge**, by a fresh agent given the
  diff and the owner rule - "every structure has one owner, and nothing
  between owners is a queue" - asked to find a word two threads write, or a
  wake that can be lost.
- **Subagents** (CLAUDE.md): Sonnet for the sweeps (every writer of every
  counter; every reader of `osoe_am.ring`; every test that counts sockets or
  names the wire's slot), the preset runs at each helper count, the README's
  check. The owner structure, the control wire's protocol, the stop protocol
  and the models stay in the main session.

## Part 0: the profile and the one-thread ladder (proposal §6)

1. **Profile** the lead's agent in the VM over loopback between two logical
   nodes under a put stream and under the mailbox pattern, with `perf record`
   on the agent's tid (`agent.c:175` has it): how the time divides between
   the kernel's socket copies, the ring's submit and reap, the library's
   parse and apply, and waits. Record the division in the step's first
   decisions file; it is the number every later claim refers to.
2. **The ladder**, each rung a change on the one thread, measured against
   `echo-uring`'s bare stream and the previous rung, merged on its own if it
   helps and recorded if it does not:
   - provided buffers' count and size against the segment size, and the
     buffer-ring exhaustion counter;
   - `IORING_SETUP_DEFER_TASKRUN` with `COOP_TASKRUN` (6.1; the probe and
     `ring-check.c` gain the check);
   - registered files for the wires;
   - the library's parse per message and the apply's copy;
   - the dirty-word exchange per pass;
   - `IORING_OP_SEND_ZC`, only if the author's §8 answer includes it, and
     only measured on a fast link, since on loopback zero copy saves nothing:
     the aggregation clocks off the notification CQE instead of the send CQE,
     `wait_word_model.py` and the §3.5 reopen protocol checked first.
   The ladder's result is the one thread at its best, and the fraction of the
   bare stream it reaches over loopback, which the README states in place of
   "a fifth".

## Part 1: owners, with zero helpers (proposal §3.2 to §3.7)

The structural change with no thread added: the lead's agent becomes owner 0
holding every wire, and the code is parameterised by owner.

1. `struct osoe_progress_owner` in `progress.h`: ring, provided-buffer
   ring, wires and slots, reply pool, scratch, dirty bitmap, sleeping flag,
   wake word, counters, per-connection state. The engine holds an array of
   owners; `osoe_am.ring` is gone.
2. `ring.c` and `wire.c`: a ring per owner, created and enabled by its
   owner's thread (`SINGLE_ISSUER` demands it); a wire attached to its
   owner's ring; the slot-to-CQE-tag map per ring.
3. `connection-area.*`: the bitmap, flag and word per owner; the peer-to-owner
   map (`1 + p mod H`, or 0); the layout bump; the PE side of the claimed
   wake addressing the owner. `lead_wake_model.py` with the owner as a
   parameter; its four broken variants still failing.
4. The poll, the sleep and the wake as functions of an owner
   (`progress-host.c`); counters per owner summed for readers
   (`metrics.c`, `osoe-stat`, the detector).
5. Stop and abort through per-owner request and done words with deadlines
   (`progress-host.c:536-690`), modelled first.
6. Verify: everything at H = 0 as today, the Pi's lines unchanged against the
   step 3 merge point, alternating. The README changes nothing yet but the
   repository table.

## Part 2: the control wire (proposal §3.1), per the author's §8 answer

1. The rendezvous and the mesh make two connections a pair - the control
   wire first, then the data wire - with the handshake on both; the listener
   tells them apart by the first message's kind; `mesh_timing.py` gains the
   second connection and the README's start-up sentence states the doubled
   chain.
2. The lead's control wires on owner 0's ring with a private send buffer a
   wire; the control queue's messages - ARRIVE, RELEASE, team control, the
   detector's probes and answers, the goodbye - on them and on nothing else;
   `enqueue` and `forward` write owner 0's queue only.
3. The data wires carry everything with a payload and their own goodbye; the
   reset rule per wire; the two goodbyes modelled (a reset judged once both
   the wire's goodbye and its end of stream have arrived, per wire).
4. The detector's probes on the control wires; `osoe_progress_idle` and
   `_quiet` through request words the owners answer.
5. Measure on the Pi, H = 0: a barrier during a 1 MiB put stream before and
   after the control wire, the control plane's own number; the mailbox rate
   and the put stream unchanged within the noise; start-up at four nodes.
   Record them.

## Part 3: helpers (proposal §3.2, §3.7, §3.8)

1. `OSOE_PROGRESS_HELPERS`, default 0, at most 64, agreed among a node's PEs,
   free to differ between nodes; the helper threads created after the agent
   in `shmem_init` with signals blocked, placed by `OSOE_AGENT_CPUS`'s rule,
   each asking `OSOE_AGENT_SLICE_US`; joined at exit after their done words.
2. With H > 0, owner 0 holds only the control wires; the data wires go to
   owners 1 to H by the map. The same poll runs on every owner.
3. The reply pool per owner sized by §3.8's argument over its wires;
   `shmem.reply-pool.overflow` run per owner.
4. `osoe-stat`'s node header: the owners, each with its wires, its passes and
   its counters.
5. Tests: the suite at H = 2 and 3 on 3, 4, 8 and 16 logical nodes under
   TSan and ASan; `osoe-pacer mix` and `mailbox` at H = 0 and 2 for a minute
   each; a test that pins the map (a PE's wake reaches the owner of its
   wire); a test of a helper that never answers a stop word (the deadline
   ends the job by name); the mutation each catches.
6. The README: Limits' "one thread a node" paragraph replaced by what is
   built - the planes, the setting, what is measured and what is not; the
   memory rows; the settings table.

## Not in this step

- More than one data wire a peer pair (the proposal's D = 1).
- Helpers in any process but the lead's.
- The mesh schedule (`docs/design/mesh-schedule-proposal.md`): the doubled
  chain is stated, not fixed, until a large system exists.
- Any change to the data collectives, the lanes, the barrier's tree, the
  landing zone.

## Stop and ask

- A word two owners must write, or a wake that the per-owner model loses:
  the design's rule false somewhere.
- A control message that turns out to need ordering against a data message
  (proposal §3.1's last paragraph names the goodbye as the only one).
- The control wire costing the Pi's barrier anything at H = 0 beyond the
  noise, or the mesh more than the model's doubling.
- The ladder's profile showing the library's own work, not the kernel's
  copies, as the larger share: put it to the author before Part 1, since
  helpers that own rings are the answer to the kernel's share.
- Any point where the build departs from the proposal.
