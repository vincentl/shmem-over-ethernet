## 1. Where a node's progress runs under Slurm's binding (item 9)

**What happens.** Every PE starts an agent thread, and the node's first PE's
agent is the node's progress engine: it moves every message the node sends
or receives (design §3.12); the other agents sleep. Slurm, when a node runs
as many tasks as it has cores and nothing says otherwise, binds each task to
one core ("auto binding"); a thread inherits its creator's mask, so the
progress thread is bound to the first PE's core. The Pi's Cortex-A76 has no
SMT (`lscpu`: one thread a core), so that core is all it has.

**Instrumented**: each node's threads read from `/proc/<pid>/task/<tid>` -
`schedstat`'s time on a CPU and time waiting in a run queue, the context
switches a thread chose (it slept) and the ones it did not (it was
preempted), its affinity - twice in a window of 15 to 30 s, 4 x 4, release,
main's code (`3d5bbe1`). Scripts and samples:
`docs/design/evidence/pi-cluster/2026-09-27/agent-placement/`.

`mailbox`, 16 PEs, the lead's agent against the lead's main thread and the
other twelve PEs' (per thread, a share of one core):

| run | messages a second | lead agent: running | lead agent: runnable, not running | lead agent: preempted a second | lead main: running | other mains: running | other mains: waiting |
|---|---|---|---|---|---|---|---|
| bound (Slurm's default) | 38,900 | 0.12 | **0.29** | 1,970 | 0.30 | 0.13 | 0.002 |
| unbound (`--cpu-bind=none`) | 243,100 | 0.68 | 0.02 | 34 | 0.18 | 0.18 | 0.04 |
| bound, then the lead's agent alone given all four cores | 38,000 → 52,000 | 0.15 | 0.26 | 2,470 | 0.23 | 0.15 | 0.006 |
| bound, then the lead's agent asks for a 0.1 ms slice | 39,000 → 63,500 | 0.19 | 0.26 | 3,270 | 0.28 | 0.12 | 0.001 |
| bound, then both | 40,000 → 67,500 | 0.20 | 0.24 | 3,190 | 0.22 | 0.13 | 0.005 |
| unbound, then the 0.1 ms slice | 249,000 → 255,000 | 0.71 | 0.01 | 19 | 0.17 | 0.18 | 0.04 |

Readings:

- **Bound, the node is idle and its progress thread waits.** Three cores run
  at about 13%; the first runs the lead's main thread (30%) and its agent
  (12%), and the agent spends 29% of the time runnable but not running,
  preempted about 2,000 times a second. Each message waits for it, and every
  PE's rounds wait for the messages.
- **Moving only the agent adds a third.** Given all four cores, it is
  still preempted wherever it goes (2,470 a second): every core has a bound
  main thread, whose wakeups beat the agent - the thread that has run most -
  under fair scheduling.
- **A short slice adds two thirds** without moving it: Linux 6.12's EEVDF
  lets a thread ask for a shorter slice (`sched_setattr`'s
  `sched_runtime`, 0.1 to 100 ms, unprivileged), which lets it preempt
  sooner when it wakes. Measured with a helper setting the lead's agent's
  slice from outside (`set-slice.c` in the evidence).
- **Only unbinding recovers it all**: with every thread free to go to an idle
  core, nobody waits (2% for the agent), the agent does five times the work,
  and the rate is 6.3 times the bound one. The short slice costs nothing
  there - 2% more messages, the node-mates' tail as it was - so a library
  could ask for it whatever the binding.

**The Slurm options.** Slurm's default binding comes from, in order: the
step's `--cpu-bind` (or `SLURM_CPU_BIND` in the environment, which works
here), the nodes' `CpuBind` in `slurm.conf`, the partition's `CpuBind`, then
`TaskPluginParam`, and only then auto binding ([Slurm's resource binding
page](https://slurm.schedmd.com/resource_binding.html)). This cluster sets none
of them (Slurm 24.11.5, `TaskPlugin=task/cgroup,task/affinity`), so auto
binding applies. So yes, there is a global option: `CpuBind=none` on the
partition's or the nodes' line of `slurm.conf`, or `TaskPluginParam=None`,
which the man page gives as "Perform no task binding by default. Overrides
automatic binding." A user can export `SLURM_CPU_BIND=none` instead.

What the library could do is the author's (For the author, 1).

## 2. The gets' rate (item 12)

**Mostly a misreading, by the tool; what is left is the landing arena.**

The sort's pull exchange - counts by alltoall, each PE's twelve remote bins
of about 2 MiB pulled by `shmem_getmem_nbi`, one quiet - then sorts and
checks what arrived, then syncs its team before any sender refills its
staging. That last sync was timed as part of the exchange, and it waits
until every other PE has sorted and checked too, so a PE that sorted sooner
than the slowest counted the difference as exchange - which is how a round's
phase maxima came to sum past the round itself (6.7 s of phases in a 5.2 s
step). The push syncs before its check. So phase 1's "a quarter of the puts'
rate" compared two different things; `7a14994` times the pull's closing sync
as its own phase, `sync`.

By whole rounds, 67 M keys each, the push taking 4.07 s bound (phase 1):

| run | a round | against the push |
|---|---|---|
| pull, the default 256 KiB arena, bound | 5.61 s | 1.38x |
| pull, 256 KiB, unbound | 5.19 s | 1.28x |
| pull, `OSOE_GET_LANDING_BYTES` 1 MiB, unbound | 4.85 s | 1.19x |
| pull, 4 MiB, unbound | 4.26 s | 1.05x |

- **The arena is what is left.** A PE's nonblocking gets land in its
  arena, 256 KiB by default, and an issue that finds it full first completes
  everything in flight (§4.6 as built): at most 256 KiB in flight a PE, the
  pipe drained to empty about a hundred times a round. At 4 MiB the pull
  is within 5% of the push.
- **Not the binding, and not the agent**: the lead's agent runs 5% of a core
  in the pull and hardly waits (0.3 to 2%); giving it all four cores moved
  the exchange 4.3 → 3.8 s, a short slice nothing, and unbinding saved 8% of
  the round.

What to do - a larger default, or refilling as replies land instead of
draining to empty - is the author's (For the author, 5).

## 3. The scan (item 10)

**A choice, made knowingly - not a fact of the problem.** Phase 1 step 10's
brief decided it (decision 4): "Pipelined pieces are not built: no program
needs a large scan", and `internode-generic.c` says the cost. A scan over a
team spanning nodes runs a pre-order tree over the team's ranks, every
member at its own place; a scan larger than a 4 KiB slot runs piece by
piece, each piece all the way up and down the tree before the next starts.
At 1 MiB that is 256 pieces, each four steps - two up, two down, the tree
over 16 ranks at the default fan-out of 4 being two deep - at about 130 µs a
step: 134 ms, where reduce, pipelined since phase 1 step 5, takes 30. (On 8
PEs the tree is as deep, hence 136.)

Pipelining the pieces, as the reductions do, is the fix: a child sends piece
p + 1 up while piece p comes down, the slots a ring of a few pieces instead
of one, which the scan's model (`tools/modelcheck/scan_model.py`) would
check. The bound then is the busiest node's link: in the 16-PE tree the
first node carries about 4 MiB each way, some 40 ms at line rate. The tree
over ranks rather than nodes is the other half of the choice - strided and
cyclic teams need every member at its own place - and costs a level of
depth, not the factor of four.

## 4. Detecting a program's own deadlock (item 8): a proposal

**By proof, not by time.** A job is deadlocked when every PE waits inside the
library, nothing any PE sent is still in flight, and that holds still. Then
nothing can wake anyone: only a library operation satisfies a SHMEM wait, and
none is left to happen. §3.15's rule - no wait gives up because time has
passed - stands; this ends a job proved unable to move.

- **Each node, from what its lead's agent already reads**: every local PE's
  "blocked in" record (what `osoe-stat` prints) and every connection's sent
  and acknowledged counts. Two additions: a count per PE, bumped whenever one
  of its threads enters or leaves a wait, and each PE's thread count from
  `/proc/<pid>/status`. A PE counts as blocked only when every one of its
  threads waits in the library, so a thread computing, one the library never
  saw (an OpenMP pool) or a process stopped in a debugger keeps it live.
- **Across nodes, two collections**: a node blocked through and through for a
  while - say 10 s - with nothing unacknowledged or queued reports up the
  collective tree; once every node has, the root asks each again, and if no
  node's counts moved in between, the job is deadlocked. Two collections with
  nothing changed between them make a consistent cut, the standard argument
  for detecting a stable property: no message can be in flight unseen.
- **Then it says where**: each node prints what `osoe-stat` shows - each PE's
  routine, team, epoch and peer - and the job ends with a nonzero status. The
  evening's `mix` hang would have said at 10 s what `osoe-stat` said at 329:
  four PEs in `shmem_uint64_sum_reduce` at epoch 83, four in the xor at 84,
  eight in `shmem_barrier_all` at 84.
- **Cost**: nothing while anything runs; per suspicion, a small message a node
  up the tree and down, twice. It scales with nodes.
- **What it needs**: a control message and a model of the protocol,
  §3.15 amended, and `OSOE_DEADLOCK`: on, report only, or off. A slice after
  the review, if the author wants it (For the author, 3).

## 5. F1 and the Pi 5's known Ethernet faults (item 14)

**The known faults** of the Pi 5's Ethernet - the RP1's Cadence MAC, driver
`macb` - on the Raspberry Pi kernel's tracker:

- **Silent transmit stalls**: the write that starts transmission, posted
  over PCIe to the RP1, can be lost, leaving frames in the transmit ring
  unsent while the link reports up ([issue
  #7339](https://github.com/raspberrypi/linux/issues/7339)). Three fixes -
  a read-back that flushes that write, a recheck after re-enabling the
  interrupt, and a watchdog that restarts a ring whose tail has not moved for
  a second - merged into `rpi-6.18.y` on 2026-05-08 ([PR
  #7340](https://github.com/raspberrypi/linux/pull/7340)).
- **Receive drops that only `ip -s link` counts**, not `ethtool` or
  `softnet_stat` ([issue #6898](https://github.com/raspberrypi/linux/issues/6898)).

**Against the nodes, neither fits.** They run `6.18.50+rpt-rpi-2712`, built
2026-09-11, four months after the stall fixes went into its branch - and the
F1 investigation of 2026-09-26 ran on that same kernel, with stalls of 36 and
52 s that a one-second watchdog would not have allowed. Since this morning's
boot every node has moved over a billion packets each way with no error,
drop or miss in `ip -s link`, and the kernel has logged nothing about the
NIC; segmentation offload is off at boot on all four, EEE enabled but
inactive.

**So F1 is still unexplained**, and still costs time, not results: four
hours of `mix` with 87 timeouts ended `failures=0`. What would explain it is
what the runbook's §11 already lists: a capture at both ends of one of
pi-002's stalls (sudo), which shows whether a segment sat on pi-002 or was
lost after it, and pi-002's card in another board, which says whether it is
the board.

## 6. A start that never finished: logind's `RemoveIPC` (found tonight)

**What happened.** The first `pull-widened` run, job 828, printed nothing and
never ended. On pi-001, PEs 0 and 3 had joined the node's control segment and
waited for the other two; PEs 1 and 2 held no segment and slept in
`open_control`'s loop, finding no name. `osoe-stat` found the segment only
through PE 0's descriptor: its name was gone, though the lead removes it only
after every local PE has mapped. The other three nodes were up, waiting for
pi-001's lead.

**Why.** systemd-logind removes a user's System V and POSIX IPC - every file
of theirs in `/dev/shm` - once the user's last login session on a machine has
ended and `UserStopDelaySec`, 10 s, has passed (`RemoveIPC=yes`, stock
systemd's default; the nodes set nothing). The measurement's sampling reached
each node over ssh, a login session each time. pi-001's journal: the step
launched at 21:55:37.4; at 21:55:44.26, ten seconds after the last sampling
session there ended, pi's user manager stopped, and the names went with it. A
probe confirmed it on pi-002: a file written to `/dev/shm` by a session that
then ended was gone ten seconds later, when the user manager stopped.
PostgreSQL's documentation warns of the same for its shared memory
([§18.4.2](https://www.postgresql.org/docs/current/kernel-resources.html#SYSTEMD-REMOVEIPC))
and recommends `RemoveIPC=no`.

**What it means.** osoe removes every name once `shmem_init` is done (§6.2),
so a running job is safe - the day's other runs, whose sessions ended while
they ran, were untouched. Until then a PE finds what its node-mates made by
name: the control segment, the job tables, the connection area, each heap. A
name removed then leaves a PE waiting for it for ever, since a missing name
is what it waits on before its creator has made it; for a heap, the job ends
with a message. A job of that user's still starting on the node when the
removal comes - ten seconds after their last session there ended - can meet
it. Why pi-001's start had not got all four PEs past the name in seven
seconds, when a start usually takes under one, is not known: the processes
were gone before their start times were read. Evidence:
`docs/design/evidence/pi-cluster/2026-09-27/agent-placement/removeipc-hang/`.

**What to do** (For the author, 2):

- Documented: the README's limitations now say so, with the remedies -
  `RemoveIPC=no` on compute nodes, or `loginctl enable-linger` for the users
  who run jobs. On this cluster either needs sudo.
- In the library: a wait that finds no name could look for a live process of
  the same user holding the object under its deleted name - `osoe-stat`'s
  own way in - and open it through `/proc/<pid>/fd`, so that init survives a
  removal. Short of that, it could say what happened and end: an object whose
  name is gone while its creator holds it open was removed, not yet to come.

## 7. The sort's 11-bit digits (item 6)

**Four times faster, and the rounds twice as many.** Two minutes each of the
default sort, 4 x 4, release, bound, back to back - main's 16-bit build
(`3d5bbe1`), then the branch's 11-bit one (`6ac31fc`):

| digits | the local sort, a round | a round | keys a second | private memory a PE |
|---|---|---|---|---|
| 16 bits, 4 passes | 2.80 s | 4.08 s | 16.4 M | 74.1 MiB |
| 11 bits, 6 passes | 0.69 s | 1.88 s | 35.7 M | 72.2 MiB |

Six passes over the keys instead of four, each 4.1 times cheaper, whose
counters and write streams now fit the caches (the comment in `sort.c`). The
exchange is now the larger part of a round, so the tool puts more of the
library's work into a minute: the default run's point. The histograms went
from 2 MiB to 96 KiB. Both runs ended `failures=0`, every key checked; the
edge - a last digit of 9 bits - is held by two static assertions, and by the
mutations below, which cut the passes short or the mask narrow.

## 9. Four hooks? (the author's question on `rebind`)

**No reason to.** The brief's `allocate`/`begin`/`end`/`release` would split
every exercise's setup and teardown in four, and the plain path would change
with them; `rebind` adds one function and leaves setup and teardown - what
phases 1 to 3 verified - as they were. The four would buy two things `mix`
does not need: an allocation sized to each team, where every exercise now
allocates once for the world, which is the most any team needs; and a place
for team-scope teardown, where nothing of an exercise's is freed between
periods. They would not have prevented the one bug `mix` found, the
barrier's timing called on a team: that was inside a step, which no hook
covers; the barrier's guard and `mix-cycle` do.

## For the author

1. **Where a node's progress runs** (item 1). Recommended, in order: make no
   binding this cluster's default - `TaskPluginParam=None` in `slurm.conf`,
   sudo; have the lead's agent ask for a 0.1 ms slice, which costs nothing
   unbound and adds two thirds to the bound rate - a small part of unbinding's
   sixfold, but free (a few lines in
   `agent.c`, where the kernel has EEVDF's slices, 6.12 and later); and have
   `shmem_init` say once, when the progress thread shares a one-core mask with
   a PE, that `--cpu-bind=none` would help. Widening the agent to the node's
   cores adds little to the slice (67,500 against 63,500) and needs every PE's
   mask in the control segment: not worth a layout change.
2. **`RemoveIPC`** (item 6). On this cluster, `RemoveIPC=no` or
   `loginctl enable-linger pi` on each node (sudo). In the library,
   recommended before the release: a wait during init that finds a name gone
   opens the object through `/proc`, from the process that holds it, so a
   start survives the removal; the heaps' creators keep their descriptors
   until the names go, so there is always one to find.
3. **A program's own deadlock** (item 4): build the proposal after the
   review?
4. **The scan** (item 3): pipeline its pieces before the release? The model
   exists to extend; about 134 → 40 ms at 1 MiB, by the link's arithmetic.
5. **The gets** (item 2): refill the arena as replies land instead of
   draining it to empty, or raise its default - 1 MiB gave 1.19x, 4 MiB 1.05x,
   at that much control segment a PE?
6. **F1** (item 5): the capture at both ends and the board swap, both at the
   cluster.
