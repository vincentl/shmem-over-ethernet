## Decisions

1. **The deprecated active-set routines run over the whole job and nothing
   else** (slice 3; `docs/prompts/phase1-step5-slice3-prompt.md`, design §7.4).
   An active set of every PE is the world team; any other ends the job by
   name. Every corpus call site passes the whole job; forming groups for
   arbitrary sets is machinery osoe does not have. `pSync` and `pWrk` are
   never touched. *Undo*: `osoe_active_set_whole_job` is the one check; real
   active sets would need split teams (§7.3) first. The same rule covers the
   collects' and alltoalls' 32/64 forms.
2. **`shmem_sync` has both forms under one name**: C11 counts the arguments,
   C++ overloads, C99 has the deprecated one only, as the spec does.
3. **The deprecated atomic names of Annex F.2.12** exist, each the modern
   routine under its old name (PRK's stencil and transpose need them).
4. **The lock is the MCS queue lock** (§4.12), because the spec requires first
   come, first served; model-checked, its release as the code runs it. Its home
   PE is a hash of its address; misuse, and a lock never zeroed, end the job by
   name; the last `shmem_finalize` warns when locks are still held. *Open*:
   the handoffs of a contended lock on an RDMA backend whose atomics do not
   notify (§4.12 states the cost and the interface change that would fix it).
5. **Symmetric statics: phase 2 directly** (§4.3 as built; step 6 slice 1),
   phase 1.5 skipped. The linker script gathers all of the executable's
   `.data` and `.bss`, not the user's objects alone - harmless because each PE
   maps its own object, and independent of how the program was built. `-no-pie`
   stays for address agreement; `-static` is refused. *Open*: the known limits
   §4.3 lists (a `fork()` child shares its parent's statics; an application
   thread or a DMA registration made before `shmem_init`), and the structural
   alternative the review offered - remapping at load time from a
   `.preinit_array` entry - which would close the window at the price of a
   remap in every program `oshcc` builds.
6. **`oshcc`** is a POSIX `sh` script the build configures twice, installed
   with the library, adding the library's own link flags (so a sanitizer
   build's programs load its runtime) and answering `--showme`.
7. **fcollect never writes another node's `dest`** (§5.5 as built; slice 4).
   The spec's precondition would allow it, and SOS does it; but a fast node's
   write for the next collective can land under a slow node's copy-out of this
   one. The lead gathers its members' blocks itself, and the internode phase
   stages through the internal region.
8. **The gather is an operation of its own at the seam**,
   `osoe_internode_collect`, given the result's layout and bound by one rule -
   a peer's buffer is written only once that peer has entered - so that an
   RDMA backend can do an allgather. The generic implementation is the
   reduction's tree running an or. *Open*: its latency, ⌈*P n* / 16 KiB⌉ ·
   2⌈log_*k* *N*⌉ hops, grows faster than log *N* - the one internode phase
   that does. It stays until a backend's allgather replaces it, or the tree
   pipelines its pieces.
9. **collect's places come from an fcollect of every member's length** into
   room the heap lends for the call - the vector the lead's alone. A scan
   (§9.10.10, not built) would give each PE its own place in O(1) memory.
10. **alltoall is direct puts and the team's barrier**; the precondition that
    `dest` is ready is the application's, including a sync after a data
    collective into the same array.
11. **Quiets are pinned by counters, not by timing**: a mebibyte put ahead of
    `shmem_barrier` did not catch a barrier without its quiet, twice; the
    transport's count of the PE's waits does.

## The afternoon

8. the nonblocking fetching AMOs, the complex reductions under C++, and what
   the SOS suite found, with the runbook's three new programs and the
   team-creation proposal (bc86e8f).

**The SOS test suite ran against osoe for the first time** (`corpus/tests-sos`,
built per program with `oshcc`, `build/scratch/sos/sweep.sh`): 127 of about 150
passed on two maps at main's `11afd5f`, and 147 after this afternoon's merge.
What still fails, each for a named reason, is in the runbook's §8.

12. **The nonblocking fetching AMOs complete at issue** (design §7.5): each runs
    its blocking counterpart's rmw and stores `*fetch` before returning, which
    the spec permits - the value is promised by the next quiet, a deadline and
    not a floor. *Open*: across nodes each is a round trip where a batch could
    overlap; the upgrade is the rmw taking `OSOE_TRANSPORT_NONBLOCKING` with a
    result destination, as the nonblocking gets do (§4.6). Nothing in the
    corpus but SOS's tests calls them.
13. **C++ sees the complex reductions where g++ or clang++ compiles it**, as
    their `_Complex` extension (`OSOE_CXX_COMPLEX`), leaving out the EDG front
    ends that define `__GNUC__` without being GCC (nvc++, CUDA's); clang++'s
    `-Wpedantic` report of the type is silenced for those declarations alone.
    *Undo*: the one guard in `shmem.h`.
14. **A C11 generic called with the wrong number of arguments no longer
    compiles** - found by the review of the nonblocking AMOs, and true of the
    blocking AMO and typed RMA generics too: an unused arity slot was empty, so
    such a call became a comma expression that did nothing, silently without
    `-Wall`. Every slot now names a function that does not exist and says what
    the call takes, as `shmem_sync`'s already did.
15. **Two SOS tests stay failing by design.** `shmemalign` asks `shmem_align` for
    an alignment of 2, which the spec leaves undefined below `sizeof(void *)`,
    and osoe names; and the `c11_*_all_any_some` tests pass `short *` to the
    `_all`/`_any`/`_some` generics, which OpenSHMEM 1.5 defined over the AMO
    types alone - SOS's extension, not the spec's.
16. **Team creation is proposed, not built**:
    `docs/prompts/phase1-step7-slice1-prompt.md`, closing design §5.7's open
    item in two slices. It is the largest group of SOS failures left, and the
    road to real active sets (decision 1). *For the author*: its ten decisions,
    above all numbers from one counter on world PE 0, never reused; a block of
    node segment, internal region and record per number; and a runtime
    `OSOE_MAX_TEAMS` the rendezvous agrees.

**For the Pi day, three more programs** (runbook §8): OSU's OpenSHMEM
micro-benchmarks, all nineteen of which built and ran in the VM; osb's ssca1;
and the SOS suite. **ssca1 raised a correctness question and answered it
itself.** Its verification run found one, two or three alignments from the same
seed, run to run, on one node as on four - which could have been osoe losing
writes. It was the program: its generator lets rank 0 put the verification
motifs into other PEs' shares while those PEs still fill them with random
codons, with nothing between. One barrier made 25 runs over three maps find
the same three alignments, including those crossing PEs' boundaries. The
runbook applies it with a `sed` line. The rest of osb is not worth the cluster's
time, and the runbook says why for each.

**Still open**: `SHMEM_THREAD_MULTIPLE` (design §4.11) - eight SOS tests and
every `_threaded` osb variant want it, and `ssca1_threaded` calls SHMEM from
