# The day of 2026-09-26: the author's decisions, the second Pi session, and the handoff

The author answered the overnight questions in the morning
(`docs/decisions/2026-09-26-overnight.md`), booted the Pi cluster, and asked
for the runbook's second session to be driven from this conversation over
`ssh pi-login`. This is the record: what the author decided, what the cluster

starts from.

## The author's decisions

1. **RoCE is a design constraint, not this project's work.** No RoCE hardware
   is coming soon. The project reaches a **release point** first; the seams
   (§4.10, `internode.h`) must keep an RDMA backend possible and every review
   still grades them so, but no RoCE backend is built here. The one local road
   is Soft-RoCE (`rdma_rxe`): absent from the cloud kernel the `osoe` VM runs,
   present in Debian's generic arm64 kernel (the `osoe-16k` VM has it,
   `6.12.107+deb13-arm64-16k`), with rdma-core 56.1 in trixie. It can test that
   the seams carry verbs, over tier 3's veth pairs; it says nothing about
   performance, XRC (V1 of `docs/reviews/archive/roce-transport.md` §10) or NIC
   atomics. Post-release, if hardware is still far off then. Written into
   design §1 and §10, `docs/prompts/README.md`, and the step 8 brief's axes.
2. **The release point** (design §1 "Release point"): 1.5 complete through
   step 8; 1.6 complete but for §7.4's recorded non-conformance, which means
   the scans; SOS clean but for SOS's own extensions; the Pi runbook green with
   the floor, `osoe-bench` and the collective sweeps recorded; a license,
   `cmake --install` and a README enough for a stranger; a version tag and a
   release note of known limits.
3. **A. Step 8 approved as proposed**: three slices, the eleven decisions,
   slice 1's build brief (`docs/prompts/done/phase1-step8-slice1-prompt.md`). Start
   with slice 1, contexts, serial only.
4. **B. `OSOE_MAX_TEAMS` default 64 approved**; per-node colouring waits for a
   RoCE backend. *Applied the same evening* (`docs/decisions/2026-09-26-evening.md`):
   the default in `bootstrap.h`, and the numbers in design §5.7, §5.8 and §10,
   `docs/pi-cluster.md` §1 (a node's four PEs then reserve about 40 MiB of
   internal region, address space touched only by leads), `SHMEM_INFO`'s text
   and a README row the variable had lacked.
5. **C. Small gathers: measure first, then decide.** Measured today (below):
   the allgather's 8-byte fcollect costs 243 µs at 4 × 1 and 269 µs at 4 × 4
   against the old tree's 190 and 197 in the first session - 1.28× and 1.37×,
   under the 1.5× the recommendation set for building the two-slot staging.
   **Accept the cost; do not build the staging or a crossover now.** The
   staging model stays as evidence if a larger cluster reopens it.
6. **D. Scans sooner**: even though no corpus program calls them, they are low
   overhead, so they follow step 8's first slice directly, before the thread
   slices - model first, then build.
7. **E. The record, not the upcall.** Talked through with the spec: every team
   descending from `SHMEM_TEAM_WORLD` is an arithmetic progression in world
   ranks (§9.4.6: any integer stride, negative reverses, zero only with size 1,
   no wrap-around; `split_2d` makes strided teams), and only
   `SHMEM_TEAM_SHARED` and its splits can be non-strided, which never leave one
   node. So a team's node-block record carries `(world_start, world_stride,
   members)` and the backend learns every internode team from its record alone;
   `osoe_internode_team_world_ranks` goes. Folded into the scans slice, which
   needs the rank mapping anyway. Recorded for the successor API in
   `project-goals` memory and L47's neighbourhood: groups as rules plus one
   locality rule cover the spec.

**Two findings.**

- **F1. fcollect at 4 × 2 with 16 KiB blocks takes 63-69 ms a call**, against
  0.8 ms at 8 KiB and 2.5 ms at 32 KiB, in three runs; every other shape and
  size is smooth (4 × 1 and 4 × 4 at 16 KiB: 1.2 and 2.4 ms). The job makes
  progress - the 120 s no-progress rule never fires - and the NICs report no
  errors or drops, but TCP's counters do: `TcpExtTCPTimeouts` on `pi-002`
  climbed 482 → 492 in eight seconds during the run where the other nodes sat
  at 2-4, and every node has fast-retransmitted about 0.03% of its segments
  since boot. A retransmission timeout is 200 ms or more, so one every few
  calls is the average. It is the pattern, not a node: on any three of the four nodes
  the row is normal (1.17 ms without `pi-002`, 1.11 ms without `pi-004`), on
  all four it is slow whatever the layout (43.6 ms cyclic), and three more
  block runs gave 63, 88 and 109 ms. 4 × 4 at 16 KiB (a 64 KiB share) and
  4 × 4 at 8 KiB (the same 32 KiB share as 4 × 2 at 16 KiB) are both smooth,
  so it is not the share size either. The author's port map: node X on switch
  port X, the head node on port 9; the switch is unmanaged as far as known, so
  no port counters. The next Pi session reproduces it with
  `-m 16384:16384` while sampling `nstat` on every node each second, and
  captures one node's traffic with `tcpdump` to see which segments are lost
  and whether the loss is at the switch (incast at step 1, where two nodes'
  64 KiB shares arrive at one) or a sender's burst. A cable swap is not
  indicated.
- **F2. Over Ethernet the tree's fan-out is a bandwidth decision for large
  messages.** Pipelining cannot take a broadcast below the root's k - 1 copies
  at line rate, so k = 2 beats the default k = 4 by 1.5× at 1 MiB and D ≥ 4,
  and a reduction by 1.45× at D = 8. Small messages pay a hop per level. The
  sweep ran from 64 KiB up, so the crossover is not measured yet (design §10,
  the fan-out item, now carries the numbers; L48).

Also learned: the head node has no `/usr/bin/time` and no `bc`; tier 1's label
carries the model checks, which take 12 to 20 minutes each on a Pi; OSU's
configure bakes the compiler's absolute path into every Makefile, so a moved
checkout needs `make distclean` and a new `configure`.
