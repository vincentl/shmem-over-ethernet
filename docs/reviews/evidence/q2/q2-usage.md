Analysis agent report for the minimal-core-API study (BRIEF-Q2). Date of source snapshot: 2026-09-16.

**Counting.** A script (`scratchpad/exp/usage-tools/count.py`, `classify.py`, `matrix.py`) strips C comments and matches `shmem_*`, `shmemx_*`, `nvshmem[x]_*`, and legacy `start_pes`/`shmalloc`/`shfree`/`my_pe`/`num_pes` followed by `(`. Fortran `call shmem_*` is matched case-insensitively. Names are then mapped to routine families. Local helper names that wrap a spec routine were aliased to that routine:
- Graph500's `shmem_long_min` and `shmem_ulong_bor` wrap `fadd` + `cswap`.
- Graph500's `*_all` helpers wrap `*_to_all`.
- Kokkos's `shmem_type_g/p` wrap typed `g/p`.
- pplx's `nvshmem_uint64_wait_until` counts as a signal wait.

**Caveats; read before using the numbers:**
1. The counts are **lexical call sites**, not runtime call frequency. Hotness is judged by reading the code around the important sites (section 2).
2. `#ifdef` alternatives are all counted. OSU has both `shmalloc` and `shmem_malloc` paths, and bale has UPC/MPI/SHMEM paths. Hot-path duplicates inflate counts.
3. Kokkos Remote Spaces call sites are mostly **typed-dispatch wrappers** (one per C type) plus operator templates. That makes 212 put/get and 130 atomic "sites"; the number of distinct usage points is much smaller, but they sit directly in the element-access path.
4. HClib apps call `hclib::shmem_*` wrappers that forward one-to-one. HClib's `shmemx_domain_*` (a pre-1.4 contexts precursor) is counted as contexts.
5. Test suites (`tests-sos/test/unit`, `spec-example`, `shmemx`) and SHOMS exercise the API for coverage. They are **not usage evidence**, and I report them separately.
6. The corpus misses private and closed codes: Cray/HPE SHMEM customer apps, classified Tri-Lab codes, and older POP/CCSM SHMEM modes. Absence in this corpus is weak evidence of absence overall.
7. GitHub code search needs authentication, and `gh` is not installed on this host. I could not run a GitHub-wide search, so the "no public users" statements below apply to this corpus plus targeted checks only.
8. Some NVSHMEM identifiers in these snapshots carry a `_warp` suffix: `nvshmemx_putmem_signal_nbi_warp`, `nvshmemi_ibgda_put_nbi_warp`, and in the Triton-distributed wrappers `nvshmemx_*_warp`. The local NVSHMEM source tree (`scratchpad/nvshmem-src/src/include/non_abi/device/pt-to-pt/*.cuh`, and `nvshmemx_*_warp` / `_block` / `_on_stream` variants) has the same spelling, so I report the names as *observed in source*. The suffix marks the GPU-kernel-granularity variant of the device API, alongside `_block` and `_on_stream`.

## 2. Hot-path idioms by code (reading the loops)

Everything in this section is *observed in source* at the SHAs in section 0.

1. **Graph500 (OSB and hclib copy)**, BFS inner loop, one iteration per edge (`ornl-languages/osb Graph500/mpi/bfs_shmem.c:190-222`): `shmem_long_min(pred2[off], v, pe)` is `fadd(x,0)` plus a `cswap` retry, followed by `shmem_quiet()`. Then `shmem_ulong_bor(bitmap[off], mask, pe)` is `fadd(x,0)` plus a `cswap` retry, followed by `shmem_quiet()`. Per level, one `shmem_int_lor_all`. This means ≥4 blocking remote atomic round trips and 2 quiets **per edge**, which is a direct translation of `MPI_Accumulate(MPI_MIN / MPI_BOR)`. Implications: (a) remote MIN, MAX and BOR as atomics would halve the trips; (b) a batched or aggregated form would help far more.
2. **HPCC RandomAccess / GUPs** (`GUPs/SHMEMRandomAccess.c:243-249`), per update: `longlong_g`, `longlong_p`, `quiet`, and conditionally `longlong_inc`. The threaded variant does the same on a per-thread context. These are single-word get/put/inc: the minimum-latency RMA path.
3. **Kokkos Remote Spaces**: each `view(pe, i)` access is a `shmem_<T>_g`/`_p` single-element RMA. `+=`/`++` on atomic views use `atomic_add`/`fetch_add`, and `*=`/`/=` use a `g` + `atomic_compare_swap` loop (`SHMEMSpace_Ops.hpp:249-337`). Block ops (`deep_copy`) use `shmem_<T>_get`/`put`. The hot primitives are single-word typed RMA plus CAS.
4. **bale conveyors** (`convey/putport.c`), per buffer flush: `shmem_putmem` or `shmem_putmem_nbi` of an aggregated buffer, then `shmem_fence` and `shmem_put64(&received[rank], &signal, 1, pe)` as a **hand-rolled put-then-signal**. Before that, `shmem_longlong_p(&consumed[slot], …)`. On-node peers use `shmem_ptr` and direct memory access. The collective mode uses `shmemx_alltoallv` when present, otherwise a `putmem` loop. **This hand-rolled pattern is what `put_signal` standardized, yet bale compiles the signal path out** (`private.h:21`).
5. **bale libgetput apps** (histo, ig, toposort, triangle; 20 `lgp_*` call sites in `apps/*_src/*.upc`): the AGP ("atomic get/put") variants issue one `shmem_atomic_add`/`fetch_inc`/`compare_swap`/`longlong_p`/`g` **per element**, with the PE computed as `index % n_pes`.
6. **ISx** (`ParRes/ISx SHMEM/isx.c:430-470`), per target PE per iteration: `shmem_longlong_fadd(&receive_offset, n, pe)` reserves space remotely, then `shmem_int_put` writes the bucket. This implements alltoallv with an atomic reservation. The 1.4 `wait_until` appears only to serialize printing (`:882`).
7. **PRK Stencil and Synch_p2p**: per iteration per neighbor, `putmem` halo + `fence` + `int_inc(flag)`, and the receiver does `int_wait_until(flag == k)` (`Stencil/stencil.c:430-477`). Synch_p2p does per-message `int_p` + `fence` + `wait_until`. This is again put-then-signal-then-wait, **hand-rolled**.
8. **NAS SP, BT and MG (Fortran)**: per timestep per face, `shmem_double_get`/`put` of line buffers, plus a `real8_sum_to_all` or `max_to_all` for norms. This is classical halo RMA.
9. **pplx-kernels** (GPU-kernel-initiated): dispatch sends `nvshmemx_signal_op(count+1, SET)` per destination expert, then `nvshmemx_putmem_signal_nbi_warp(dst, token, stride, &numRecv[group], 1, SIGNAL_ADD, rank)` **per token per expert** (`internode_dispatch.cu:104,157`). The receiver runs `nvshmem_uint64_wait_until(&numTokens[group], CMP_NE, 0)` then `wait_until(&numRecv[group], CMP_EQ, n)` (`:191-193`). Combine does the same (`internode_combine.cu:52,88,105,139`). **Put-with-signal plus signal-set plus wait_until is the entire hot protocol.**
10. **DeepEP** bypasses NVSHMEM's public RMA API on the hot path. It inlines IBGDA WQE posting (`csrc/kernels/legacy/ibgda_device.cuh:170-275`) and calls `nvshmemi_ibgda_put_nbi_warp` per token or chunk, `nvshmemi_ibgda_amo_nonfetch_add` for remote counters, `nvshmemi_ibgda_rma_p` for scalar puts, and `nvshmemi_ibgda_quiet`. The public API is used only for setup (`init_attr`, uniqueid, `team_split_strided`, `align`/`free`, `barrier`). This is strong evidence that the most performance-sensitive user wanted (a) GPU-initiated put, (b) remote counter add, and (c) explicit progress/quiet, with **zero library overhead**.
11. **Triton-distributed** device-side kernel calls (counts of `libshmem_device.*` references in `python/triton_dist/kernels` and `layers`): `signal_wait_until` 45, `barrier_all_block` 21, `signal_op` 20, `putmem_signal_nbi_block` 20, `fence` 19, `putmem_signal_block` 18, `putmem_nbi_block` 13, `putmem_warp` 10, `putmem_nbi_warp` 10, `remote_mc_ptr` 8, `getmem_block` 4. The same signal-centric pattern as pplx, plus explicit barriers and fences issued from kernels.
12. **PyTorch** symmetric memory (`nvshmem_extension.cu`): `nvshmem_put_with_signal` → `nvshmemx_putmem_signal_on_stream`; `nvshmem_wait_for_signal` → `nvshmemx_signal_wait_until_on_stream` (`:117-128`); `alltoallmem_on_stream`, `broadcastmem_on_stream`, `nvshmem_int64_p` (4), `ptr`/`mc_ptr`, `team_translate_pe`. In other words, the signal ops are **exposed as first-class PyTorch ops**.
13. **OSU OMB**: by design, `putmem`/`getmem` (blocking and `_nbi` + `quiet`), `put_mr` (a putmem loop to the next PE), one of each atomic per type, and `barrier`/`broadcast`/`collect`/`fcollect`/`reduce` (`*_to_all`). No teams, no contexts, no `iput`/`iget`, no `alltoall` in 7.5. These are the micro-benchmarks vendors tune for, so their op set de facto defines "the fast path" for evaluations.

## 4. What this implies for a minimal core API (usage side only)

These are inferences from the evidence above. They are not claims about any network.

1. **Must be fastest.** The four patterns below cover essentially all the HOT sites in the corpus:
   - Single-word typed RMA (`p`/`g`, typed put/get of 1 element): Kokkos, GUPs, bale, SSCA1.
   - Bulk `putmem`/`getmem`, blocking and NBI: convey, stencil, NAS, OSU, DeepEP/Triton-distributed.
   - Remote atomic add / fetch-add / compare-and-swap on 64-bit words: Graph500, bale, Kokkos, ISx, GUPs, DeepEP `amo_nonfetch_add`.
   - Cheap `quiet`/`fence` (progress/flush), including when nothing is pending: G500 and GUPs call it per op.
2. **Put-then-signal plus wait** is re-implemented by hand in CPU codes (bale convey `putmem` + `fence` + `put64(received)`; PRK `putmem` + `fence` + `inc` + `wait_until`; ISx `fadd` + `put`) and used natively in GPU codes (pplx, Triton-distributed, PyTorch, DeepEP internal). A core "RMA write with an attached remote counter update (ADD/SET)", plus a local "block or poll until a symmetric counter satisfies a predicate", would serve both groups. OpenSHMEM 1.5/1.6 `put_signal`/`signal_*`/`wait_until` then layer on top with no extra trips.
3. **Collectives** in real codes are dominated by `barrier_all` (phase fencing, often 2 per collective in bale) and **1-element reductions**. Broadcast, collect and fcollect are cold. `alltoall` is modest. **alltoallv** is what codes actually want (bale via `shmemx_alltoallv`, ISx via `fadd`+`put`, MoE libraries via put-with-signal). Collectives can live above the core, but barrier and small reduce must scale.
4. **Contexts** matter for threaded variants (GUPs_threaded, Graph500_threaded, hclib, SOS perf). The hot ops are unchanged; only the resource (per-thread endpoint) differs. The core needs a cheap per-thread or per-context send resource. The 1.4 teams-plus-contexts object model otherwise has only cold users.
5. **Candidates to implement "deliberately more slowly" in software**, justified by no hot users in this corpus: strided `iput`/`iget`, `ibput`/`ibget`, `alltoalls`, scans, sessions, `pe_quiet`, `team_ptr`, `team_split_2d`, `team_get_config`, the vector/any/some wait/test forms, locks (layer on CAS), `addr_accessible`/`pe_accessible` (asserts only), `realloc`/`calloc`/`malloc_with_hints`, and `global_exit`. **Caveat:** absence from ~18 public code bases, most of them benchmarks, is thin evidence for the newest routines. Sessions and `ibput`/`ibget` were designed for exactly the hot patterns above (bulk and repeated RMA to many peers), so they should stay implementable above the core without penalty. Do not demote them on usage grounds alone.
6. **`shmem_ptr`** (on-node load/store) is used by the most sophisticated CPU library (convey) and by the GPU codes (`mc_ptr`). It is a core-relevant capability, since it gives a zero-copy intra-node path.
