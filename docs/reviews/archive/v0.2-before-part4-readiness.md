## Verdict

**Ready to be public once Part 4 lands, after one named change; nothing blocks.**

**The named change (this round's Q5-1, *fix before release*)**: the README never
says that every node of a job must run the same osoe. 0.2 is the first release a
site can mix with an older one. A job that does - measured both ways round, a
0.1.0 node beside a 0.2 node - waits at its start until a timeout. Its notices
blame the hello and the ports, never the versions. The release note says it; the
README's Limits, which promise every limit a program can meet, do not. One
sentence fixes it.

**The rest are minors**, of which one is code:

- **A blocking get blames the wrong node** (this round's Q5-2). Its wait for room
  in the landing zone names its own target, even when the room is held by gets
  toward another node that has stopped. This is new since round eight: 0.1.0
  named no node there. Measured twice; a few lines to fix, best made before the
  tag.
- **The release note** omits what an upgrading user asks first: whether to
  rebuild. Measured here: they need not. A program built against 0.1.0 ran on
  0.2's library over one and two logical nodes, the exported names (3,595) and
  the installed headers identical.
- **Small drift**: the checklist's section for the tag, the indexes and the
  seam's comments have fallen behind the newest work, and two of the README's
  numbers - 422 tests where it says "about 410", a 29-second build where it says
  20 - drifted.

**The README tells an MPI programmer the truth about this tree.**

- **Its counts are exact.** 867 tests in the release preset, 467 of them
  `internode`, 40 models; the single-node build 404 - the full build's 399 and
  its own five (*measured*, both builds built).
- **Every settings row's default and range is the code's.** The subagent's sweep
  of every row against every parser found no wrong default, range or *checked*
  claim, and the clauses cited below were re-read in the source. Each of the 22
  invalid values tried in the two builds was refused by name with its range or
  form, and the two that differed between a node's PEs or between nodes were
  refused naming both (*measured*).
- **The newest sentences hold where they could be run.** Keepalive off on
  loopback, and `SHMEM_DEBUG` saying so. The zero-copy notice under `ulimit -l
  0`, the job finishing. The blocking get's limits paragraph, its arithmetic
  included.

**The failures are loud, and `osoe-stat` finds the hangs** - in the
single-node build as in the full build, wherever one node can fail:

- a dead PE or lead;
- a stopped node, under `OSOE_NO_PROGRESS_TIMEOUT`;
- a deadlock;
- a collective that differs between nodes;
- threads or teams exhausted;
- `/dev/shm` too small;
- no `shmem_finalize`;
- a stalled blocking get of one piece or many, which names its node and PE.

The exceptions are documented limits - a collective called differently within a
node, a stopped node's PEs looking like waiting ones - and Q5-2.

**The repository is fit to publish.**

- **The licence line**: every one of the 751 tracked source files carries it but
  the four specification examples, which carry the OSSS notice.
  `shmem.license-lines` has already caught one regression (`9bf176d`).
- **Nothing private** in the newest evidence or anywhere else, beyond the
  author's own address, which the author chose to keep.
- **No new third-party material.**
- **`docs/` reads as a record**: indexed at three levels; what drifted is a few
  lines.

**The seam is unchanged.** `transport.h` and `internode.h` have not moved since
round eight; the blocking get's thread-place block and the zero-copy refusal
live wholly below them.

### Q5-1. Nothing in the README says every node must run the same osoe, and a mixed job waits at its start blaming the network (fix before release: a sentence; high in the facts, medium in the rating)

- **Location**: README "Limits", "Launching" (`README.md:1020-1091`), whose
  nearest entry is "Every node of a job must have the same architecture"
  (:1068), and "When a job fails or hangs" (:545-573), neither of which names
  the version; `shmem/src/listener.c:44-46` (`HELLO_VERSION 4`, 0.1.0's 3) and
  :446-447, which drops a hello of the right magic and another version "as a
  stranger", saying nothing. The release note's draft says it
  (`docs/release-notes/0.2.0.md:91-96`).
- **Scenario**: a site upgrades its install to 0.2 but one node keeps 0.1.0 - a
  node-local prefix, an image not refreshed, a program built against an older
  prefix by its absolute run path. Every job that lands on that node and another
  waits at `shmem_init`.
- **Evidence** (*measured*, `e-upgrade.sh`; two logical nodes, node 0 running a
  program built and run against 0.1.0, node 1 one of 0.2, both orders,
  `OSOE_TEST_NOTICE_SECONDS=5`, `OSOE_NO_PROGRESS_TIMEOUT=20`):
  - 0.1.0's lead: "shmem_init on node 0 has waited 5 s for node 1, its child
    in the rendezvous tree, to call it on port 23769 (1 caller part-way
    through the hello); still waiting".
  - 0.2's lead: "shmem_init on node 1 has waited 5 s for node 0 (127.0.0.1, at
    127.0.0.1) to answer on its candidate ports in OSOE_PORT_RANGE=17000-26999:
    no answer to the hello on a candidate port".
  - At 20 s, "no progress for 20 s (OSOE_NO_PROGRESS_TIMEOUT): this node's lead
    has not finished the job rendezvous", status 1. Without the setting it would
    wait for the launcher (*documented*: no start-up wait gives up because time
    has passed).
  - Nothing names a version. A reader is sent to firewalls and port ranges; the
    one clue is "part-way through the hello". (Each PE's `SHMEM_VERSION=1` line
    does say 0.1.0 or 0.2.0, which is how I told them apart.)
- **Why it is a finding**: the Limits open with "What follows is every limit a
  program can meet". This one becomes reachable with 0.2, the first release
  with a predecessor, and the README is the reference that outlives the release
  note. The README's "A problem is worth a report" does ask for the line
  `SHMEM_VERSION=1` prints, which would show a mixed job to whoever compares
  the nodes' lines; nothing tells the user to compare them. The release note's
  sentence is accurate (*measured*: the start waits, with notices naming the
  node waited for, until a timeout).
- **Fix**: a Limits entry under "Launching" - every node of a job must run the
  same osoe; nodes of different versions do not recognize each other's hello,
  and the start waits with "no answer to the hello" until the launcher or
  `OSOE_NO_PROGRESS_TIMEOUT` ends it; `SHMEM_VERSION=1` shows each node's - and
  the same in a line of "When a job fails or hangs". After the release (Q5-8):
  a listener that meets a hello of the right magic and another version could
  say so, naming both, rather than dropping it unannounced.
- **Confidence**: high in the facts. Medium in the rating: a refuter may call
  it minor, since the note says it; it is rated for the README's promise of
  completeness and because 0.2 creates the case.

### Q5-2. A blocking get's wait for landing-zone room names its own target, though gets toward another node may hold the room - it sends the user to a healthy node (minor; high)

- **Location**: `shmem/src/transport-internode.c:858-866`, `make_room`, whose
  comment's premise "A blocking get's room comes back as the replies from the
  one node it asks land" is false when other gets hold the zone; its callers
  for a blocking get at :1084 (a piece at a time) and :1318-1319 (pieces
  together). Introduced by `c06ac75` (the blocking gets' read, finding on D-6),
  after round eight. 0.1.0's room wait named no node (`v0.1.0:shmem/src/transport-am.c:930-931`).
- **Scenario**: the landing zone is the PE's, shared by its threads and
  contexts, as the README says (:999-1001). A PE's gets toward node 2 fill
  it - its own nonblocking gets, or under `SHMEM_THREAD_MULTIPLE` another
  thread's large get - and then a blocking get toward node 1 waits for room.
  If node 2 stops, the waiting get's record and its no-progress message name
  node 1 and its PE.
- **Evidence** (*measured*, `c-failures.sh getmix` and `getmix_multi`; three
  logical nodes, `OSOE_NO_PROGRESS_TIMEOUT=10`): PE 0 issues `shmem_getmem_nbi`
  of 200 KiB from PE 4 (node 2), node 2 is stopped, then PE 0 calls
  `shmem_getmem` of 60 KiB (one piece) or 128 KiB (two) from PE 2 (node 1).
  - The message, both times: "shmem_get: no progress toward node 1 (PE 2) for
    10 s (OSOE_NO_PROGRESS_TIMEOUT): the landing zone's released extents has
    stayed at 0".
  - `osoe-stat` at 6 s: "shmem_get (reply from node 1) for 3.972 s".
  - Node 1 was healthy throughout; node 2 was the stopped one.
  - The same job with the blocking get toward the stopped node itself is named
    right: "shmem_get: no progress toward node 2 (PE 4) ... the landing zone's
    released extents", for 4 MiB, and "... the thread's reply slot" for
    32 KiB.
- **Why it matters**: §3.15's loud failure is "naming what it waited for", and
  D-6 is that a wait names its node. A wrong name is worse than none: on a
  cluster it sends the user to log in to the one node that is fine. It is
  narrow - a stall, and gets toward two nodes sharing the zone - but it is the
  common shape of a hybrid program whose threads get from different nodes, and
  the records (`docs/decisions/2026-10-10-blocking-gets.md`, `c06ac75`) claim
  these waits name their node.
- **Fix**: name the target only while this call's own pieces hold all the
  zone's held extents (the blocking get knows what it issued; `zone_bytes_held`
  gives the rest), and otherwise keep the nonblocking form, which names no node
  and gives the zone's bytes - or name the node of the oldest record holding
  extents. A test like `getmix` - a nonblocking get toward a stopped node, then
  a blocking get elsewhere - would pin it. Cheap; best made before the tag, with
  Part 4's gets section about to exercise the zone.
- **Confidence**: high.

### Q5-3. The release note omits what an upgrading user asks first, and one number (minor; high)

- **Location**: `docs/release-notes/0.2.0.md:16-24` ("Every installed header
  is 0.1.0's byte for byte, and the library exports the same names") and
  :87-90 ("The costs"); :206-207 ("about twenty seconds"); the release
  checklist's soname item, `docs/release-checklist.md:153-157` ("a program
  built against 0.1.0 should link and run against 0.2, which no one has
  tried").
- **Evidence** (*measured*, `e-upgrade.sh`):
  - **The exported names are identical.** `nm -D --defined-only`: 3,595 names
    in 0.1.0's library and 3,595 in 0.2.0's, none in only one. The fact-check
    could not run this; the note's claim is true.
  - **The installed headers are identical** (`diff -r`).
  - **A program built against 0.1.0 runs against 0.2 unchanged.** The README's
    ring was built against an install of 0.1.0, then this tree (as 0.2.0) was
    installed over that prefix: `libosoe.so.0` moved to `libosoe.so.0.2.0`. The
    same binary then printed "osoe 0.2.0, OpenSHMEM 1.6" and the four right
    lines, status 0, on one node and on two logical nodes.
  - **`osoe-stat` of either version reads the other's job's segments**
    (`--summary`, both ways, status 0).
  - **The quick start's build** took 29 s at `-j4` (above), against the note's
    and the README's 20 (Q5-5).
- **What the note leaves out** that a user of 0.1.0 needs:
  - **No rebuild is needed.** The soname is still `libosoe.so.0`, so installing
    over the old prefix moves existing programs to 0.2. That is now tried, with
    the README's ring, and the checklist's "which no one has tried" can say so.
    It is worth a run of its own on the tagged tree, since a program's statics
    and the linker script are what a layout change would break.
  - **Every node and every program moves together.** The note says nodes of the
    two versions do not form one job. It does not say that an upgraded prefix
    upgrades every program built against it at once, and that a program built
    against a prefix left at 0.1.0 is a 0.1.0 node in a mixed job (Q5-1).
  - **The other costs.** Besides the internal region, the note's "two sockets
    for every other node" doubles a lead's descriptors per peer. `shmem_init`
    raises the soft limit to the hard one, so where the hard limit is 1,024 a
    lead of 256 PEs runs out at about 385 nodes (`init.c`'s comment), where
    0.1.0's ran out short of 800. The default connection buffer doubled too, so
    each peer node costs the connection area 512 KiB of `/dev/shm` where it
    cost 256.
- **Checked and true** (*measured* or *observed in source*, against `v0.1.0`):
  - the eleven new settings and the five changed defaults (the settings tables
    of both READMEs compared, none removed);
  - the internal region 6.03 MiB at four nodes in 0.1.0's README;
  - `osoe-launch` not installed by 0.1.0 (`v0.1.0:tools/launch/CMakeLists.txt`
    has no install rule);
  - the hello's version 3 against 4, and the wait a mixed job makes;
  - the zero-copy refusal's notice and the job completing (below);
  - the Pi and loopback figures quoted, against the README and the records
    they cite: 1.43 to 1.47, 1.20 to 1.26, 1.32 to 1.41, 3.3 to 3.9 against
    17 to 20 ms, 1.67 against 4.1 to 4.4 ms, a fifth less for a mebibyte's
    get.
- **Fix**: a sentence in "What changed": programs built against 0.1.0 run on
  0.2 without a rebuild (the soname is `libosoe.so.0`), and every node, and
  every install a job's programs load from, must be upgraded together. A
  clause on descriptors under "The costs". "About thirty seconds". The
  checklist's soname item amended.
- **Confidence**: high in the facts; minor, since the note is a draft its
  checklist item makes true at the tag.

### Q5-5. Two counts and a few settings clauses have drifted from the tree (minor; high)

*Measured*, or *observed in source* as marked.

- **"About 410 of the test suite's 867 tests fail" where io_uring is refused**
  (README :301-305): 422 of 867 fail under `deny-io-uring setup`, every one

  note's "about twenty"): 29 s at `-j4` on an idle VM of the same kind. The
  figure was measured on 2026-10-04 (`5ee2225`), on 0.1.0's smaller tree.
- **Scans under `tree`** (*observed in source*). The `OSOE_COLLECTIVE_FANOUT` and
  `OSOE_COLLECTIVE_PIPELINE` rows (:1491-1492) say a scan keeps 0.1.0's fan-out
  and window "under `link`". `internode-generic.c:2442-2458` keeps them under
  every shape but `fixed`, and the `OSOE_COLLECTIVE_SHAPE` row (:1494) says
  "under `link` and `tree`". It is the same kind of clause as round eight's
  Q5-7, two rows over. `SHMEM_INFO` (`init.c:155`) says "a scan keeps 2 under
  link" alone.
- **`OSOE_HEAP_SHIFT`** (:1535; *observed in source*): "A size". The code
  refuses anything not a whole number of pages (`bootstrap.c:540-543`), so `4k`
  is refused on a Pi 5's 16 KiB pages. The `OSOE_HEAP_BASE` row says its rule;
  this one does not.
- **`OSOE_TEST_NOTICE_SECONDS`** (:1539; *observed in source*): a value outside

  30 s (`base/stall-watch.c:33-38`). Every other setting refuses a bad value by
  name. It is a testing hook; refuse it, or say so.
- **Fix**: the numbers as measured, or in words; the two rows' "under `link` and
  `tree`"; the two testing rows' clauses.

## The seam

*Observed in source.*

- **Unchanged since round eight.** `git diff c897948 3b45472` leaves
  `transport.h` and `internode.h` untouched, and `internode-backend.h` changed
  one comment ("data wires" for "wires"). Round eight's reading - a contract a
  backend of AM's shape implements, with one leak, the detector's use of AM's
  owner records (its Q5-8, on the checklist) - stands.
- **The blocking get's thread-place block lives below the seam.**
  - The block is in the node segment (`node.h`, on the boundary in
    `cmake/CheckBoundary.cmake`), indexed by `osoe_node_thread_context`.
  - Only `transport-internode.c`, the internode backend, uses it.
  - Its 4,095 limit is AM's token's twelve owner bits, a limit the README
    states (:1011-1013).
  - An RDMA backend whose gets are reads into a registered buffer would leave
    the block unused - 128 bytes of the control segment for each thread place
    of each PE - with nothing to rewrite above the seam.
- **The zero-copy refusal is wholly below.** It lives in `ring.c`, `progress.c`
  and `wire.c`, plus one function of `base/` (`osoe_locked_memory_kib`) that the
  probe shares.
- **Keepalive's default is below; the documentation of it is above.** The
  decision is made in `progress-host.c`. Above the boundary,
  `bootstrap.c`/`.h` gained a flag saying the setting was given, and
  `SHMEM_INFO` (`init.c`, the API's file) states AM's keepalive default, as it
  has stated AM's settings since 0.1.0. That text would be a porter's to edit,
  not code to rewrite.
- **What a porter would misread is Q5-7's comment in `transport.h`.**
