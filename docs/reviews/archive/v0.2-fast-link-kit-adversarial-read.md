## Verdict

**Not ready to rent machines for as written.**

**One finding is fatal** to the decision the kit exists for, §5's progress helpers:

1. **`multistream` sends each node's whole stream to one peer node at a time.** Every PE of a node
   has the same target list and starts on the same peer. So the sweep cannot show what helpers buy,
   which is traffic to several peers at once. §7's and §8's stream runs inherit the same pattern.

**Eight should be fixed before a node is rented:**

2. **Thirty-two PEs a node are more tasks than a `c4-standard-16` has CPUs.** `srun` refuses them
   without `--overcommit`: 48 of the sweep's 144 jobs, and three start-up jobs.
3. **Debian 13 keeps `/usr/sbin` off a user's `PATH`.**
   - `slurm-setup.sh`'s `ssh node slurmd -C` finds no `slurmd`, so it writes a `slurm.conf` with no
     nodes.
   - `facts.sh` records no `sysctl` value, silently, and no `ethtool` fact.
4. **The bare aggregate is not a baseline for §5:**
   - each side's k processes are bound to one core, since `on` passes no `--cpu-bind=none`;
   - it runs in one direction, where `multistream` loads both;
   - it is never printed beside the helper table, as §5 says it is.
5. **`floor.sh` can wait for ever.** A client that misses its server leaves the server's job
   running, and nothing bounds `wait`.
6. **The kit describes two unmerged branches as if this commit held them:**
   - a blocking get's pieces in flight together (`blocking-gets`);
   - the copy fallback for want of locked memory (`zero-copy-memlock`).
7. **`summarize.py` hides missing rounds and connections,** and rounds CPU a GiB to one decimal.
8. **Nothing ends a stuck job short of 900 s on eight nodes:** no `OSOE_NO_PROGRESS_TIMEOUT`, and no
   `timeout -k`. And one and four helpers would run for the first time anywhere on the rented
   nodes.
9. **`SOS_BUILD` is looked for under a `test/` that `docs/pi-cluster.md` §8 does not make,** and the
   build exists on the first node only.

## Findings, ranked

### Fatal

**1. `multistream` sends each node's traffic to one peer node at a time, so the helper sweep cannot
show what helpers buy** (*observed in source*; the target lists *measured* by rebuilding them; how
long the convoy lasts *measured* only in a processor-sharing model, Appendix)

- **Where:**
  - the target list: `docs/fast-link/multistream.c:154-161`;
  - the comments it contradicts: `:5-7` and `:154-155`;
  - a quiet every 8 MiB: `:164-165` and `:176-186`;
  - used by: `helpers.sh:25-30`, `zero-copy.sh:34-37` and `gets.sh:20-21`.
- **What.** Each PE lists the PEs of other nodes in the order (me + k) mod npes, k = 1, 2, and so on.
  - Under the block layout every PE of a node gets the same list, and it starts at the next node's
    first PE. On 8 nodes of 8 PEs, PEs 0 to 7 all start at PE 8 and go 8, 9, ..., 63. PEs 8 to 15
    all start at PE 16.
  - The comment says the node's PEs "start on different peers". They start on the same one.
  - With 1 MiB blocks a quiet falls every eight operations. So every 8 MiB a PE moves goes to one
    peer node: one window a node at 8 PEs a node, four windows in a row at 32.
  - A blocking 1 MiB put holds its PE on that connection until most of it has drained through the
    256 KiB buffer. A 1 MiB nonblocking get waits on its 256 KiB landing zone. So a node's PEs move
    as a convoy: the whole node sending on one data wire, to one peer, and receiving on one other.
- **How long the convoy lasts.** The model is per-wire processor sharing, every wire with its own
  capacity, blocks jittered by ±10%, over a ten-second window's blocks (about 400 a PE at 8 PEs a
  node, 100 at 32):

  | PEs a node | `multistream`'s order | Targets interleaved, offset by local rank |
  |---|---|---|
  | 8 | 2.0 to 2.8 peers at once, of 7 | 3.8 to 4.2 |
  | 32 | 1.5 | 6.2 to 6.4 |

  Without jitter, `multistream`'s order stays on exactly one peer.
- **Why it matters.**
  - Helpers own peers, not streams. A peer's data wire is owner 1 + (p mod H)'s
    (`shmem/src/owner-map.h:5-10`). The README says what helpers add is "the traffic to several
    peers at once" (`README.md:1163-1165`).
  - With one to three peers busy a node, helpers 3 and 4 idle, and the sweep would report that two
    helpers buy what four do. That would be worst at 32 PEs a node, the top of the brief's range.
  - It would also measure something else under the helper count's name: every PE of a node waiting
    on one connection's buffer. That is the wake cost `README.md:1201-1209` leaves unmeasured at
    many PEs.
  - §7's zero-copy runs inherit it: a buffer by reference holds one connection for a round trip, and
    one connection is all a node uses at a time.
  - So does §8's get stream: a node's PEs share one connection's 64 reply credits
    (`am-configuration.h:51`; `reply.h:35-41`). If each piece in flight holds a credit - the
    proposal names the zone and the credits as a get's two limits - then at 8 PEs a node a landing
    zone above about 512 KiB is held by the credits, not the zone.
- **Fix:**
  - For a PE of local rank r on node n, make target i the PE of local rank (r + i div (N-1)) mod P
    on node (n + 1 + (r + i) mod (N-1)) mod N. Consecutive operations then go to different nodes,
    and a node's PEs start on different ones. A per-PE seeded permutation would also do.
  - Print, for each node, the bytes sent to each peer (or read `osoe-stat`'s per-wire counters around
    the window), so that the spread is in the output rather than assumed.
  - Keep the present order only as a named one-peer case, if wanted.

### Should fix

**2. Thirty-two PEs a node are more tasks than a `c4-standard-16` has CPUs, and `srun` refuses them**
(*observed in source*; the rule from `srun`'s manual)

- **Where:**
  - `docs/fast-link/helpers.sh:15`: `PES_PER_NODE` "8 16 32";
  - `scale.sh:22`: start-up at 1, 8 and 32;
  - `common.sh:21`: `KIT_SRUN` is `-K1 --cpu-bind=none` and nothing else;
  - `slurm-setup.sh:27-30`: each node's CPUs as `slurmd -C` reports them, 16 on a
    `c4-standard-16`. The partition (`:51`) does not oversubscribe.
- **What.** `srun`'s manual: without `--overcommit` it will not start more than one process a CPU.
  `-N8 --ntasks-per-node=32` on nodes of 16 CPUs fails at allocation.
- **Why it matters.**
  - It loses 48 of the sweep's 144 jobs and the three 32-PE start-ups, at the top of the brief's "8
    to 32 PEs a node".
  - The summary then drops those rows without a word (finding 7).
  - `osoe-launch` has no such rule, so the dry run could not show it.
- **Fix:** `--overcommit` in `KIT_SRUN`'s default. With `--cpu-bind=none` and no cgroup plugin the
  tasks run on every CPU of the node anyway, and `--exclusive` beside it keeps Slurm's books on the
  whole node. Add one `srun` at 32 PEs a node to §3, before the sweep.

**3. Debian 13 keeps `/usr/sbin` off a user's `PATH`: `slurm-setup.sh` writes a `slurm.conf` with no
nodes, and `facts.sh` records no `sysctl` and no `ethtool`** (*observed in source*: Debian's
packaging; *recalled*: that `bash` run by `sshd` for a command keeps `sshd`'s `PATH`, and what
`slurmd` does with no line for its host)

- **Where:**
  - `docs/fast-link/slurm-setup.sh:27-30`: `ssh "$n" slurmd -C | sed ... | awk ...`;
  - `facts.sh:31`: `ethtool`;
  - `facts.sh:32-36`: `sysctl`, with its errors sent to `/dev/null`.
- **What the packaging says:**
  - `slurmd`, `sysctl` and `ethtool` live in `/usr/sbin`; slurm-wlm 24.11.5's `slurmd` is
    `/usr/sbin/slurmd`.
  - Trixie's openssh is built with a default `PATH` for users of
    `/usr/local/bin:/usr/bin:/bin:/usr/games` (`debian/rules`, outside Ubuntu).
  - base-files' `/etc/profile` gives users `/usr/local/bin:/usr/bin:/bin:/usr/local/games:/usr/games`.
- **What `slurm-setup.sh` then does:**
  - Over `ssh`, `slurmd -C` is "command not found". The pipeline's status is `awk`'s, so `set -e`
    does not stop.
  - `NODE_LINES` is empty, and the `slurm.conf` printed and installed on every node has a partition
    and no `NodeName`.
  - `slurmd` has no line for its host and does not start. The script ends at the first
    `systemctl restart slurmd`, with Slurm down everywhere.
- **What `facts.sh` then does.** Its steps carry the login shell's `PATH`, since `srun` exports it.
  - `sysctl` is not found, and the error goes to `/dev/null`. So the TCP buffers, the congestion
    control, `tcp_notsent_lowat` and `io_uring_disabled` are silently absent.
  - The `ethtool` facts are "command not found" lines.
- **Why the dry run passed.** In the VM both ran: its `facts.txt` has every `sysctl` line and the
  `ethtool` output (*measured*). That shell had `/usr/sbin`, which a stock Debian login does not.
- **Fix:**
  - Call `/usr/sbin/slurmd -C` (or `sudo slurmd -C`), and stop unless `NODE_LINES` has one line a
    node.
  - Read `/proc/sys/...` directly, and call `/usr/sbin/ethtool`.
  - Never send a fact's error to `/dev/null`.

**4. The bare aggregate is one core's on each side, runs in one direction, and is never set beside
the helper table** (*observed in source*; Slurm's auto binding from its manual, and *recalled*)

- **Where:**
  - `docs/fast-link/common.sh:84-92`: `on` runs `srun -N1 -n1 -w NODE`, with no `-c` and no
    `--cpu-bind`;
  - `floor.sh:31-38`: k servers in one step, k clients in another;
  - `floor.sh:46-49`: `iperf3` the same;
  - `summarize.py:145-151`; `docs/fast-link.md:189-196`.
- **One core.**
  - Each side's k processes are one Slurm task of one CPU. With `TaskPlugin=task/affinity`, a
    one-task step on a one-core allocation is bound to that core by default (auto binding).
  - The README says the same of a full node (`README.md:1062-1063`). That is why `KIT_SRUN` carries
    `--cpu-bind=none` - which `on` does not.
  - So 16 servers share one core's two threads, and so do 16 clients and `iperf3 -P 16`'s threads.
  - The curve flattens where a core does, not where the link does.
- **One direction.** It runs client to server, where `multistream` loads every node both ways at
  once.
- **Summed medians.**
  - Summing each connection's median of seven fixed-size streams is an aggregate only while all k
    stream at once, and nothing checks that.
  - Each client also runs a 64 MiB copy and a fence loop after its trials (`echo-uring.c:736`),
    on the core the others are still streaming on.
- **Not beside the helper table.** §5 says `summarize.py` prints the bare aggregate "at the matching
  connection count" beside each helper row. It prints the two in separate tables, and nothing defines
  the matching count.
- **Why it matters.** §5's rule (`fast-link.md:192-196`) is whether a helper count raises a node's
  rate toward its bare aggregate. A baseline capped by one core makes every helper count look near
  the link, or past it.
- **Fix:**
  - Run `on` with `-c "$(nproc)" --cpu-bind=none`, or `--exclusive`.
  - Take the aggregate over one span: `iperf3`'s `-t` sum, or all k streams' bytes from the first
    start to the last end.
  - Add the other direction (`iperf3 --bidir`, or servers and clients on both nodes).
  - Print it beside the helper table, or drop the sentence.

**5. `floor.sh` can wait for ever** (*observed in source*)

- **Where:**
  - `docs/fast-link/floor.sh:31-40` and `:46-50`;
  - `tools/echo-uring/echo-uring.c:402-418`: the server loops until it is sent a `QUIT`;
  - `echo-uring.c:464-468`: a client that cannot connect exits.
- **What.** The servers' job starts in the background, then `sleep 2`, then the clients' job.
  - A client that dials before its server listens fails and exits without sending `QUIT`, and so
    does one that dies mid-run. A slow allocation or launch of the servers' job is enough for the
    first.
  - Its server then never returns, the servers' job never ends, and `wait "$servers"` (`:40`) waits
    with no bound. `on` has no timeout.
  - `iperf3 -s -1` waits for its one client the same way (`:46-50`).
- **Why it matters.** It is a stall that nothing on the clock ends, in the first session's last step.
- **Fix:**
  - Put `timeout` around both `on` calls.
  - Wait for the port before starting the clients, or make the client retry its connect.
  - `scancel` the servers' job once the clients' job ends.

### Notes

**10. `srun` under `timeout` keeps the terminal as its input** (the mechanism *recalled*; the remedy
*observed* in `docs/pi-cluster.md`)

- `launch` (`common.sh:73`) runs `srun` with the terminal as standard input, which `srun` forwards
  to the tasks by default.
- It runs inside `timeout`'s own process group, outside the terminal's foreground, where a read
  stops it with `SIGTTIN`. A keystroke during a sweep could hold a job until `KIT_TIMEOUT`.
- `docs/pi-cluster.md`'s loops give `srun` `< /dev/null` (`:395`, `:528`). Do the same, or use
  `--input=none`.

**11. The two-node sections do not pin their pair** (*observed in source*)

- `floor.sh:23-24`, `ladder.sh:37` and `gets.sh:18` run `launch 2 ...`, which lets Slurm choose two
  nodes. The bare stream runs between `NODES`' first two, by `-w`.
- In practice `cons_tres` takes the first idle nodes in `slurm.conf`, which `slurm-setup.sh` writes
  in `NODES` order, so the pair will usually match (*recalled*).
- `-w "$(node 1),$(node 2)"` makes it so.

**12. `PropagateResourceLimits=NONE` takes every limit from `slurmd`, not only memlock**
(*observed in source*, Debian's units; glibc's fallback *recalled*)

- **Every limit** (`slurm-setup.sh:41`). Trixie's `slurmd.service` sets `LimitNOFILE=131072`,
  `LimitMEMLOCK=infinity` and `LimitSTACK=infinity`, so the steps get an unlimited stack as well.
  - glibc then sizes threads' stacks by the architecture's default rather than `ulimit -s`: 2 MiB on
    x86-64, against the 8 MiB the Pi's and the VM's limits gave (*recalled*). osoe's threads have
    not run that way.
  - `facts.sh` records only memlock and the open files.
- **The narrower setting.** `PropagateResourceLimitsExcept=MEMLOCK` gives the steps an unlimited
  memlock and the session's other limits.
- **The drop-in** (`:67`) repeats what Debian's unit already sets.
- **The pid file.** `SlurmctldPidFile=/run/slurmctld.pid` (`:44`) cannot be written: Debian runs
  `slurmctld` as `User=slurm`, with `RuntimeDirectory=slurmctld`. It logs an error, and nothing
  more.

**13. What the runbook leaves to the reader before §1 works** (*recalled*, but the C4 line from
Google's page)

- **The firewall.** §0's ports omit Slurm's: 6817 and 6818, `srun`'s ephemeral ports back to the
  first node, and `ssh`. A VPC made for the run - to choose its MTU, say - starts with no rule
  between its instances; "allow all TCP between the nodes" is the line to give.
- **Access:**
  - how the tree reaches the first node;
  - how the first node reaches the others over `ssh`, since the keys are on the Mac;
  - the host keys asked on first contact inside `slurm-setup.sh`'s loops
    (`StrictHostKeyChecking=accept-new` would answer them).
- **One user id on every node,** since Slurm runs tasks by user id. OS Login gives it. Accounts made
  on each instance from metadata keys may not.
- **The installs:**
  - `apt-get update` before them;
  - `iperf3`'s install question on the first node's terminal - a yes starts a daemon on 5201;
  - `DEBIAN_FRONTEND=noninteractive`.
- **The disk.** C4 boots from Hyperdisk only.
- **Each session.** Machines deleted between sessions mean §1 and §2 again every session. The plan's
  sessions 2 to 4 do not budget them.
- **The names.** `NODES` must hold Slurm's node names - the short hostnames `slurmd -C` reports.
  `on` passes them to `-w`, and `SlurmctldHost` takes what comes before the first dot, so an IP
  address breaks it.

**14. `multistream`'s accounting, smaller points** (*observed in source*)

- **The counter dump.** PE 0 runs `osoe-stat` before it reads its CPU and starts its clock
  (`multistream.c:168-172`), while the others have started.

  - The "start" counters miss the others' first milliseconds.
  - Zero-copy runs only.
- **Every PE's agent.** `thread_cpu` counts every PE's `osoe-agent`: `init.c:384` starts one on

- **CPU no named thread holds.**

  - `io_uring`'s worker threads (`iou-wrk-*`) count as the program's.
  - A node's `/proc/stat` busy time over the window would bound the total.
- **The get's buffer.** Gets land in one reused buffer, so the copy out of the landing zone is into
  cache-warm memory.

- **`multistream`'s arithmetic, finding 1's ordering aside:**
  - `shmem_ptr` picks the remote PEs;

  - the slowest PE's time comes from a max reduction over symmetric statics;

  - Its JSON keeps the transport counters per owner, so summing a leaf name across owners is the
    node's total, with nothing counted twice.
  - The segment regex picks node 0's record.

  alternates. The job counts are as stated: 144, 33, 24, 24 and 36.

  connection as it needs.

## Appendix: the model behind finding 1

Per-wire processor sharing: each directed node pair is one wire of capacity one block a unit of
time, shared equally by the PEs putting on it - as if every wire had its own owner and the NIC no
limit. Block sizes are jittered by ±10%. It reports node 0's mean count of distinct peers in use,
over a ten-second window's blocks. Three seeds were run at each size.

```python
import random
def run(N, P, order, jitter, blocks_each, seed):
    rnd = random.Random(seed); npes = N * P; node = lambda pe: pe // P; lists = []
    for me in range(npes):
        t = [(me + k) % npes for k in range(1, npes) if node((me + k) % npes) != node(me)]
        if order == "interleaved":
            local = me % P; peers = [(node(me) + 1 + j) % N for j in range(N - 1)]
            t = [peers[(j + local) % (N - 1)] * P + (r + local) % P for r in range(P) for j in range(N - 1)]
        lists.append([node(x) for x in t])
    pos = [0] * npes; left = [1 + rnd.uniform(-jitter, jitter) for _ in range(npes)]
    done = [0] * npes; area = span = 0.0
    while min(done) < blocks_each:
        wire = {}
        for pe in range(npes):
            wire.setdefault((node(pe), lists[pe][pos[pe] % len(lists[pe])]), []).append(pe)
        rate = {pe: 1.0 / len(pes) for pes in wire.values() for pe in pes}
        dt = min(left[pe] / rate[pe] for pe in range(npes))
        area += len({w for w in wire if w[0] == 0}) * dt; span += dt
        for pe in range(npes):
            left[pe] -= rate[pe] * dt
            if left[pe] <= 1e-12:
                pos[pe] += 1; done[pe] += 1; left[pe] = 1 + rnd.uniform(-jitter, jitter)
    return area / span
# run(8, 8, "multistream", 0.1, 400, s)  -> 2.11, 2.02, 2.84;  "interleaved" -> 3.84, 4.19, 3.92
# run(8, 32, "multistream", 0.1, 100, s) -> 1.45, 1.46, 1.47;  "interleaved" -> 6.43, 6.43, 6.23
```
