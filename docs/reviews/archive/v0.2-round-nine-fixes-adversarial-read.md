### R9F-3. The gate cannot see layout settings that a test's script sets (note)

- **Where:** `cmake/thread-sanitizer-gate.py:113-132`.
- **The gap.** The gate reads each test's settings from ctest's list alone: the
  test's command and its environment.
  - `shmem.link.few-lanes.0-1` runs `link.sh`. The script sets
    `OSOE_COLLECTIVE_FANOUT=2` and `OSOE_COLLECTIVE_PIPELINE=1` itself
    (`shmem/tests/link.sh:37-39`).
  - So the gate judges that test at fanout 8.
- **What that misplaces.** At fanout 2 on two nodes, the internal region's
  lanes begin at offset `0x238000`. Offset `0x238200` lies inside a lane slot.
  The real place program names that offset differently at the two fanouts:
  - at fanout 2: `past-the-team-words`;
  - at fanout 8: `lane-word`.
- **What happened (*measured*, `logs/batch3/synthetic-gate.txt`).** I wrote a
  synthetic report of two helpers' `osoe_am_parse` landings at that offset of
  the test's heap.
  - The real gate, using the real place program, **passed** it: "in the
    internal region, at its lane-word: osoe_am_parse against osoe_am_parse".
  - Control: the same offset in `shmem.circulant.5.ceiling-2` failed. That
    test's fanout 2 is on its command line, and the gate reported "at its
    past-the-team-words, not among those explained".
- **How far it reaches (*measured*, across all 610 tests' commands).** This is
  the only multi-node test whose script sets a layout setting.
  - `dev-shm-capacity.sh` sets sizes, but only for single-node jobs and a
    refused one.
  - The size regex misses formats the library accepts, such as `3.1M`, `1e6`,
    `20kk` and `64MB`. Only `shmem.heap-size.3.1M` uses one, and it is a
    single-node test: with no helper, any report there fails anyway.
- **Why it is only a note: no current exposure.**
  - With two nodes, node 1 has one peer. One helper lands everything there.
  - The program splits no team.
  - So no landing-against-landing or zeroing race can arise in that test.
- **Why it still matters.** The README says a report there passes "only at the
  places ... the gate names". For this test, a later change could make that
  false without anyone seeing it.
- **Fix.** One of:
  - give `few-lanes` its settings through the test's environment;
  - have the gate refuse to pass an internal-region report of a test whose
    command runs a script (`sh`, `-P`).

### R9F-4. The gate ignores tool lines it does not recognize, if the file also holds a report it passes (note)

- **Where:** `cmake/thread-sanitizer-gate.py:229-230`.
- **The gap.** The gate fails only lines beginning `ERROR: ThreadSanitizer:`,
  and files with no report at all (lines 244-245).
- **What happened (*measured*, `logs/batch3/synthetic-gate.txt`).** I gave the
  real gate two files, each with one passing heap race plus a fatal runtime
  line. Both files passed:
  - one with `ThreadSanitizer: CHECK failed: ...`;
  - one with `FATAL: ThreadSanitizer: unexpected memory mapping ...`.
- **Why it matters.**
  - Both lines end the process through the runtime's `Die()`. Under
    `abort_on_error=1` that is SIGABRT.
  - A test judged by its exit status fails on that.
  - A test judged by a pass expression does not, if another PE has already
    printed the pass line.
  - Such lines are rare, so this is a note.
- **Fix.** Fail any line of the file that falls outside the report blocks and
  the "reported N warnings" line. At least fail lines matching
  `ThreadSanitizer: CHECK failed|^FATAL: ThreadSanitizer`.

### R9F-5. "Neither can make a program that ran before fail" holds for the program, not for the user's other processes (note)

- **Where:** `README.md:1737-1738`, and the comment at `shmem/src/init.c:314-316`.
- **What the kernel does.** The locked-memory count is the user's, for the whole
  host. Each process is checked against its own soft limit.
  - The P9-1 refuter measured this: `budget.c`, run as a separate process, found
    the leads' rings charged against its own limit (*documented*).
- **What changed.** Before this change, each osoe process stopped at its own
  soft limit. Where the hard limit is higher, osoe's processes can now hold
  more than another process's limit. A Slurm step on the Pi has no hard limit.
- **The clearest case.** It concerns the zero-copy send, which is off by
  default.
  - Before, a send the limit refused was sent again by copy. The job ran and
    stayed under 8 MiB.
  - Now no send is refused, so the job can hold more.
  - Any process of the same user still at 8 MiB is then refused what it had
    before. Examples: another program's ring on Linux 6.14 or later, or a 0.1.0
    job beside it.
- **In the suite.** `env.probe` and `env.echo-uring` make rings without calling
  `shmem_init`. On a 6.14 or later kernel, a full `ctest -j4` run under a higher
  hard limit could refuse them beside the 64-node tests.
  - That is computed, not measured: the refuter measured nine pages per lead at
    two helpers, so 64 leads hold about 9 MiB.
  - The runbook's tier 2 is not exposed: every ring-maker there calls
    `shmem_init`.
- **Fix.** Add one sentence, for example: "the count is the user's on the host:
  while a job holds more than another process's own limit, that process -
  another program, or a release before 0.2 - is refused what it would have
  been given".

## What I checked and found sound

**The helpers' release (`shmem/src/progress-host.c:1142-1162`, `1243`,
`1331-1373`; *observed in source*, *measured*).**

- When a helper reaches `wait_released`:
  - The only way in is `return wait_released()` from `helper_main`
    (`1202`, `1213`).
  - That happens only after the helper's last `say_stop(HELPER_DONE)`.
  - The helper gets there by a `REQUEST_STOP`, which only
    `osoe_progress_host_exit` posts; that function always joins, after
    `wait_helpers(NULL)` has seen every helper done.
  - Or it gets there by the node's abort, which ends the process: either
    through `osoe_progress_host_abort` then `osoe_abort_end`, or through a
    sweep's `osoe_abort_end`.
- What the agent does with each helper:
  - It releases only helpers it then joins: in `join_helpers` every started
    helper, and in `leave_helpers` only those whose `stop` is at least
    `HELPER_DONE`.
  - `HELPER_DONE` is the last store before the wait, so no join waits on a
    thread that cannot return.
  - The rest are detached.
  - `started` is cleared either way, so no helper is joined or detached twice.
- Hazards that do not arise:
  - No helper can wait in a process that goes on running.
  - A later session gets a fresh `osoe_am.owner` array, and `released` is
    zeroed before `pthread_create`.
  - A fatal on any thread ends the process by `_exit`, with the waiting
    helpers still running.
  - The deaf-helper hook and `OSOE_TEST_ABORT_DELAY_MS` (at most half the
    grace) end inside the agent's grace.
- §3.16: one acquire load and one release store. The futex is private, on
  process-private memory, and sleeps a sweep at a time.
- The four death-path tests at two and three helpers ran 10 of 10 with no thread
  leak, and the gate passed (*measured*, `logs/batch2/leaks-*`). The lead
  reverted to the parent's `progress-host.c` and saw leaks.

**A blocking get's wait for room (`shmem/src/transport-internode.c:832-839`,
`852-905`, `1112`, `1346`; *observed in source*).**

- Why `bytes_in_flight(own)` counts this get alone:
  - `own` is the calling thread's thread-place block. No program context uses
    it.
  - `complete_gets` leaves it balanced at every return.
  - The one exception is a thread cancelled inside its get, which leaves the
    block unbalanced for whichever thread takes the place next. Cancelling a
    thread inside a call is unsupported (round nine's C9-3).
- Why it cannot underflow, and when it can change:
  - While `make_room` waits, `bytes_issued` does not move, because no piece is
    issued.
  - `bytes_copied` only grows, and a piece is counted copied only after it was
    counted issued. The `issued > copied` guard covers the rest.
  - It can read 0 while the extents are still set only between `copy_out`'s add
    (`798`) and its `release_run` (`801`). There the switch to an unnamed wait
    is harmless.
- How the wait record behaves:
  - The switch happens at most once.
  - `am_wait_end` followed by `am_wait_begin` reads, to the deadlock detector,
    as a wait that ended, which is conservative.
  - The no-progress timer restarts only after the named wait has seen its own
    pieces land.
- The one-piece path waits for each piece and releases it before issuing the
  next, so it never holds the zone while it waits for room. Naming no node
  there is right.
- The new tests (*measured*):
  - With the parent's `transport-internode.c` swapped in, both `zone-held` tests
    failed 3 of 3, with "no progress toward node 1 (PE 1)" (`logs/zone-old-*`).
  - With `7d1d868` they passed: debug 3 of 3; under ThreadSanitizer, 4 of 4
    alone and in all five full runs.
  - `pieces-20` still names node 1.
- Why they are deterministic:
  - The 64,513-byte nonblocking get is one piece at the default 64 KiB chunk.
    The payload limit is the chunk less the headers, about 65.5 KB.
  - That piece takes all 64 extents.
  - At a 16 KiB chunk, its four pieces fill the 64 extents exactly.

**The locked-memory raise (*observed in source*, *measured*).**

- The library calls `setrlimit` in two places, open files and locked memory
  (`init.c:304`, `321`), and nowhere else.
- It handles `RLIM_INFINITY`.
- The zero-copy refusal tests (`locked-memory.h`) lower the limit after
  `shmem_init`, in one session, so the raise does not defeat them.
- The test catches the raise's removal (R9F-7).
