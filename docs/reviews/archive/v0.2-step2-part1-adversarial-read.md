# Adversarial read: v0.2 step 2, Part 1 (`tree-shape`)

A fresh agent's read of `main...tree-shape`, run on 2026-10-06 against `eefb36f`
(the lead amended it to `b073e7a` while the read ran, a change to
`test-internode.c` alone), asked to find a PE that could end `shmem_init` with
another shape or other link numbers than its peers, or a chooser that returns a
fan-out above the ceiling or a window above the capacity. The read's report
follows as it was handed back; what was done with each finding is in
`docs/decisions/2026-10-06-tree-shape.md`, "The adversarial read".

**Verdict:** the rule holds. Every PE ends `shmem_init` with the same
`OSOE_COLLECTIVE_SHAPE` and the same link numbers, and the chooser never returns
a fan-out above the ceiling or a window above the capacity. One real defect needs
fixing before the merge (finding 1).

## Findings

**1. The measurement kills a job whose node 1 has fewer threads than node 0.**
- Where: `shmem/src/link-measure.c:76-87` (`child_scratch`). Fix before merge;
  confidence high.
- Cause: the stream window is sized from the root's own `OSOE_MAX_THREADS`:
  `min((root threads + 1) × lane_bytes, 512 KiB)`. But `OSOE_MAX_THREADS` is
  only checked among a node's PEs, not between nodes - the README row,
  `internal-region.h:121` ("needs no agreement") and the rendezvous's
  `struct agreement` all confirm it (observed in source). So node 1 can
  legitimately have less lane space than the root assumes, and the 512 KiB
  stream runs past the end of its internal region.
- What happens: node 1's agent hits the bounds check in `progress-host.c:66-77`
  and ends the job at start-up, the message blaming the wrong settings
  (measured, osoe VM): "a peer addressed 16384 bytes at offset 3801088 of PE 1's
  internal region, which is 3805184 bytes; the nodes disagree about
  OSOE_COLLECTIVE_FANOUT, OSOE_COLLECTIVE_PIPELINE, OSOE_SMALL_COLLECTIVE_BYTES or
  OSOE_MAX_TEAMS ... waiting in shmem_init".
- Reproduction (measured):

  | Run | Result |
  |---|---|
  | `osoe-launch -n 2 -m 0,1 -e 1:OSOE_MAX_THREADS=1 -- shmem_test_barrier`, fan-out 4, pipeline 2 | status 1 |
  | the same with `OSOE_COLLECTIVE_SHAPE=fixed` | status 0 |
  | the smaller value on rank 0 instead of rank 1 | status 0 |
  | `OSOE_COLLECTIVE_FANOUT=2 OSOE_COLLECTIVE_PIPELINE=1`, node 1 at `OSOE_MAX_THREADS=4` | status 1 |
  | `OSOE_MAX_THREADS=1` on every node | status 0 |

  This configuration worked at the 0.1.0 tag.
- Fix: size the window for the fewest lanes any node can have - two
  (`OSOE_MAX_THREADS` is at least 1, plus the agent's lane): either
  `min(2 × lane_bytes rounded down to whole pieces, 512 KiB)` or stream within
  one lane.

**2. test-internode read its start-up baseline from the wrong PE** - already
fixed in `b073e7a`. At `eefb36f`, `counter()` was called before `local_id` was
set, so every non-lead PE read local id 0's counter blocks. Measured: the debug
preset passed 772 of 778, all six failures this test
(`shmem.internode.{0-0-0-1-2-2,0-1-2-0-1-0}`, their force-remote variants,
`slurm.internode.0-1-2-0-1-0`, `heap-shift.internode.0-1-2-0-1-0`); a remote
partner's `deferred > 0` check also passed only through unsigned underflow. The
same fix in the read's VM copy gave 15 of 15.

**3. An open stop-and-ask: the message cost varies run to run.** The record's "A
fourth stop-and-ask": the message cost ranges from 0 to 21 µs between starts,
more than the brief's factor of two. The brief says stop and ask; the record
says it was put to the author "and not waited on", and
`docs/decisions/2026-10-06.md` has no answer. Merging ships option (a) without
the author's decision (observed in source). A process question; the decision is
the lead's.

**4. osoe-stat can show a mixed link triple** (`tools/stat/stat.c:371-373`;
minor). `shape_text` reads the hop, then the message cost, then the bandwidth,
and takes the bandwidth being non-zero to mean "measured"; a read overlapping the
lead's three stores can print a hop of 0 beside a real bandwidth. Read the
bandwidth first: the release stores then make the other two visible.

**5. The measurement's traffic shows as the application's in node 0's lead's
counters** (minor: document it, or don't count it). A 2-node
`shmem_test_sleeper` after one barrier, read by `osoe-stat -c`:

| Counter on node 0's lead | shape `link` | shape `fixed` |
|---|---|---|
| `transport.put.calls` | 138 | 0 |
| `transport.put.bytes` | 1,966,248 | 0 |
| `transport.wait.calls` | 23 | 1 |
| `am.wakes_deferred` | 2 (on every lead) | 0 |

The record says the AND keeps "the world team's epochs ... the application's
own", which holds for epochs, not for these transport counters.

**6. The measurement allocates up to 512 KiB on node 1's lead** (minor). The
README's `OSOE_MAX_THREADS` row says lane space "a thread that does neither never
touches"; the stream now writes up to 512 KiB of node 1's lead's lanes at every
start, so those `/dev/shm` pages are allocated whether or not the program runs a
large collective.

**7. Start-up cost grows as the link slows** (minor; after the merge; computed
from source). Every start streams a fixed 1.875 MiB (3 × (128 + 512) KiB) plus
about 22-52 waited round trips: about 27 ms on the Pi, about 170 ms at
100 Mbit/s, where the brief expected under 100 ms, about 1.7 s at 10 Mbit/s.
Part 1 pays it on every multi-node `link` job although nothing reads the numbers
yet.

**8. A noisy bandwidth reading falls back to the most extreme value**
(`link-measure.c:190-192`; minor, a Part 2 risk). When the long stream is no
slower than the short, the bandwidth is set to the maximum, 10 TB/s. With 34
logical nodes in the VM all 34 PEs agreed on exactly 10000000000000 bytes a
second (measured). Under Part 2's chooser bytes would cost nothing, so the star
would win at every size - the shape F2 showed slowest for large messages. A
conservative fallback or a retry would be safer.

**9. Two notes for Part 2** (minor). The message cost is taken as 0 on a 2-node
job because "every fan-out is the same tree there": true of trees over nodes,
not of the brief's Part 2 scans, whose tree is over members. And `osoe.job.link`
is written after the agent starts; nothing in the agent reads it today, and an
agent-side reader added later would race (observed in source).

**10. Stale or inaccurate text** (minor; observed in source):
- `node.h:763` says "The finalize team never uses `copied`"; the init AND now
  uses it.
- `link-measure.c:22-25` says "Each number is a median" - the message cost is a
  trimmed mean - and "25 ms (24.8-25.3)", where the record and README say 27 ms.
- `link-measure.c:219` says "The root of every team's tree over the job's nodes
  is node 0": true for reductions; a broadcast's tree is rooted at its root's
  node (`find_lead_tree`).
- `node.h:809` says "once every PE holds it"; it should be every PE of that
  node.
- `tools/stat/segment.h:326`: the layout-32 line omits `node.link.measured_*`.
- `docs/decisions/README.md:95` still says "Until the link is measured and the
  chooser reaches..."; the link is measured now.
- The README's "How a job starts" (line 1494) promises that a start-up wait
  reports what it waits for after 30 s; the new AND inside `shmem_init` is
  silent.
- The record's Verification cites `8553de7` and `72f27a6`, which no branch
  contains (they predate the rebase), and no preset run is recorded after the
  measurement commit.
- `osoe_shape_cost` does not check its inputs: a fan-out below 2, a window of 0
  or a piece size of 0 divides by zero; no setting in its allowed range can
  produce them.

## Checked and found sound

- **Same path on every PE.** Every PE calls `osoe_link_establish`
  unconditionally, and its branch conditions (node count, shape, link settings)
  are agreed three ways: read by each PE, compared in `open_control`, and
  compared at the rendezvous. The up header is exactly 80 bytes with no padding,
  matching its assert.
- **Same numbers everywhere** (measured): 0,0,1,1 and 0,1,2 (fan-out 2), three
  sessions each; 34 nodes at fan-out 32 (34 of 34 identical); 30 runs of
  `link.sh` on 0,1,2, and 20 under `OSOE_TEST_PERTURB=1`: no failures.
- **Re-init**: each session measures again; numbers differ between sessions and
  agree within each.
- **The finalize team's AND** uses internal-region counters and number 2's split
  words, which nothing else uses; the finalize barrier runs on the agent's tree,
  and its epoch continues (1, then 2) the same on every PE.
- **The measurement's writes** are zeros, the slots' cleared state; slots are
  read only after their counters move, and all puts complete before the root
  contributes to the AND.
- **The deadlock detector** cannot fire during the measurement: node 0 is never
  quiet, its puts unacknowledged.
- **The root dying mid-start**: killing the root's lead at eight different
  moments ended the job within 0.25 s each time (measured).
- **The chooser**: 80,000 random inputs across every setting's full range,
  built with clang's address, undefined-behaviour, unsigned-overflow and
  implicit-conversion sanitizers (measured): the C and `shape_timing.py` agree
  exactly; the fan-out is always between 2 and the ceiling and the window always
  1 or the capacity; the only overflow reported is the harmless
  `while (exponent--)` wrap. The closed form matches a walk of every node on 808
  cases at depths 3 to 6, up to 6,000 nodes (the model's own walk check stops at
  120-300). `model.shape_timing`'s check and grid-compare both pass.
- **The single-node build**: 393 of 393, no warnings.
