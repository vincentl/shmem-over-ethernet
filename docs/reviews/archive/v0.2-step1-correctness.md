## Verdict

**Correct as built. In this question's area the single-node build can be
offered to desktop users as the README describes it, and the full build is
still what 0.1.0 was; nothing must change first.** What convinced me:

- **One tree, two builds, no drift holds at the level of machine code.**
  Compiled on one compiler, the 59 library objects the two builds share are
  instruction-for-instruction identical but one: `init.o`, where one immediate
  differs, 5,765 against 5,785 - the length of `SHMEM_INFO`'s text, which in the
  single-node build carries the 20 bytes " (single-node build)" (*measured*).
  Their compile commands differ only by the version macro. So a job of one node
  runs the same code in both builds but for the futex file, the internode
  backend's four `internode.h` calls - where AM's `osoe_internode_init` also
  allocates an arrivals array the refusing backend does not - and the version
  text (*observed in source*).
- **The classic futex is futex2's semantics as the library uses them**, but
  for the thread's timer slack (K4): the same 32-bit compare, the same private
  flag (128 in both), the same absolute `CLOCK_MONOTONIC` deadline taken through
  the same time-namespace conversion, a bitset that must be nonzero and matches
  alike, the same futex hash and queue under contention, and the same keys
  across processes (*recalled*: the kernel's futex code). The two semantic
  differences the step's adversarial read found - a timed classic wait ends with
  `EINTR` under every handler, and a classic wake of 0 wakes one - are fixed in
  both files, and every breakage of the classic file I made fails a test
  (*measured*, Mutations).
- **The refusing backend's unreachable entry points are unreachable**: every
  call site guards on a fact a job of one node never has (*observed in
  source*), the guard is loud when it is broken (*measured*), and a job of two
  logical nodes is refused by name on every PE with nothing left in `/dev/shm`.
- **The suites hold under load on Rocky with GCC 11**: the single-node build's
  debug suite at 8 and 16 spinning threads on four cores, release, AddressSanitizer
  and ThreadSanitizer, all whole; the pacer's threaded exercise under GCC 11's
  ThreadSanitizer, which the suite does not run there, clean for two minutes;
  64 PEs on four cores; a one-node job stopped for 15 seconds with the deadlock
  detector at one second, finishing clean (*measured*, Runs).
- **The full build is 0.1.0's library** but for fourteen objects, each
  accounted for by the step's records: the split, two files of settings moved
  whole, the io_uring check moved under the seam, the futex2 file's three fixes,
  a fifth heap base, the `pidfd` notice (*measured*: the tag and `7053819`
  compiled side by side). Its debug suite passes whole under eight spinners,
  729 of 729, and round six's fixes in this area hold (*measured*).

What I found is about coverage and documentation, not code. Ranked:

- **K1 (after release)**: the `internode` label is right, but the single-node
  build loses one-node coverage the record does not list - fifteen of
  `shmem_global_exit`'s modes, four of the deadlock detector's, the sibling
  heaps' exclusion from a core, a destroyed team's refusal, and the pacer's
  threaded exercise under ThreadSanitizer - each of which I ran on one node in
  the single-node build, all passing.
- **K2 (after release)**: the one-node quiet's serializing fence - the whole of
  `shmem_quiet` in the single-node build - can be deleted with every test
  passing; on the default aarch64 build even a litmus aimed at it cannot see
  the deletion, because the counters `shmem_quiet` bumps compile to `ldar`/`stlr`,
  which order a store before a later load on aarch64. Built for Armv8.3
  (`ldapr`), the litmus sees 109 forbidden outcomes in 500,000 rounds without the
  fence and none with it. On x86-64, where most desktops are, the counters are
  plain moves and the fence is all there is.
- **K3 to K6 (minor)**: a wake lost to a wrong scope on the one-node agent's
  word passes the whole suite and makes a short job 14 times slower; the classic
  wait honours the thread's timer slack where futex2's does not, and nothing
  but the record's adversarial-read paragraph says so; liveness without
  `pidfd_open` - every kernel from the single-node build's floor, 4.17, to 5.2 -
  has no test, though it works; and two sentences of the records.

## Findings, ranked

### K1. The single-node build loses one-node coverage beyond what its record lists (after release; high confidence; *measured*)

- **Location**: `shmem/tests/CMakeLists.txt` - `shmem_global_exit`'s modes in
  `if(OSOE_INTERNODE)` at `:2955-3027` and the `KILLS` cases at `:3051-3077`,
  every one on `0,0,1,1`; the deadlock cases at `:2731-2792` (`sleeping`,
  `reinit`, `mismatch`, `off` on two nodes only); `osoe_tier2_map_test(core-exclusion 0,0,1,1)`

  at `:3147-3157`. `tools/pacer/CMakeLists.txt:561-564` (the threads exercise

  job of more than one node is `internode` and is not registered in the

  labelled `internode` is lost coverage" (this round's brief).

  `0,0,0,0` beside `0,1`.

### K2. The one-node quiet's fence - all of quiet in the single-node build - has no test that fails without it (after release; high confidence; *measured*)

- **Location**: `shmem/src/transport-am.c:407-419` (`osoe_transport_wait` in a
  job of one node: a counter, `osoe_serializing_fence()`, a counter);
  `base/order.h:16-21` ("a load after it must not be satisfied before a store
  before it is visible (W->R) ... An mfence on x86-64, a dmb ish on aarch64");
  `base/counters.h:37-41` (`osoe_counter_add`: an acquire load and a release
  store); `shmem/src/quiet.c:45-50`. The same fence was the one-node quiet at
  the tag (`wait_body`), so the gap is older than this step; what is new is a
  build whose every job takes it.
- **Breakage**: the fence deleted from `osoe_transport_wait`'s one-node path
  (`wait_no_fence` in `mutate.py`): the single-node debug suite, **347 of 347
  pass**.
- **Why nothing sees it on aarch64**: between the program's store and its later
  load `shmem_quiet` bumps three counters, each an `ldar` and an `stlr` with
  GCC's default `-march`. A store-release followed by a load-acquire is ordered
  on aarch64 (RCsc), and a plain store before the `stlr` and a plain load after
  the `ldar` are ordered by release and acquire, so the counters alone keep the
  store before the load - in the hardware, not in C11 (*recalled*, the Arm
  memory model; *observed in source*). My store-buffering litmus through the API
  (`quiet-litmus.c`: PE 0 `X = 1; shmem_quiet(); r0 = Y`, PE 1
  `Y = 1; shmem_quiet(); r1 = X`, both on PE 0's heap, rounds started by a spin
  barrier so that the two race within a line transfer of each other) finds no
  forbidden `(0, 0)` in 500,000 rounds on Rocky's GCC 11 build either with the
  fence or without it, in either mode (stores and loads through `shmem_ptr`, or
  `shmem_int_p`/`_g`).
- **Seen where the counters do not mask it**: the same library built with
  `-march=armv8.3-a` on Debian's GCC 14, whose acquire loads are `ldapr` (89 in
  `libosoe.so`), which an earlier `stlr` does not order: the litmus in `shmem_ptr`
  mode finds **109 forbidden outcomes in 500,000 rounds** without the fence, and
  **0** with it (and 0 in both in `put` mode). On x86-64 an acquire load and a
  release store are plain moves, so nothing but the fence's `mfence` stands
  between a store in the store buffer and a later load (*observed in source*,
  `base/order.h`; *recalled*, x86-TSO), and no x86-64 kernel has run osoe.
- **Why it matters**: the project's standard is that a test asserting an
  ordering fails when the mechanism under it is removed, and this ordering is
  the single-node build's quiet, whole, on the platform most desktop users have.
  The code is right; a refactor that loses the fence would pass every test on
  the project's aarch64 machines, and the counters' masking would hide it there
  for good.
- **Fix**: the litmus as a tier-2 test on one node, two PEs, built where
  `ldapr` is emitted (`-march=armv8.3-a` with GCC 14, as here) and on x86-64
  when a machine exists; `wait_no_fence` in the records' mutation lists,
  and a line in `transport-am.c` that on aarch64 the counters hide the fence's
  absence.

### K3. A wake lost to a wrong scope on the one-node agent's word passes the whole suite (minor; high confidence; *measured*)

- **Location**: `shmem/src/transport-am.c:202-208` (the one-node agent waits on
  its wake word, `OSOE_FUTEX_SHARED`); its wakers `agent.c:336` (stop),
  `node.c:1665` (the node's abort), from the PE's own thread or another process.
- **Breakage**: the agent's wait made `OSOE_FUTEX_PRIVATE`
  (`agent_wait_private`), so no `OSOE_FUTEX_SHARED` wake reaches it: **347 of
  347 pass**, and twenty 4-PE runs of `shmem_test_init` take **319 ms a job
  against 22 ms** - every stop and abort waits out the agent's 100 ms sweep. The
  suite's other scope breakage, the classic file giving every wait the private
  flag (`scope_private`), fails 102 tests by timeout, so the suite sees a wrong
  scope where many waits share it, not at one call site.
- **Why it matters**: the sweep is the designed backstop (§3.10), so this is
  latency, not a hang - and the same in both builds. But it is the one wake on
  the single-node build's progress threads, and its loss is invisible to the
  suite and to `osoe-stat`.
- **Fix**: a bound on a trivial one-node job's finalize, or a test that a short
  one-node job's agents end no wait at its deadline (`osoe_futex_timeouts`).

### K4. The classic wait honours the thread's timer slack; futex2's does not, and only the record's adversarial-read paragraph says so (minor; high confidence; *measured*)

- **Location**: `base/futex-classic.c:61-65`; `base/futex.h:37-46`; the README's
  "only the system call its waits sleep in differs" (`README.md:147-149`); the
  record's "but for findings 1 and 2 and the classic call's timer slack".
- **Evidence**: the kernel arms a classic `FUTEX_WAIT_BITSET`'s timer with the
  thread's `timer_slack_ns` and futex2's `futex_wait` with none (*recalled*).
  `slack.c` on `osoe-load` (6.12, both calls), ten 100 ms waits each, under
  `PR_SET_TIMERSLACK` of 50 µs, 5 ms and 50 ms: classic 8.4, 13.4 and 41.3 ms
  late on average (worst 10, 15 and 60 ms); futex2 7.1, 6.5 and 6.4 ms
  (worst about 10) whatever the slack - the VM's timer granularity.
- **Why it matters**: at the default 50 µs, nothing. A desktop session that
  raises the slack for a power saving (a `prctl`, a service's
  `TimerSlackNSec=`) stretches every sweep of the single-node build by it - the
  liveness check, `OSOE_NO_PROGRESS_TIMEOUT`, the deadlock detector's rounds -
  and not the full build's. No correctness rests on a deadline's precision (*observed in
  source*: every library deadline is the 100 ms sweep or seconds).
- **Fix**: a sentence in `futex-classic.c` and `futex.h`; the README's sentence
  is true enough as it stands.

### K5. Liveness without `pidfd_open` - the single-node build's kernels from 4.17 to 5.2 - has no test (minor; medium-high confidence; *measured*)

- **Location**: `shmem/src/liveness.c:22-28` and `:114-133` (`open_watch` falls
  back to `kill(pid, 0)`), `:180-186` (the same in `osoe_liveness_outlast`);
  the README's single-node requirement "Linux 4.17 or newer" (`README.md:202-206`).
- **Evidence**: no test reaches the fallback: the full build needs 6.7, and
  nothing denies `pidfd_open` (*observed in source*). Emulated with a seccomp
  filter returning `ENOSYS` for `pidfd_open` around `osoe-launch`
  (`deny-pidfd.c`): the four one-node `dead-pe` cases and two `death-in-wait`
  cases pass, the death named by the lead, "watching local PEs by pid instead"
  printed once, by the lead, as `liveness.c` now intends.
- **Why it matters**: Debian 10's 4.19, and any other kernel between the stated
  floor and 5.3, runs this path on every job; it works, but a regression there
  would not show. A filter is not the old kernel, which the README rightly says
  the build has not met.
- **Fix**: `deny-pidfd`, in the form of `deny-futex.c`, around the one-node
  `dead-pe` cases, in both builds.

## What convinced me

**The rule, in machine code.** On `osoe-load`, the full and single-node debug
builds of `7053819`: every library object both compile (59, `base/` included)
disassembles identically but `init.o`, whose one differing instruction is the
`fwrite` length of `SHMEM_INFO`'s text (5,765 against 5,785 bytes); stripped of
`-DOSOE_VERSION_STRING`, the compile commands are the same (*measured*). What a
one-node job reaches outside those objects: `futex-classic.o` or
`futex-futex2.o`; `osoe_internode_backend_check`, which both backends answer
NULL for one node, AM without calling `osoe_ring_check`; and `internode.h`'s
four calls - the fan-out, the same constant in both
(`OSOE_INTERNODE_FANOUT_DEFAULT`), and init, fini and a number taken again,
which both hand to the generic phase, AM's init also allocating its
`consumed` array (`internode-am.c:63-70`) (*observed in source*). The option never
reaches the compiler - no `-D` carries it - and in the sources its name appears
in comments and the refusing backend's message only (*observed in source*).

**The seam's split.** The far half moved whole: the old `transport-am.c` from
`mark` to its end against `transport-internode.c`, with `c->internode->`
read as `c->`, differs only in the entry points' names and signatures, the
locality dispatch and counters that stayed in `transport-am.c`, the
`osoe_am.internode` tests that the call sites now make, and line wrapping
(*measured*, a normalized diff). The dispatch is the old one: a multi-node wait
on a shared context still takes `wait_shared`, a serial one `wait_body`, a
serial `wait_gets` `complete_gets`. The one-node answers in `transport-am.c`
are the old `progress-host.c` guards' one-node answers - a pass that moves
nothing, a shared-scope futex wait on the agent's word to the sweep, idle and
quiet with nothing applied, the same fatal for a deadlock message - read
against the tag's `progress-host.c:603-778`. The one counter-visible change, a
shared context's wait on one node, is the record's, and on one node no get is
ever in flight to close a counter pair on.

**The refusing backend.** Each entry point of `transport-single-node.c` but
its check is reached only through a guard a one-node job never passes:
`transport-am.c`'s `internode` (`node_count > 1`) at every agent call, start,
stop, fence and wait; `c->internode`, NULL on one node, at context close;
`osoe_routes_in_process`, true for every PE of a one-node job, at put, get and
rmw, after `osoe_check_pe` has refused an invalid PE (`symmetric.c:66-71`); the
`node_count == 1` return in `job.c:327-344` before `lead()`'s advertise and
rendezvous; and for `internode.h`'s data calls a team's `internode`, which is
`local_members < members` (`team.c:1020`) and so never true on one node
(*observed in source*). `OSOE_FORCE_REMOTE=1`, the one setting that changes
routing, is refused on one node by name in both builds ("needs a job of at
least two logical nodes") (*measured* in the single-node build, 13 programs; the same object code in the full build). With the refusal removed,
a job of two logical nodes reaches `osoe_internode_backend_advertise` and ends
naming it as a defect (*measured*): the guard is loud.

**The classic futex against futex2** (*recalled* for the kernel's code, which
both calls share below their entry points: `futex_wait_setup`, the queue and
hash, `futex_wake`'s bitset match, `futex_init_timeout`):

| | futex2 (`futex-futex2.c`) | classic (`futex-classic.c`) |
|---|---|---|
| word, compare | `FUTEX2_SIZE_U32`, 32-bit | 32-bit |
| private scope | `FUTEX2_PRIVATE` = 128 | `FUTEX_PRIVATE_FLAG` = 128: the same key, (mm, address); shared: (inode, offset) for `/dev/shm` |
| deadline | absolute, `CLOCK_MONOTONIC`, time namespace converted | the same, through the same `futex_init_timeout`; `FUTEX_CLOCK_REALTIME` never set |
| bitset | nonzero, shared bit wakes | the same (`epoch.c`'s 1 or 2) |
| a signal | `-ERESTARTSYS`: restarted under `SA_RESTART`, else `EINTR` | timed: restart block, `EINTR` under every handler |
