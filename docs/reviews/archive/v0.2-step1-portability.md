# v0.2 step 1, question 4: will it run anywhere else?

Review of `main` at `7053819`, run 2026-10-06 against
`docs/reviews/adversarial-review-prompt.md`, at the merge point of v0.2's step 1,
the single-node build (`docs/decisions/2026-10-05-v0.2.md` items 2 to 5, the
brief `docs/prompts/v0.2-step1-single-node-prompt.md`, and the records
`docs/decisions/2026-10-06-single-node-seam.md` and
`docs/decisions/2026-10-06-single-node-build.md`). The previous round's answer
to this question is `phase1-step7-slice4-portability.md`, at `375973a`, and its
fixes are `docs/decisions/2026-10-05-step-e-review-fixes.md`; 0.1.0 is the tag
on `53b8f0f`. Labels: *documented* (a source says so: the tree, a package's own
version string, a vendor's text), *observed in source*, *measured* (run here, on
this tree), *recalled* (from memory, not checked; no web access was used).

## Machine and method

The review tree was copied out of its worktree into each VM's `/tmp` and built
there, every build and run under `/tmp/osoe-vm.lock`, every command in the
foreground (one, a configure of seconds, passed its call's limit while waiting
for the lock and finished in the background); each copy was removed when done.

- **`osoe-rocky`**: Rocky Linux 9.8, kernel `5.14.0-687.10.1.el9_8.0.1.aarch64`,
  GCC 11.5.0, CMake 3.31.8, glibc 2.34, Python 3.9.25, SELinux enforcing, the
  session `unconfined_t`; `pkgconf` installed, no liburing headers (*measured*).
  There: the README's desktop section as printed, the release suite, CMake 3.25.1
  and 3.22.1 (Kitware's own aarch64 binaries, Debian 12's and Ubuntu 22.04's
  versions), four mechanisms broken on purpose, and - in rootless containers
  (`nerdctl`, containerd 2.3.3) on Rocky's 5.14 kernel - the userlands of Debian
  12, Ubuntu 22.04, 24.04 and 26.04, Fedora 44 and Alpine 3.24, each with its own
  compiler, CMake, glibc and kernel headers. No package was installed in the VM
  itself: Rocky's `clang` would have brought `gcc-c++` with it, and with it the
  headers' C++ test, changing the Rocky suite from 347 tests to 349 under the
  other investigators. The images were removed afterwards.
- **`osoe-x86`**: Debian 13, kernel `6.12.111+deb13-cloud-arm64`, Rosetta
  registered for x86-64 programs. Started for this review and stopped after it.
  There: the single-node build for x86-64 with `x86_64-linux-gnu-gcc` 14.2 and
  with Clang 19.1.7 (`--target=x86_64-linux-gnu`), run under Rosetta with no
  shim; the full build for x86-64 (liburing 2.9 amd64), run under Rosetta without
  and with round three's futex2 shim; the single-node build with Clang natively.
  Clang was installed for these runs and its 24 packages removed after.
  Rosetta is an x86-64 user space on an aarch64 kernel, with x86's memory order
  on Apple cores; it is not an x86-64 kernel.

The Pi cluster was not used. Scripts are in this session's scratchpad
(`.../scratchpad/q4/`, `r-*.sh` for `osoe-rocky` and `x-*.sh` for `osoe-x86`),
run with `limactl shell <vm> -- bash -s < script`.

## Verdict

**The single-node build can be offered to desktop users as the README
describes it.** Its commands, run as printed, build, install and run on Rocky
Linux 9 and in the userlands of every distribution the README names for it,
with GCC 11 to 16 and with Clang 19, with no liburing, no pkg-config and CMake
from 3.25.1 up; a job of more than one node is refused by name with nothing left
in `/dev/shm`; and the question no round could ask before has its answer: **an
x86-64 build's one-node job runs under Rosetta**, with no shim - the classic
futex is forwarded where the futex2 calls are refused - its suite passing
everything the emulator can run and six minutes of the stress tester clean.
**The full build is still what 0.1.0 was**: the same requirements, the same 3,595
exports, the same wire and checks; what changed in it is listed below, and none
of it is a regression in this question's area. **Nothing blocks and nothing must
change first.** Four cheap changes are worth making before the build is
announced: Q1's two lines, for a test that fails on GCC 16, and three sentences
of the README (Q3, Q4, Q6); the rest can follow.

What convinced me:

- **Rocky Linux 9, as printed** (*measured*): the desktop section's commands
  configure, build and install in 18 s with no warning; the installed `oshcc` and
  `osoe-launch` say `0.1.0 (single-node build)`; the ring's eight lines come back
  with status 0 (at `SHMEM_SYMMETRIC_SIZE=64m`: this VM's 1.8 GiB `/dev/shm` is
  short of the eight PEs' 2.1 GiB, which is refused by name - Q6); two logical
  nodes are refused on both PEs, status 1, nothing left; `libosoe` needs libc
  alone; `ctest --preset release -j4` passes 347 of 347 in 30 s, under SELinux
  enforcing.
- **Every userland the README names, and the newest beside them** (*measured*,
  on Rocky's 5.14 kernel, which is older than any of theirs): Debian 12 (GCC 12.2,
  CMake 3.25.1, glibc 2.36), Ubuntu 24.04 (GCC 13.3, CMake 3.28.3, glibc 2.39),
  Ubuntu 26.04 (GCC 15.2, CMake 4.2.3, glibc 2.43) - no warning, the ring at
  eight PEs, 349 of 349 each; Ubuntu 22.04 the same with `pip install cmake`
  (CMake 4.4.4); Fedora 44's GCC 16.2 two warnings in test programs and 346 of 347
  (Q1); even Alpine's musl, which nobody promised, builds clean and runs, 345 of
  349 (below).
- **The CMake floor holds exactly** (*measured*): CMake 3.25.1 configures, builds,
  tests (347 of 347) and runs the README's `cmake --workflow --preset release`;
  3.22.1 refuses.
- **Clang** (*measured*): Clang 19 builds the single-node build with no warning,
  natively (349 of 349) and for x86-64.
- **x86-64 under Rosetta** (*measured*): the x86-64 single-node build passes 343 of
  its 349 tests, the six failures the emulator's (seccomp refused) or the cross
  build's; its PEs are Rosetta's (`/proc/<pid>/exe`, `uname -m` saying `x86_64`)
  and sleep in the kernel's `futex_wait_queue`; `osoe-pacer --quick`, five
  minutes of `mix` and `threads` and `teams` at 8 and 16 PEs on four cores all end
  `failures=0` - x86-64 code generation and x86's memory order on the one-node
  protocols, as far as the suite and the stress tester reach them.
- **The single-node build's own mechanisms have tests with teeth** (*measured*):
  with the refusal removed, with the futex check's shared scope removed, with the
  signal restart removed and with a wake of none waking one, the test standing on
  each fails, and only that one.
- **Nothing of the network is left in it** (*measured*): the x86-64 single-node
  library needs only libc and the loader, imports no socket, `getrandom` or
  io_uring call, and exports exactly the full build's 3,595 names (1,794 strong
  `pshmem_`, 1,787 weak `shmem_`, no `osoe_`).

Ranked:

## New findings

### Q1. `shmem.strict-c11` fails on GCC 16, in both builds (after release; high)

- **Where**: `shmem/tests/test-global-exit.c:196` and `shmem/tests/test-dead-pe.c:65`,
  `volatile unsigned long spins = 0; while (...) spins++;`, unchanged since
  2026-09-26; `cmake/CheckStrictC11.cmake:61`, which fails the test on any
  `warning:` in a nested build that compiles every test program
  (`BUILD_TESTING=ON`).
- **Scenario**: a user on Fedora 44 - "current Fedora", which the README names
  for the full build - or on any distribution that moves to GCC 16 follows the
  desktop section's advice and runs `ctest --preset release -j4`: one test fails,
  in either build.
- **Evidence** (*measured*, `fedora:latest` = Fedora 44, GCC 16.2.1, CMake 4.3.0,
  glibc 2.43): both builds compile with exactly these two warnings,
  `variable 'spins' set but not used [-Wunused-but-set-variable=]`, and nothing
  in the library or the tools; the single-node suite passes 346 of 347, the one
  failure `shmem.strict-c11`; `shmem.static-link`, which builds the library
  alone, passes. GCC 15.2 (Ubuntu 26.04, Alpine 3.24) gives no warning.
- **Fix**: read each counter once after its loop (a `(void)spins;` reads a
  `volatile`); and consider holding the strict check's "no warning" to the
  library and the tools, where the project controls what a new compiler sees,
  rather than to every test program.

### Q2. The nested-build checks use the default compiler, not the configured one (minor; high)

- **Where**: `cmake/CheckStrictC11.cmake:39-44` and `cmake/CheckStaticLink.cmake:35-40`
  configure with neither `CMAKE_C_COMPILER` nor `CMAKE_C_COMPILER_TARGET`;
  `shmem/tests/CMakeLists.txt:63-85` passes neither.
- **Scenario**: a user configures with `CC=clang` (or a Rocky `gcc-toolset`); the
  two tests pass having compiled the tree with `/usr/bin/cc`; where `cc` is not
  installed they would fail for a reason unrelated to the build (by reading).
- **Evidence** (*measured*): in a Clang 19 build, both nested caches read
  `CMAKE_C_COMPILER:FILEPATH=/usr/bin/cc`. In a Clang build for x86-64,
  `shmem.static-link` passed after building an aarch64 archive with the host's
  `cc` and linking it with the configured Clang, which `oshcc` and this check
  run without the target - so it checked nothing of the build it belongs to; in
  the GCC cross build it failed instead, "Relocations in generic ELF (EM: 183)".
- **Fix**: forward `-DCMAKE_C_COMPILER=${CMAKE_C_COMPILER}` (and the target and
  the C flags where set) into both nested configures, as `SINGLE_NODE` already is.

### Q3. The README's x86-64 passages describe the tagged tree, and leave out what the single-node build changed (minor; high)

- **Where**: README 210-214 ("An x86-64 build of this tree passed every test an
  emulator on an aarch64 kernel can run, with a shim standing in for the futex2
  calls") and 958-974 ("On x86-64 this tree built without warnings and passed
  every test that can run under Rosetta ... 369 of the suite's 718", and "The
  single-node build ... on no x86-64 machine").
- **Evidence** (*measured*, this tree): the runs those sentences cite were of the
  tagged tree (`docs/release-checklist.md` 89-98); this tree registers 729. Here:
  the x86-64 full build compiles with no warning, and with the shim copied into the
  VM its 345 one-node tests pass but 4 - `shmem.static-link` (the cross build),
  `shmem.no-io-uring.one-node` (seccomp refused), `tools.pacer.installed.one-node`
  (`ldd` of another architecture) and `env.probe` (io_uring refused) - so the
  passages' substance holds; but the single-node build, which needs no shim at
  all, is the news: 343 of 349 under Rosetta with GCC, every failure the
  emulator's or the cross build's (below). The same class as round six's Q1:
  a sentence that says "this tree" of a run is false at the next merge.
- **Fix**: say "the tagged tree" where that is what ran, or the numbers above;
  and one sentence for the single-node build: an x86-64 build runs one-node jobs
  under Rosetta, the classic futex forwarded where the futex2 calls are refused.

### Q4. Ubuntu 22.04 is turned away for its CMake alone (minor; high)

- **Where**: README 225-227: "9.0 to 9.2 shipped 3.20, where `pip install cmake`
  gives a newer one - ... Ubuntu 22.04's CMake, 3.22, is older than the floor."
- **Evidence** (*measured*, `ubuntu:22.04`, GCC 11.4, glibc 2.35, kernel headers
  5.15): the stock CMake 3.22.1 answers the desktop section's first command with
  `CMake Error: Could not read presets from ...: Unrecognized "version" field`,
  which does not say it is too old (configured without the preset, it does: "CMake
  3.25 or higher is required"); after `pip3 install cmake` (CMake 4.4.4) the
  section's commands build with no warning, the ring runs at eight PEs, and the
  suite passes 349 of 349. 22.04 is an LTS still in support, and the most likely
  Ubuntu on a developer's desk after 24.04 (*recalled*).
- **Fix**: give 22.04 the same clause as Rocky 9.0 to 9.2, and quote the error.

### Q5. Without pkg-config the default configure never reaches the message that names the single-node build (minor; high)

- **Where**: `CMakeLists.txt:69`, `find_package(PkgConfig REQUIRED)`, before the
  liburing message at 71-77 that names `-DOSOE_SINGLE_NODE=ON`.
- **Scenario**: on Debian 12 or Ubuntu 24.04 with the desktop section's packages,
  `build-essential cmake`, a user who runs the quick start's `cmake --preset
  release` - the default build - is told only that PkgConfig is missing;
  installing it, they are told liburing is, and only then of the option.
- **Evidence** (*measured*): in `debian:12` with those packages and nothing else,
  `cmake --preset release` stops at `FindPkgConfig.cmake` ("Could NOT find
  PkgConfig"), status 1; with the option it configures. On Rocky, whose image has
  `pkgconf`, the same command reaches osoe's message, and the option then
  reconfigures the same build directory cleanly.
- **Fix**: `find_package(PkgConfig)` without `REQUIRED`, and its absence folded
  into the liburing message, which names the option.

### Q6. The desktop example needs about 2.1 GiB of `/dev/shm` (minor; high)

- **Where**: README 136-145 ("here as eight PEs, which a machine of four cores
  runs too") and 154-156.
- **Evidence** (*measured*, `osoe-rocky`, 4 GiB): `~/osoe/bin/osoe-launch -n 8 --
  ./ring` is refused at once: "/dev/shm has 1822 MiB free, but this node's control
  segment and 8 heaps of 261 MiB ... need 2100 MiB: lower SHMEM_SYMMETRIC_SIZE or
  those, run fewer PEs per node, or enlarge /dev/shm ..."; with
  `SHMEM_SYMMETRIC_SIZE=64m` it prints its eight lines. A machine's `/dev/shm` is
  half its memory by default, so the example needs a machine of about 4.2 GB.
- **The library is right**: loud, at once, with the remedies; the section's next
  paragraph gives the figure a PE. The quick start got an explicit clause for the
  same case last round (round six Q3).
- **Fix**: "on a machine of 4 GB, `SHMEM_SYMMETRIC_SIZE=64m` in front".

### Q7. The directory READMEs predate the step (minor; high)

- **Where** (*observed in source*): `tools/README.md:12`, "`cmake --install`
  installs `oshcc`, `osoe-stat` and `osoe-pacer`" - `osoe-launch` is installed in
  both builds now (record, choice 3; the prefixes here hold it);
  `base/README.md:7` and `:16-17`, the io_uring check listed as base's, and
  "`futex.h`, the one place the library makes the futex2 system calls" - there
  are two files behind it now and only one makes futex2 calls;
  `shmem/README.md:17-19`, "the one backend below it, active messages over TCP
  and io_uring", with nothing of `internode-backend.h` or the refusing backend;
  `dev/README.md:3-8`, "`lima/` defines the virtual machine", `osoe.yaml` alone.
  None of the four changed in the step. The top-level README says each "says
  what the directory holds".
- **Fix**: a sentence each. (Shared with question 5.)

### Q8. 64-bit only, refused at compile time and still unstated (minor; high)

- **Where**: `shmem/src/team.c:578` (`_Static_assert(sizeof(uintptr_t) == 8, ...)`),
  `shmem/src/lock.c:83`; the README's requirement lists name no word size.
  Raised in round two (F15) and noted in rounds four and five; Raspberry Pi OS and Debian 12 still
  ship 32-bit userlands (*recalled*).
- **Fix**: "a 64-bit system" in both requirement lists.

### Q9. Minor notes

- **The pidfd line.** Rosetta answers `pidfd_open` with `ENOSYS`, and every job
  prints, from its lead, "cannot open a pidfd for local PE 1 (pid N): Function
  not implemented; watching local PEs by pid instead (§3.15)" (*measured*). A
  kernel before 5.3 does the same (`liveness.c:121-129`), and the README's floor
  for the single-node build, 4.17, admits such kernels without mentioning the
  line.
- **The full build's futex refusal under Rosetta** reads "osoe needs Linux 6.7 or
  later, for the futex2 calls (they fail with "Function not implemented"); this
  kernel is 6.12.111+deb13-cloud-arm64" (*measured*) - true of what failed,
  contradictory about why; a sandbox answering `ENOSYS` gets the same. This is the
  after-release list's Q6, unchanged; the single-node build's text names the
  sandbox.
- **The 4.17 floor is conservative**: the heap's map treats a kernel without
  `MAP_FIXED_NOREPLACE`, which takes the address as a hint, by unmapping a
  misplaced map and trying the next candidate (`node.c:452-460`); `pidfd_open`
  falls back. The rest of what the single-node build's sources call is older
  (*observed in source*: `futex`'s bitset calls, `gettid`, `mmap`, `pwrite64`,
  `sched_setattr` - 3.14, its result ignored - `SEEK_DATA`, `posix_fallocate`,
  `MADV_DONTDUMP`; the versions *recalled*). A floor stated high is no defect.
- **The models on a small desktop**: `model.abort` needs about 1.4 GiB, and the
  record saw it killed for memory at `-j4` in this 4 GiB VM (*documented*); the
  README's Building gives the models' time, not their memory.
- **Rocky's suite is 347**, not the README's 349: the headers' C++ test needs a
  C++ compiler, which `gcc make cmake` does not install. Harmless.
- **DT_RPATH on Rocky**: binutils there writes `-rpath` as `RPATH`, Debian's as
  `RUNPATH` (*measured* on Rocky), so `LD_LIBRARY_PATH` cannot point a program
  built on Rocky at another osoe install. Probably what a user wants.
- **A Rosetta stall, for whoever runs the x86-64 item next**: the full x86-64
  suite under the shim read from the host's mount stalled after 244 of 729 tests
  in 558 s, `rosettad` at 400% CPU and a load of 245 that did not fall in 30
  minutes; after a restart of the VM and with the shim copied into its tmpfs, the
  same tests ran at the usual speed. Copy the shim into the VM.

## x86-64 under Rosetta: does a one-node job of an x86-64 build run?

**Yes.** (*measured*, `osoe-x86`)

- **The single-node build**, GCC 14.2 for x86-64, `RelWithDebInfo`: 10 s, no
  warning; installed; the ring at eight PEs prints its lines and exits 0, every
  PE's start-up line `osoe 0.1.0 (single-node build), OpenSHMEM 1.6`.
- **They are Rosetta's processes**: during a job, each PE's `/proc/<pid>/exe` is
  `/mnt/lima-rosetta/rosetta`, its maps hold `ld-linux-x86-64.so.2` and
  `rosettad`'s translation caches, `uname -m` inside it says `x86_64`; the PE
  waiting in a barrier and both agents sleep in `futex_wait_queue`, in syscall 98,
  aarch64's `futex` - Rosetta forwards the classic call, where it answers the
  futex2 calls with `ENOSYS`.
- **The suite** (release preset, `-j4`): 343 of 349 in 39 s. The six: the four
  tests that wrap a job in a seccomp filter (`deny-futex: seccomp: Invalid
  argument` - Rosetta refuses `seccomp`), `shmem.static-link` (Q2's nested build,
  an aarch64 archive), and `tools.pacer.installed.one-node` (`ldd` of an x86-64
  program: "not a dynamic executable"). `base.futex` among the passes: the
  classic futex's whole contract - a wake across processes on a shared mapping,
  the private wait, the deadline, a stale value, the bitset, a wait under a 10 ms
  timer with and without `SA_RESTART`, a wake of none.
- **The stress tester**, the installed `osoe-pacer` under the installed
  `osoe-launch`, on four cores:

  | Run | Result |
  |---|---|
  | `--quick`, 8 PEs | `failures=0`, 7 s |
  | `mix`, 16 PEs, 64 MiB heaps, 180 s | `failures=0`: four teams out of step, every exercise on each (mailbox, atomics, rma, locks, collectives, waits) |
  | `threads`, 8 PEs, 90 s | 2,254,809,216 operations, `failures=0` |
  | `teams`, 8 PEs, 90 s | 2,946,334 collectives, 39,631 renewals, `failures=0` |

  Round six put x86's memory order on the network path through an aarch64 build;
  these put x86-64 code, x86's `char` and x86's order on the one-node paths the
  suite and the stress tester reach, in real x86-64 binaries.
- **The full build, for contrast**: built for x86-64 with no warning; a one-node
  job without the shim is refused by name at `shmem_init` (Q9's message); its probe
  fails the futex2 and io_uring checks with `ENOSYS`. With the shim, its one-node
  tests pass but the four the emulator or the cross build cannot run (Q3).
- **What it is not**: an x86-64 kernel, or Intel's and AMD's memory systems.
  Nothing in the single-node build depends on the kernel's architecture beyond
  the generic futex, mmap and tmpfs code; the risk left is small, and the first
  x86-64 desktop to install it is still its first native run.

see.** Its requirements are the tag's (`CMakeLists.txt:65-80`: liburing 2.6 by

- **The pidfd notice** is printed by the node's lead alone where `pidfd_open` is
  `ENOSYS`, once.
- **`osoe-launch` is installed**; tests were relabelled, and added - 729 against

## Kernels, sandboxes and the probe

- **What the single-node build asks of a kernel** (*observed in source*): the
  classic `FUTEX_WAIT_BITSET` and `FUTEX_WAKE_BITSET`, checked at init in both
  scopes and refused by name (`futex-classic.c:99-120`, `init.c:291-299`);
  everything else is old or has a fallback (Q9's notes).
- **What a sandbox can deny it, and what happens** (*measured* where marked):
  `futex` - refused by name with nothing made (the build's own
  `shmem.refuse.no-futex` and `.no-shared-futex`, and below); `pidfd_open` -
  watched by pid, one line (Rosetta); `sched_setattr` - ignored
  (`agent.c:88`); `seccomp` itself - only the tests that use it (Rosetta); io_uring
  and sockets - never called. A container's default profile denies nothing of it
  (Debian 12 under containerd's).
- **The probe** checks exactly the facilities that have no fallback: the classic
  calls, a wake across processes on a named object, and the reopening through
  `/proc` that `osoe-stat` stands on (`tools/probe/probe.c`,
  `probe-single-node.c`).

## Breaking the single-node build's mechanisms on purpose

(*measured*, `r-break.sh`, `r-break2.sh`, Rocky, GCC 11; each mutation built
whole, then the one test that stands on it run)

| Mechanism removed | Test | Result |
|---|---|---|
| the refusal: `osoe_internode_backend_check` answers NULL for any node count | `shmem.single-node.refuse-nodes` | **fails**: each PE makes its control segment, then ends at the rendezvous with "osoe_internode_backend_advertise was called in the single-node build ... a defect in the part of the transport every job uses" - loud still, but after objects were made |
| the futex check's shared scope | `shmem.refuse.no-shared-futex` | **fails**: "osoe: futex wake failed: Operation not permitted", and the control segment and both heaps left behind |
| the restart after a signal (`EINTR` returned as a wake, as before the step's fix) | `base.futex` | **fails**: `test-futex.c:102-103`, the wait under a 10 ms timer ends early |
| a wake of none returning at once | `base.futex` | **fails**: `test-futex.c:226`, a waiter woken by a wake of 0 |

So the refusal by name, the check that keeps a half-allowed sandbox from leaving
objects, and the two places where the classic call differs from futex2 each
have a test that sees their absence.

## Slurm and trust

- **Slurm**: the single-node build keeps the bootstrap's whole Slurm parsing and
  its captured and written fixtures (`shmem.bootstrap.*`, 12 tests), a one-node
  job through the Slurm path (`shmem.slurm.internode.0-0-0-0`), and the refusal of
  a program run outside a step; a job of several nodes is refused by name - here
  through `osoe-launch -m`, and under Slurm's names in the record's adversarial read
  (*documented*). No Slurm was at hand to run `srun -N1`.
- **Trust**: the single-node build opens no port and makes no socket, so the
  README's Trust paragraph does not apply to it. Locally, every object is created
  `O_CREAT | O_EXCL`, mode 0600, and an existing one is used or reclaimed only if
  its owner is this user (`shm-object.c:18-32`, `:34-89`): another user on a
  shared desktop can block a start by taking a job's name, which is refused by
  name, and can do nothing else (*observed in source*).

## What is sound, and what convinced me

- **The build is what the README says, wherever I could put it**: six userlands
  and two architectures, GCC 11 to 16 and Clang 19, CMake from the floor to 4.4, no
  liburing, no pkg-config, no Python needed; every library and tool compiled with
  no warning on every compiler but GCC 16, and there only two test programs.
- **The answer to the new question is yes, with evidence**: x86-64 one-node jobs
  run under Rosetta on the classic futex, the suite and the stress tester clean.
- **The single-node build has no network in it and no difference at its surface**:
  libc alone, no socket or io_uring import, the same exports; a job of several
  nodes refused by name before anything is made.
- **Its tests can fail**: four mechanisms removed, four tests failing, each on
  exactly what was removed.
- **The full build is unchanged where it matters**: requirements, exports, wire;
  its changes are fixes, and it compiles on what comes next.
- **The previous round's fixes hold** for the tree they were made on; one sentence
  has gone stale with the step, as sentences of this kind do (Q3).
