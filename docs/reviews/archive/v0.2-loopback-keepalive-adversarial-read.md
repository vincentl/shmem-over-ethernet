## Verdict

**Nothing fatal. The rule is right in every launch path a job can run in:**
- **osoe-launch:** its logical nodes, under `-s` too, have keepalive off.
- **Clusters and tier 3** keep it.
- **One machine named by its own address, not loopback:** keeps it, as before.
- **A cross-machine job never loses it.** An all-loopback table puts the job in one network
  namespace, for every job whose mesh forms.
- **Its two readers:**
  - the decision is made before both;
  - only a lead reads it;
  - nothing compares it, so it cannot refuse a job.
- **Nothing a test or a user relies on is lost:** a killed logical node's kernel closes its
  connections, and a stopped one's still answers.
- **Every test whose outcome turns on keepalive sets `OSOE_KEEPALIVE`, and keeps it.**
- **The evidence:** the lead's mutant is real, and the counts are right.

**Two findings are rated *should fix*:**
1. **The default between machines is pinned by no test.** That default is keepalive and the
   silent-peer check on, with `OSOE_KEEPALIVE` unset, on nodes with addresses of their own.
   - A mutant that turns keepalive off on every job passes the suite.
   - So does one that leaves the silent-peer check on over loopback.
2. **Sentences the change made false or left short:**
   - the README's limit on vanished nodes, and the row's Default column;
   - `test-wire-pair.c`'s comment;
   - §3.15 on the silent-peer check;
   - §8.1's list of what loopback does not test.

## Findings, ranked

### Should fix

**1. The default between machines is pinned by no test: a mutant that turns keepalive off for every
job with `OSOE_KEEPALIVE` unset passes the suite** (*observed in source*: every registration that
sets or reads keepalive; the mutants worked in `surviving-mutants.txt`, not run)

- **Where:**
  - `shmem/tests/CMakeLists.txt:1624-1645`: the two new tests, both tier 2, so both on 127.0.0.1
    and .2;

  - `shmem/tests/test-wire-pair.c:78-95`: a zeroed bootstrap handed to `osoe_wires_open`, below
    `progress-host.c`'s default.
- **What the suite can see.** These are the only tests that read keepalive on a socket, or whose
  outcome turns on it (a `git grep` of `KEEPALIVE`, `SO_KEEPALIVE` and `TCP_KEEP` over
  `shmem/tests`, `cmake` and `tools` finds no other):

  | `shmem.keepalive.set-on.0-1` | 127/8 | `60,10,6` | on, node 0's two wires |
  | `shmem.wire-pair`, `tier3.*.wire-pair` | 127/8, 10.99/16 | unset | `wire.c`'s default; never reaches `progress-host.c` |
  | `shmem.stopped-node.keepalive`, `shmem.stopped-bulk.0-0-1` | 127/8 | `1,1,3` | set |
  | `tier3.*.vanished-node.*`, `.vanished-node-inflight.0-1` | 10.99/16 | `1,1,3` | set |

  None runs a job whose nodes have addresses of their own with `OSOE_KEEPALIVE` unset, and looks at

- **So these mutants survive:**

- **Why it matters.** This change's risk is the default's other half: a cluster losing its
  vanished-node detection silently.

    nodes have links of their own, where keepalive is tested". That holds only at `1,1,3`.
  - `test-wire-pair.c:99-100` says only tier 3's cut link would notice keepalive gone. It would not
    notice the default gone.
  - Design §8.1 has a list, "What loopback does not test, each named so no test is mistaken for it"
    (`docs/design/shmem-ethernet-design.md:7370-7395`). It does not name keepalive and the
    silent-peer check at their defaults, which loopback no longer runs.
- **Fix:**
  - **Pin the default between machines.** A tier-3 test,
    `osoe_tier3_test(keepalive.default-on pi 0,1 shmem_test_keepalive ARGS on)`, with the pass
    expression `KEEPALIVE ON OK`. `sudo` passes no `OSOE_KEEPALIVE` into it, so it takes the default
    path. Or: the rule as a function of the address table and `keepalive_set`, unit-tested on
    loopback, mixed and 10.99 tables.
  - **Name it in §8.1's list.**
  - **For the silent-peer half,** note 5's `SHMEM_DEBUG` line would make it observable.

### Notes

**3. The test's socket filter admits more than TCP, and reads one side of the wires**
(*measured* on macOS, `unix-peer.txt`; Linux's `getpeername` on a connected Unix socket *recalled*
as the same)

- **The filter** (`test-keepalive.c:47-48`) is `SO_TYPE == SOCK_STREAM` and a `getpeername` that
  succeeds. A connected `AF_UNIX` stream socket passes it and reads `SO_KEEPALIVE` 0.
  - The job may inherit such a descriptor: systemd's journal stream as standard output, or a runner
    built on libuv, whose child pipes are socket pairs (*recalled*).
  - Then `set-on` fails, on keepalive "off" on a socket that is no wire, and `loopback-off` counts
    that socket toward its two.
  - ctest's own pipes are pipes: the lead's mutant run counted exactly the two wires.
  - The header says "every connected TCP socket". Requiring `peer.ss_family == AF_INET` makes it
    so.
- **One side only.** Only node 0, the side that connects, is read. Node 1's accepted sockets are
  not, and that is where an option a listener passed on to its accepted sockets would show. In
  `-m 0,1` both PEs are leads, so reading on both costs nothing.
- **The environment.** `loopback-off` assumes `OSOE_KEEPALIVE` is absent from ctest's environment.
  The correctness review ran tests with it set (`OSOE_KEEPALIVE=20,5,6`), and a suite run so fails
  this test. `cmake -E env --unset=OSOE_KEEPALIVE` pins it.

**4. The rule is narrower than "one machine", and the backlog is not loopback's alone**
(*observed in source*; the kernel paths *recalled*)

- **One machine, not on loopback.** A job on one machine whose host list names a non-loopback
  address keeps keepalive, and Q2-1's exposure with it. Examples:
  - `osoe-launch -H` with the host's own address;
  - several `slurmd` on one host;
  - containers on one host, each in a namespace of its own.
- **Why the exposure stays there.** Traffic to the host's own address goes through the loopback
  device too. veth delivers through the same per-CPU backlog (`netdev_max_backlog`), with GRO off
  as `tier3.sh` sets it.
- **Keeping keepalive is right** wherever a link can be cut. The README's `osoe-launch` paragraph
  and §3.15 would be exact if they said the probes are dropped by the receive backlog, which
  loopback shares with veth.

**5. Nothing reports the derived choice** (*observed in source*). `SHMEM_DEBUG` says each node's
unsent limit (`progress-host.c:493-514`), but not that keepalive and the silent-peer check were
turned off; `osoe-stat` does not either. A user cannot tell from the job which way it went. One line
under `SHMEM_DEBUG` would tell them, and would let a test pin finding 1's silent-peer half.

**6. What loopback loses** (*observed in source*; the kernel's behaviour *recalled*). One thing only:
the loopback failing under a running job - `lo` taken down, or a firewall reloaded to drop 127/8.
- Such a job now waits for the launcher's timeout or `OSOE_NO_PROGRESS_TIMEOUT`, where it ended in
  two minutes.
- No test or document relies on it.

**7. Q2-1's fix is argued, not measured.** No run repeats the review's reproduction with the
default. That would be `shmem.circulant.64` and `.70` at three helpers under six busy loops, or the
pair at no helpers.
- The review's mechanism runs set `OSOE_KEEPALIVE=20,5,6`, which now holds, so a rerun must leave
  it unset.
- One rerun would close it: no "stopped answering" lines, and `TCPAbortOnTimeout` unmoved.
- With keepalive and the silent-peer check off, `ETIMEDOUT` can now come only from `tcp_retries2`,
  some fifteen minutes.

**8. The record.**
- **Its undo** names the default and the `osoe-launch` sentence. It does not name:
  - the two tests;
  - the release checklist's item;
  - the README's row and limit, and §3.15;
  - `SHMEM_INFO`'s line;
  - `wire.c`'s and `bootstrap.h`'s comments.
- **Its evidence:** it cites none yet. The mutant's is in `build/scratch`, and the verification is
  running.
- **The decisions index:** its silent-peer check line (`docs/decisions/README.md:91`) is
  unqualified. `:108` carries the change.

**9. Outside the change: `osoe_listener_own_address` checks one other node only**
(`listener.c:780-786`; *observed in source*). It checks node 1 for node 0, and node 0 for every
other node.
- **The case:** a host list names one Debian host twice beside another host. That needs
  `osoe-launch -H`, or several `slurmd` on one host.
  - Node 0 reports its real address.
  - The later entry's node finds node 0's name resolving to loopback, and keeps 127.0.1.1.
  - The other host's lead then dials its own loopback, and the mesh never forms.
- **Keepalive's rule is unaffected:** a mixed table keeps it on.

## What is sound

- **Every launch path:**
  - **`osoe-launch -m`, and `-s` too**, give the nodes 127.0.0.[1-N] (`launch.c:257-258`).
    - The literals are taken as given (`listener.h:117-138`), so every lead reports 127/8 and keepalive
      is off.
    - `-s` gives the same list as `SLURM_STEP_NODELIST` (`bootstrap.c:472`).
  - **Slurm on a cluster:**
    - Names are resolved.
    - A name that resolves here to loopback, as Debian's 127.0.1.1 does, is replaced by the address
      this host sends from toward another node: a connected UDP socket's `getsockname`
      (`listener.c:773-806`). The table holds real addresses, so keepalive is on.
  - **Tier 3:** 10.99.0.[1-N] (`tier3.sh:101`, `:144-147`), never loopback, so keepalive is on. Its
    cut-link tests set `1,1,3` besides.
  - **A job of one node:** no wires, no silent-peer check, no table (`job.h:113-116`); unchanged.
- **Mixed jobs cannot be taken for one machine:**
  - **What the table holds.** Each lead's own report (`rendezvous.c:308`, `:243`), the same table on
    every lead, so every lead decides alike.
  - **An all-127/8 table means one network namespace,** for any job whose mesh forms.
    - Node 0 dials every other node at its table address (`progress-host.c:786-789`, `wire.c`), and
      on 127/8 that reaches only node 0's own namespace.
    - So a job across kernels with such a table never gets past `shmem_init`.
    - Keepalive is set at attach, after the connect.
    - Through a proxy or a tunnel on 127/8, keepalive probes only the near end anyway.
  - **The reverse happens and is harmless:** a one-machine job named by a non-loopback address is
    taken for a cluster, with keepalive on as before (note 4).
- **The readers, and their order:**
  - `keepalive_off` is read at `wire.c:132` and at `progress-host.c:528`. The first is reached through
    `osoe_wires_open`, whose one call in the library is `progress-host.c:806`; the second is
    `silent_check_start`, called at `:853`.
  - The decision at `:803-804` comes before both.
  - It is written only at `bootstrap.c:453` and `progress-host.c:804`.
  - Nothing else in `shmem/src`, `base` or `tools` reads it, and no copy of the bootstrap exists but
    `osoe.bootstrap` (`state.h:27`).
- **Leads only, and nothing compared:**
  - Non-leads return at `progress-host.c:678`, before the decision, and never read it. Helpers do not
    read it.
  - Keepalive is not among the settings compared between a node's PEs (`node.c:654-695`,
    `:1146-1250`), nor between nodes (`rendezvous.c:117-170`, the hello), so the derived value cannot
    refuse a job.
  - `SHMEM_INFO` prints fixed text. `osoe-stat` and `SHMEM_DEBUG` do not read it.
- **What a loopback job keeps:**
  - **A logical node killed with `SIGKILL`:** its kernel closes its sockets, so its peers read an end
    of stream without a goodbye, or a reset, and the job ends naming it (`progress.c:868-890`; the
    `shmem.dead-pe` tests).
  - **A stopped one:**
    - its kernel acknowledges data and probes;
    - a full buffer is probed through a zero window with nothing outstanding;
    - so the silent-peer check never fired there either (`shmem.stopped-bulk` pins that condition).
  - **Data in flight to a stopped node** is the same case.
  - The tests that set `OSOE_KEEPALIVE` keep it (`keepalive_set`), and none of them relies on the
    default.
- **The lead's mutant is real** (`keepalive-check.sh`):
  - It replaces exactly the two lines, asserting one occurrence, with `(void)one_machine;`, and
    builds both trees in the release preset.
  - The base passed 7 of 7.
  - The mutant failed `loopback-off`: "PE 0: 2 connected sockets, 0 with keepalive off". `set-on`
    and `invalid` passed.
  - A count of 2 shows the filter found the two wires and nothing else under ctest. The mesh
    listener is closed by `osoe_wires_open`, the rendezvous sockets are closed, and io_uring's
    descriptors are not sockets.
- **The counts:**
  - 859 and 460 are the lead's verification's own (debug: "out of 859", "internode ... (460 tests)").
  - The single-node build's 399 = 859 - 460 is unchanged, since both tests are inside
    `if(OSOE_INTERNODE)`.
  - "About 410" and "about 680" move by two at most: both new tests fail at `shmem_init` without
    io_uring or in 64 MiB of `/dev/shm`.
- **The rest:**
  - `set-on` pins `!keepalive_set`.
  - Both tests are labelled `tier2` and `internode`, with ctest's 90 s over the launcher's 60.
  - Correct as written: `SHMEM_INFO`'s line (`init.c:184-187`), the README's `osoe-launch`
    paragraph and the row's body, `wire.c`'s and `bootstrap.h`'s comments, the decisions index
    `:108`, the record's rule, and the release checklist's item removed.
  - The verification so far: debug 859 of 859 at zero, two and three helpers, and release 859 of
    859 at none.
