# v0.2 step 1, question 1: is osoe OpenSHMEM 1.6? (the single-node build's merge point)

Review of `main` at `7053819`, run 2026-10-06 against
`docs/reviews/adversarial-review-prompt.md`, with the changes its lead gave: the tree
is the one v0.2's first step left - the single-node build, `OSOE_SINGLE_NODE`
(`docs/decisions/2026-10-05-v0.2.md` items 2 to 5; the brief
`docs/prompts/v0.2-step1-single-node-prompt.md`; the records
`docs/decisions/2026-10-06-single-node-seam.md` and
`2026-10-06-single-node-build.md`) - held to the step's rule, one tree, two builds, no
drift: a job of one node runs the same code in both builds but the wait syscall. The
previous round is round six (`phase1-step7-slice4-*`, `375973a`), whose fixes merged as
`docs/decisions/2026-10-05-step-e-review-fixes.md`; 0.1.0 is the tag on `53b8f0f`.
Labels: *documented*, *observed in source*, *measured*, *recalled*. Section numbers
are the specification's (`docs/reference/OpenSHMEM-1.6.pdf`, present, read as
`pdftotext -layout`); "design §N" names the design notes.

**How it was run.** The review worktree was copied into each VM's `/tmp` and built
there with the `release` preset, every build and run under `/tmp/osoe-vm.lock`:
in `osoe-rocky` (Rocky Linux 9.8, kernel 5.14, GCC 11.5, no liburing headers) the
single-node build, 10 s, no warning; in `osoe-load` (Debian 13, kernel 6.12, GCC 14)
the full build (22 s) and the single-node build with liburing hidden from pkg-config
(11 s), both without a warning, and the 0.1.0 tag from `git archive 53b8f0f`. Each was
installed into a prefix of its own and every probe built with that prefix's `oshcc`
and run with its `osoe-launch`, as a desktop user would. The probes, written from the
specification and not from the design notes, are in Sources. Five mutants, each made
in a fresh copy and removed after, showed that the tests and probes leaned on here can
fail, and a sixth showed C1's fix. The Pi cluster was not used, and no finding needs
it.

## Verdict

**Yes, in this question's area: the single-node build can be offered to desktop users
as the README describes it, and the full build is still what 0.1.0 was.** Nothing
blocks, and nothing must precede either; four minors, below.

- **The single-node build is the same OpenSHMEM 1.6 as the full build for a job of one
  node** (*measured*). It installs the same files, the same five headers byte for byte
  and the same 3,595 exported symbols, so a program built against one runs against the
  other. A probe calling 107 of the library's routines, every result checked against
  the specification's text, printed byte-identical output and errors in both builds at
  1, 2, 3, 4 and 8 PEs under `shmem_init` and under `SHMEM_THREAD_MULTIPLE`, and at 16
  and 32 under the latter; Rocky's single-node build printed the same as Debian's. 160
  settings - valid, invalid and at both edges of every variable the README names, the
  specification's four and their `SMA_` spellings among them - ended identically in
  both builds at one PE and at two: the same status, the same lines. `SHMEM_INFO`,
  `SHMEM_VERSION` and `SHMEM_DEBUG` print the same text but the version, which says
  `(single-node build)` where the README says it will. Start-up, nested and repeated
  initialization, finalize and `shmem_global_exit` behave the same. The SOS suite on
  one node: the same exit status from both builds for every one of its 142 C programs
  at two PEs and at four; on Rocky, every one passes but SOS's own four, as the
  runbook lists them.
- **The one departure is said, and holds** (*measured*, *documented*): a job of more
  than one node - two to three logical nodes, Slurm's names or the launcher's, a map
  or a hand-made environment - is refused by every PE at `shmem_init`, naming the
  build, the node count and the remedy, with status 1 and nothing left in `/dev/shm`.
  The README says so in its desktop section (`README.md:151-154`), in Requirements
  (`:186-189`), under "Running a program on one machine" (`:468-469`) and in Limits,
  "Launching" (`:943-945`).
- **The full build is 0.1.0 for every program-observable behaviour I could construct**
  (*measured*): the probe on one node (1 to 8 PEs) and over six maps of two to eight
  logical nodes, both thread levels, and the settings matrix at one and two PEs, gave
  output identical to the tag's, byte for byte. The changes since the tag a program
  could notice at all are the step's recorded futex fixes - a signal no longer ends a
  timed wait early, and a sandbox that allows only private futexes is refused by name
  at start-up instead of aborting at the first shared wait - and a fifth heap base
  candidate, which matters only where the four before it are taken (GCC 11's
  ThreadSanitizer). All three are improvements, and recorded.

The four minors:

- **C1**: a heap whose `SHMEM_SYMMETRIC_SIZE` is not a multiple of 16 bytes is smaller
  than §8 allows - the specification's own example, `3.1M`, gives a heap that cannot
  hold 3,250,586 bytes. Both builds, since 0.1.0; a one-line fix, shown.
- **C2**: the README's SOS sentence still names the tree of 28 September - round six's
  M3, whose condition was met on 2026-10-05 - and gives nothing for the single-node
  build, for which this round has a sweep.
- **C3**: `SHMEM_INFO`'s text in the single-node build describes `OSOE_PORT_RANGE`,
  `OSOE_JOB_SECRET` and `OSOE_KEEPALIVE` as acting; the README says they do nothing
  there.
- **C4**: the single-node build's suite has no test of §9.1.6's handlers, two callers
  or flushed streams (those tests run over two nodes only), and no build tests
  `SHMEM_DEBUG` or the `SMA_` spellings of the other three; each is right today, by
  this round's probes.

### 1. What differs between the builds, by construction

- **Files, not branches** (*observed in source*). `OSOE_SINGLE_NODE` appears in no C
  file of the library: `base/CMakeLists.txt:13-17` builds `futex-classic.c` where the
  full build has `futex-futex2.c` and `ring-check.c`; `shmem/CMakeLists.txt:39-41`
  builds `transport-single-node.c` where the full build has the twelve files of the
  internode backend; `cmake/OsoeVersion.cmake:22-25` appends `(single-node build)` to
  the version text. Nothing else in the library differs.
- **What a program links against** (*measured*, `osoe-load`): the two installs hold
  the same file list; `shmem.h`, `pshmem.h`, `shmemx.h` and both `mpp/` headers and the
  statics linker script are identical; `oshcc` differs in its version line alone;
  `nm -D` lists the same 3,595 exported symbols with the same bindings. The full
  library needs `liburing.so.2` and imports 29 calls the single-node library does not -
  sockets, name lookup, io_uring, `getrandom`, `fcntl` and `ioctl` - and the
  single-node library imports nothing the full one lacks. So the builds are
  ABI-identical, and `SHMEM_VENDOR_STRING`, `shmem_info_get_name` ("osoe") and
  `shmem_info_get_version` (1.6) are the same: no program can tell them apart through
  the API, which is as it should be.
- **The refusing backend is never entered on one node but where it should be**
  (*observed in source*, *measured*). `transport-am.c` calls the backend only behind
  `internode` (`osoe.job.node_count > 1`, `:136`) - start, stop, the agent calls,
  context open and close, fence and both waits - or for a PE that does not route in
  this process (`:326`, `:339`, `:354`), and every PE of a one-node job routes in
  process, an out-of-range one being refused by name above the boundary first
  (`symmetric.c:66-71`, `context.c:118-129`). The four `internode.h` calls a job of one
  node makes are handed to the generic phase as AM hands them, but for AM's arrival
  array, which nothing on one node reads. Across every run of this round - the probes,
  the matrix, 572 SOS runs in `osoe-load` and 286 in `osoe-rocky` - the unreachable
  entry points' message ("was called in the single-node build") appears nowhere.
- **The control segment** (*measured*): `osoe-stat` on a live four-PE job of each
  build reads layout 31, 2,232,320 bytes, 221 metrics, descriptor checksum
  `0x360d6c61`, the same 54 counter names in its default view. The record's claim
  holds.

### 6. The wait syscall: the classic futex against futex2

- **Call for call the same contract** (*observed in source*): the private flag, an
  absolute `CLOCK_MONOTONIC` deadline (`FUTEX_WAIT_BITSET` without
  `FUTEX_CLOCK_REALTIME`; futex2's `CLOCK_MONOTONIC` argument), `FUTEX_BITSET_MATCH_ANY`
  for the plain calls, `EAGAIN` as a wake, `ETIMEDOUT` counted, `EINTR` retried to the
  same deadline in both files, a wake of 0 or less returning at once in both, the
  start-up check making a wake and a stale-value wait in each scope in both.
- **The record's three fixes are needed** (*measured*, each a mutant of
  `futex-classic.c` in the single-node build): `EINTR` returned as a wake again fails
  `base.futex`; the `n <= 0` early return removed fails `base.futex`; the start-up check
  trying the private scope alone fails `shmem.refuse.no-shared-futex`, which the job
  then passes by aborting at its first shared wait.
- **What a program sees under a signal** (*measured*, `sigwait.c`): a waited-for word
  stored plainly through `shmem_ptr` - no wake - while the waiter takes `SIGALRM` every
  10 ms is found within 4 to 111 ms in both builds, with `SA_RESTART` and without,
  three runs each: inside the 100 ms sweep `README.md:1085-1095` promises. With the
  `EINTR` fix taken out it is found in 4 to 9 ms - each signal ends the wait and the
  predicate is looked at again - so the defect the record found showed in the sweep's
  counters and in `osoe-stat`'s reading of the PE, not in a program's results; the
  `base.futex` pin is what holds it.
- One aside, not a finding: SOS's `spam` took 25 s on the single-node build against
  6 s on the full one in the sweep; five runs of each at four PEs then took 4.1 to
  10.0 s and 5.3 to 23.4 s. Noise of a four-core VM running eight threads, in both.

## Findings

Nothing rated *blocks release* or *fix before release*.

### Minor

- **C1. A heap whose size is not a multiple of 16 bytes holds less than §8 requires**
  (*measured*, *observed in source*). §8: "The resulting size is implementation-defined
  and must be at least as large as the integer ceiling of the product of the numeric
  prefix and the scaling factor"; its example: "the string '3.1M' is equivalent to the
  integer value 3250586". `osoe_allocator_init` sets the capacity to
  `capacity / 16 * 16` (`shmem/src/allocator.c:15`), rounding down, though the heap's
  mapping is page-rounded beyond it (`node.c:1489`). *Scenario* (`heapfill.c`, two PEs,
  every build including the tag): under `SHMEM_SYMMETRIC_SIZE=3.1M`,
  `shmem_malloc(3250586)` returns NULL and the largest object is 3,250,576 bytes; under
  `1000`, `shmem_malloc(1000)` fails and the largest is 992; `1m`, `.5m`, `20kk`, `1e6`
  and `64m` hold their whole size. *Shown*: rounding up instead -
  `(capacity + 15) / 16 * 16`, which stays inside the page the internal region begins
  after - holds 3,250,592 and 1,008, and the 24 tests matching alloc, malloc, heap,
  align, memory, calloc or realloc still pass. Not a listed departure

### Refuted, or no finding

- **The settings matrix differs between the builds without `-k`**: the launcher's kill
  race, run to run, in either build; with `-k`, 160 of 160 identical.
- **`spam` four times slower on the single-node build**: noise (above).
- **`shmem_align`'s promise cut from 64 GiB to 4 GiB** (`malloc.c`'s comment, with the
  fifth heap base): the check is made against the base actually chosen
  (`malloc.c:166-168`), which is the first candidate, as before, wherever it is free -
  the probe's first object at `0x100000053fd0` in the full build, the single-node
  build and the tag alike. A program sees a change only where the four earlier
  candidates are all taken, and then a refusal it can see, not a wrong address.
- **An invalid PE reaching the refusing backend's unreachable put on one node**: every
  path that names a target PE checks it above the boundary first (`symmetric.c:66`,
  `context.c:118`, `active-set.c:137`); none was found that does not.
- **The one-node shared context's wait without its mutex (part 1)**: the mutex was
  never taken by issue (§4.11 item 4), so it ordered nothing a program could see on one
  node; the multi-node probe and matrix are identical to the tag's.

## What is sound, and what convinced me

- **The two builds are one library for a job of one node.** Not because the records
  say so, but because nothing distinguishes them that a program can reach: the same
  headers, exports and control segment; the same output from a specification-derived
  probe at seven PE counts and two thread levels, and from SOS; the same answer to 160
  settings; the only difference the version text, which the README names.
- **The seam is a seam.** The refusing backend's 25 unreachable entry points were never
  reached in about 1,500 runs of the single-node build this round, and the boundary is
  files, not `#ifdef`s - which is what makes the first claim cheap to believe and to
  keep.
- **The refusal is by name, early and clean** in every shape tried, and its test fails
  when the check is removed.
- **The classic futex keeps futex2's contract**, and the three defects the step's
  adversarial read found in it are each held by a test that fails without its fix.
- **The full build has not drifted**: identical to 0.1.0 under the same probes on one
  node and on six maps of logical nodes, and under the settings matrix.

**Noted outside this question**, for the lead to route: the desktop section's example
runs eight PEs (`README.md:136-142`), which at the default heap needs about 2.1 GiB of
`/dev/shm` - more than the project's own 4 GiB Rocky VM has, where it is refused (by
name, with the remedies); and its "345 of the full build's 729 tests ... and four of
its own" is 347 on a Rocky machine set up as the README says, which has no C++
compiler. Both are the README's reader's matter (question 5).
