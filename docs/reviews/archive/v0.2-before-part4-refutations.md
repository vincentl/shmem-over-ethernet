## C9-1, the refutation: stands with changes

The finding: C9-1 in
`<repo>/build/scratch/wt/review-nine/docs/reviews/archive/v0.2-before-part4-correctness.md`
(lines 83-158). ThreadSanitizer's gate at a helper count passes a test that
failed its own checks. Checked against `main` at `3b45472` on 2026-10-11. Each
claim carries a label: *documented*, *observed in source*, *measured* or
*recalled*.

## Verdict

**The finding stands with changes to its scope and to its fix. Its severity,
fix before release, stands.**

The core of the finding is right. A process that has reported a race and then
fails leaves with ThreadSanitizer's 66 instead of its own status, and
`tsan-gate.py` reads any 66 as "the tool's reports alone". I planted failures of
my own, different from the investigator's. At two helpers the gate passed them
(*measured*):

- a segmentation fault in PE 1 of `shmem.ack-echo.0-1`, before or after
  `shmem_finalize`: passed six runs of six;
- a wrong byte in `shmem.circulant.4` that the test's own check found on PE 0:
  passed two runs of three.

At no helpers every one of these plants failed, every run.

The changes:

1. **The hole is wider: a crash passes too, not only a failed check.**
   ThreadSanitizer's deadly-signal handler leaves with 66 whether or not a race
   was reported. The gate counts only `WARNING: ThreadSanitizer:` lines, so an
   `ERROR: ThreadSanitizer: SEGV` beside any heap race passes it.
2. **The hole is wider: the run at no helpers does not back the gate up the way
   the finding says.**
   - The finding's "why not more" says "ThreadSanitizer at no helpers fails on
     any report". That holds for 290 of the preset's 606 tests.
   - 333 of the 606 are judged by a pass expression, and ctest ignores the exit
     status of such a test. Only 17 of the 333 have a fail expression that
     matches the launcher's "exited with status 66".
   - I planted a race in one process of `shmem.circulant.4` and ran it at no
     helpers. It passed ctest five runs of five. The report sits in the output
     of a passing test, which the verification never prints.
   - At two helpers, the gate reads only the tests whose reports happened to
     cost them their verdict. In one run where no rank was cut short, 27 tests
     reported a race. 13 of them are pass-expression tests that passed in the
     integration's run at two helpers, so no gate ever read their reports.
3. **The finding overstates what the runs it cites left unchecked.**
   - It says that for those tests "the runs at a helper count said nothing
     about whether the result was right". In fact the runs checked the results;
     only the gate did not read them.
   - Every `shmem_finalize` is a barrier (`shmem/src/init.c:561-564`). So every
     rank had run its checks before any rank could leave with 66, and a check's
     failure goes to stderr, which is unbuffered.
   - The SIGTERM costs a rank only its unflushed stdout. That is why the
     circulant tests lost their pass line.
   - The integration's logs at two and three helpers contain no `CHECK(` line,
     no fatal and no `ERROR: ThreadSanitizer`.
   - Under the corrected remedy the whole suite passes its own checks: 606 of
     606 at no helpers, and 605 of 606 at two and at three, the one failure at
     each being `stopped-bulk`'s explained timeout. Every race report there is
     a data race in a heap and names a helper thread.
   - I found no defect hiding in this tree.
4. **The fix as proposed has a side effect.**
   - **`exitcode=0` alone:** a crash that ThreadSanitizer catches then leaves
     with status 0. A segmentation fault after `shmem_finalize` passed ctest two
     runs of two.
   - **With `abort_on_error=1` added:** crashes end by SIGABRT and fail, and the
     controls pass.
   - **The report files:** they must be gated at every count, no helpers
     included. Gated there, they make the run at no helpers stronger than it is
     today.
   - **The first run under the remedy fails on thread leaks** that today's runs
     never show. These are helper threads left unjoined in processes that end on
     a death path. Each must be either explained, as `stopped-bulk`'s timeout
     is, or joined.
   - **The smaller remedy cannot fail on a missing pass expression** unless the
     exit-code change comes first. Five and four of the cited tests lack their
     pass line only because of the launcher's SIGTERM.

**Why the severity stays at fix before release, and why not higher:**

- The tag's checklist runs the four presets again at no helpers, two and three.
  The release note will then restate what those runs established.
- Five records say the gate checks what it does not: the README, the release
  note, the record of step 4's merge point, the helpers record, and the release
  note's fact check, which marked the sentence true on the gate's say-so.
- The fix is small, and it is in the test infrastructure, not in the library.
- It does not block release:
  - debug, release and AddressSanitizer run the same tests at the same helper
    counts and judge their results;
  - the corrected run finds nothing hidden.

Round eight's Q2-2 is unchanged in the gate: the diff between the two copies is
the licence line alone. The README already states that limit, so it does not add
to C9-1's severity.

## The claim, part by part

### 1. The status (*measured*, `probe/status-probe.c`, `logs/probe.log`)

The probe is a program built with gcc 14.2's ThreadSanitizer. It either races
on a shared mapping or does not, then leaves in one of six ways:

| Leaves by | With a race, default options | Without one | With a race, `exitcode=0` | Without one, `exitcode=0` | With a race, `exitcode=0:abort_on_error=1` |
|---|---|---|---|---|---|
| `return 0` | **66** | 0 | 0 | 0 | 0 |
| `return 1`, `exit(1)` | **66** | 1 | 1 | 1 | 1 |
| `_Exit(1)` | 1 | 1 | 1 | 1 | 1 |
| `abort()` | 134 | 134 | 134 | 134 | 134 |
| SIGSEGV | **66** | **66** | **0** | **0** | 134 |

What the table shows:

- The investigator's mechanism holds: `CHECK`, which returns from `main`, is
  masked. `CHECK_FATAL` and the library's fatal, which `_exit`, are not.
- A crash leaves with 66 even without a race, because the deadly-signal handler
  ends in the same `Die()`.
- Under `exitcode=0` that same `Die()` leaves with 0.
- With `log_path` set, every report, the SEGV included, goes to `<path>.<pid>`
  and none goes to stderr.
- The race-free `return 0` row shows the side effect for the run at no helpers:
  under `exitcode=0` a reported race no longer changes a process's status.

### 2. End to end, at two helpers, with the integration's gate (*measured*, `vm/planted.sh`, `logs/job-planted.log`, `logs/planted/`)

Each case was run three times through ctest and then through
`tsan-gate.py --timeout-explained shmem.stopped-bulk.0-0-1`, exactly as
`verify-integration.sh:52-55` applies it:

| Case | No helpers: ctest / gate | Two helpers: ctest / gate | Ranks at two helpers |
|---|---|---|---|
| Control, `shmem.ack-echo.0-1` | pass 3/3; nothing to gate | fail 3/3 (66) / **passed 3/3** | PE 1 66 |
| Crash before `shmem_finalize` | fail 3/3 / failed 3/3 | fail 3/3 / **passed 3/3** | PE 1 66, PE 0 SIGTERM |
| Crash after `shmem_finalize` | fail 3/3 / failed 3/3 | fail 3/3 / **passed 3/3** | PE 1 66 |
| Control, `shmem.circulant.4` | pass 3/3 | fail 1/3, pass 2/3 / passed 3/3 | reports in one run of three |
| Wrong byte on PE 1 | fail 3/3 / failed 3/3 | fail 3/3 / failed 3/3 | a rank with no report left with 1 |
| Wrong byte on PE 0 | fail 3/3 / failed 3/3 | fail 3/3 / **passed 2/3** | every rank 66 or SIGTERM |

The investigator's own three logs, `correctness/vm/logs/tsan-demo-h2-*.full`,
read the same: `TSAN GATE PASSED`.

The mask works process by process. A failure that also reaches a rank which
reported nothing fails the gate, because that rank leaves with 1 unless it is
ended first (the PE 1 row). So the gate is blind to a failure confined to the
processes that report, and the receiver of a helper's landing is exactly such a
process. In the crash rows, ctest's own reason for the failure,
"Error regular expression found", sits in the log, but the gate never reads
ctest's reason.

- So the strict run at no helpers fails on a report in 290 tests: 273 judged by

**The gate's population.** The suite at two helpers was run with

- 13 of them are pass-expression tests that the integration's run at two

### 4. Narrower than stated: the cited runs (*measured*, *observed in source*)

I re-read the lead's `verify-integration-4df0047/tsan-OSOE_PROGRESS_HELPERS_{2,3}.full`
(`<repo>/build/scratch/ladder/merge-point/`).

The investigator's counts hold:

- 15 failed tests at two helpers and 13 at three, every one passed by the gate;
- 5 and 4 of them missing their pass expression, all `shmem.circulant.*`;
- 11 and 14 ranks ended by SIGTERM.

What they mean is narrower than the finding says:

- **The checks ran.** `pshmem_finalize` is a barrier for every PE
  (`init.c:561-564`). The circulant test prints its pass line only after every
  PE's failures are summed (`test-circulant-reduce.c:668-673`). Every PE checks
  the sum with `CHECK(all[0] == 0)`, and every check prints its failure to
  stderr before `shmem_finalize`.
- **The circulant tests lost only the pass line.** In those tests PE 0 printed
  its pass line to a buffered stdout. The launcher's SIGTERM came after another
  rank's 66 (`tools/launch/launch.c:530-536`), and it took that stdout with it.
- **The logs show nothing hidden.** In the failing tests' output there is no
  `CHECK(` line, no `osoe: PE` line and no `ERROR: ThreadSanitizer`. Outside the
  reports, the output is the tests' own pass lines: "PE 0: rotation passed",
  "300 rounds passed", the pacer's `failures=0`.
- **The results were right when measured whole.** Under the corrected remedy
  (`vm/suite-remedy.sh`, `logs/suite/`) every one of those tests passes its own
  checks at two and three helpers.

In short, the evidence the release note cites hides no failure. What it lacks is
an automatic verdict that would have caught one.

### 5. What else would catch it

- **The same tests run in three other presets** (*measured*). The

  variants of the pacer's tests: `threads` on `0,1` and `0`, and `mix` on
  `0,0,0,0`. The other presets run those exercises on other maps.
- **Those presets judge the results at the same helper counts** (*documented*,

  AddressSanitizer 852 of 852, at two and at three helpers. A deterministic
  defect that only shows with helpers is therefore caught there.
- **A wrong result seen only under ThreadSanitizer's timing has never been

  one found none). That does not prove one cannot happen. ThreadSanitizer is the
  slowest of the four presets, and its timing differs most. That residue is what
  the fix is for.
- **The gate's verdict stops nothing** (*documented*). In the run the release
  note cites, `verify-integration.sh`'s own call of the gate failed to start

### 6. The remedies, tried (*measured*)

**The investigator's remedy, `TSAN_OPTIONS=exitcode=0` with `log_path`, at two
helpers, two runs each:**

- The wrong byte fails ctest, because the ranks leave with 1.
- The crash before `shmem_finalize` fails, but only because PE 0's library sees
  its peer vanish ("node 1 ended its control wire without its goodbye",
  status 1).
- **The crash after `shmem_finalize` passes ctest 2 of 2.** The SEGV appears
  only in the report file.

**With `abort_on_error=1` added:**

- Both crashes end by SIGABRT and fail.
- The wrong byte fails.
- The controls pass, with their reports in the files.

**The corrected remedy, `exitcode=0:abort_on_error=1:log_path=...`, on the whole
suite, `-j4 --timeout 600` as the verification runs it:**

| Count | ctest | Report files | Reports | `file-gate.py` |
|---|---|---|---|---|
| none | 606 of 606 | 1 | 1, a `thread leak` | fails on the leak |
| two | 605 of 606, `stopped-bulk` timed out (explained) | 92 | 102: 100 heap data races, each naming a helper thread, and 2 `thread leak` | fails on the 2 leaks |
| three | 605 of 606, the same timeout | 92 | 107: 105 heap data races and 2 `thread leak` | fails on the 2 leaks |

About these runs:

- Each count took about three minutes, as today's runs do.
- **The leaks.** They are helper threads left unjoined at exit in processes
  that end on a death path. The verbose run at two helpers names
  `shmem.helpers.deaf.0-1`, `shmem.reply-pool.overflow`,
  `shmem.kill-after-init.TERM` and `shmem.dead-pe.lead.0-0-1-1`. Every one of
  these tests passes ctest under the default options, so no current run shows
  the leaks. A remedy run will fail on them until each is either explained or
  its helpers are joined.
- **The race planted at no helpers, under this remedy:** ctest still passes it,
  as expected, and the file gate fails it 3 of 3. Gated by its report files,
  the run at no helpers covers all 606 tests. Today it covers 290.

**The smaller remedy** (`vm/gate-amended.py`):

- I added two failures to `tsan-gate.py`: any `ERROR: ThreadSanitizer` line,
  and any `CHECK(` line.
  - On the cited runs it passes both, as before.
  - On the plants it fails all eight that the original gate passed, and the
    investigator's three.
- The proposed failure on a missing pass expression would fail the cited runs
  (5 and 4 tests), unless `exitcode=0` comes first.
- Failing on ctest's "Error regular expression found" fails
  `tools.pacer.threads.0-1` every run, because its fail expression matches the
  launcher's 66 line.
- This gate stays blind to two things:
  - a failure written in a test's own words, such as the pacer's `failures=N`;
  - any pass-expression test whose report did not cost it its verdict.

  It is a stopgap. The exit-status remedy is the fix.

## Refutation of portability P9-1: Linux 6.14's ring charge, per user per host, against logical nodes and the suite

The finding: `<repo>/build/scratch/wt/review-nine/docs/reviews/archive/v0.2-before-part4-portability.md`,
lines 21-35 and 132-235, rated *fix before release*, "computed, not run". Read at
`3b45472` in the review worktree. Nothing in the repository or the worktree was
changed. Run on the Pi cluster, the one 6.14+ kernel at hand. Labels:
*observed in source*, *documented*, *measured*, *recalled*.

## Verdict: stands with changes - scope and fix; the severity holds, as documents and the runbook

**Every number the finding computed for the Pi's pages is exact, now measured.**
With one PE a logical node, `osoe-launch` starts 112 logical nodes and refuses
113 at no helpers. At two helpers the line is 56 against 57, and at three it is
42 against 43. Alone, `shmem.circulant.64` and `.70` are each refused at two and
three helpers, and so are two 64-node tests the finding does not name,
`shmem.shape.chosen.pi.64` and `.loopback.64`. At the step's default limit, the
runbook's tier 2 at `-j4` failed in each of the four runs made so far, the
lead's two and two here.

**Two premises are wrong, and they change the fix.**

- **"So a user cannot raise it"** is true of a login session (8192 KiB soft and
  hard, measured on `pi-login`). It is not true of a Slurm job here: in a batch
  script and in a step the soft limit is 8192 KiB but the hard limit is
  **unlimited**. `ulimit -S -l unlimited` there works, and with it:
  - all eight refused runs pass;
  - the runbook's whole tier 2 passes, 760 of 760 at `-j4`;
  - 254 logical nodes start and finish on one Pi node.
- **"No kernel of 6.14 or later has run the suite"** is wrong. The Pi has run
  6.18.50 since at least 2026-09-28, with tier 2 at no helpers on it. What has
  never run on 6.14 or later is the suite at helpers.

The finding's `RESOURCE_LOCK` would not have made the Pi's suite pass at two or
three helpers, where each large job is refused alone. It also leaves out the two
shape tests.

**Who meets it:**

- **Desktop users of `osoe-launch` with many logical nodes** on 6.14 or later.
  The hard limit there is 8 MiB, so raising it is an administrator's change.
- **The suite on such kernels.**
- **The tag's own Pi check, as written.**
- **Not a real cluster's job.** One lead a host costs at most 2.6 MiB of rings
  even at the default 4,097-node ceiling (measured by emulation on the Pi's
  pages).

So it is fix before release: the README's sentences and one `ulimit` in the
runbook's tier-2 step. No library change is needed before the tag. The refusal
is immediate and names the limit.

## Claim by claim

**1. The charge: every ring of a user on a host, against each process's
`ulimit -l`.** *Holds* (*measured*). Each `hold` run measured the user's count
once every lead's rings were made. It was exactly the sum of the leads' rings,
the same at once and two seconds later, and the refusals came where that sum
passes 512 pages (8 MiB of 16 KiB pages).

| Per lead | No helpers | Two helpers | Three helpers |
|---|---|---|---|
| Pages, 2 to 64 logical nodes | 3 | 9 | 12 |
| Pages, 70 to 112 logical nodes | 4 | 9 | 12 |
| Pages, 113 to 128 logical nodes | 5 | 9 | 12 |

Every ring is three regions of a page each on this kernel: its completion ring,
its submission entries and its provided-buffer ring. That is 48 KiB a ring
whatever its size, so at two and three helpers the extra rings, not their sizes,
set the line.

**The finding's formula is a little high for large rings, and no threshold
moves.** Its arithmetic (`calc/ring-charge.py`) counts an index array that is
never made: liburing 2.9 passes `IORING_SETUP_NO_SQARRAY` (`flags.c`: a ring made
as `ring.c` makes its own has flags `0x11048`; *measured*). As written, the
formula matches 32 of the 36 points measured from 2 to 2,049 nodes and overstates
four, at 1,000 and 2,049 nodes, by 1 to 4 pages. Without the array it matches all
36.

**2. "8 MiB, soft *and* hard ... so a user cannot raise it."** *True of a
login session, wrong for a Slurm job here* (*measured*).

| Where | Soft | Hard |
|---|---|---|
| `pi-login`'s shell | 8192 KiB | 8192 KiB |
| An `srun` step | 8192 KiB | unlimited |
| An `sbatch` script, and its step | 8192 KiB | unlimited |

## Refutation of portability P9-2: the fast-link kit's `srun` cannot start more PEs a node than CPUs

The finding: `<repo>/build/scratch/wt/review-nine/docs/reviews/archive/v0.2-before-part4-portability.md`,
lines 36-45 and 237-282, rated *fix before release* (high confidence). Read against `main` at
`3b45472` in the review worktree, and run in the `osoe` VM's Slurm (24.11.5-4+deb13u1, one node of
4 CPUs) under `/tmp/osoe-vm.lock`, in three runs of under four minutes each. Scripts, every
`slurm.conf` tried and every log: `<repo>/build/scratch/review-nine/refutations/P9-2-work/`
(`p92-slurm.sh`, `p92-slurm2.sh` and `p92-slurm3.sh`; `p92-slurm-log.txt`, `p92-slurm2-log.txt`
and `p92-slurm3-log.txt`, and a first attempt's, stopped after 18 s; `p92-slurm-confs.txt`). Labels: *documented* (Slurm 24.11.5's man pages,
installed in the VM), *observed in source* (the kit; Slurm's own source on GitHub, branch
`slurm-24.11` and `master`, read through a fetch tool), *measured*, *recalled*.

## Verdict: stands with changes (to the fix)

The refusal is real, it holds under the kit's own `slurm.conf`, and the source says why: in
`select/cons_tres`, `--ntasks-per-node` takes precedence over `--overcommit` when Slurm tests whether
a job fits a node. Memory accounting, `OverSubscribe` and the task plugin do not enter into it. Every
32-PE-a-node job of the kit fails at allocation on a `c4-standard-16`.

The changes are to the fix:

- **Drop "a larger `CPUs=` in `slurm-setup.sh`".** As stated it does not work: `slurmctld` resets
  `CPUs=` to the product of the node line's sockets, cores and threads. The variant that does work
  fakes the node's topology and needs an override the manual calls "generally only useful for
  testing purposes".
- **Add the smallest working change:** each `launch` its own exclusive allocation, with the kit's
  `srun` as its one step. I measured it end to end, including `launch`'s timeout and its cleanup by
  name, and it leaves the rest of the kit's assumptions as they are.
- **The per-section allocation the finding proposes also works,** but it needs more than
  `--overlap`. `launch`'s cleanup by job name no longer reaches a step, and a step whose `srun` was
  killed holds its CPUs until its tasks end.
- **The obvious improvisation, `-n` instead of `--ntasks-per-node`, is a trap.** Without
  `--exclusive` it starts, but it confines all of a node's PEs to the one CPU it was allocated. With
  `--exclusive` it pends for ever.

The severity stays *fix before release*, which here means before Part 4's nodes are rented; the
library is not affected. Checking binding turned up two related problems outside P9-2's statement.
`on`'s and `spawn`'s jobs are confined to one core (R1), and `slurmd -C` crashes in this VM (R2).
Both are at the end, for the lead.

### 2. "The documentation allows it": it says two things, and the code honours neither for this form

`srun`'s `--overcommit` (*documented*, 24.11.5) has a paragraph for job allocations and another for
steps:

- **For job allocations:** "(not including jobs requesting exclusive access to the nodes) the
  resources are allocated as if only one task per node is requested ... Options used to specify the
  number of tasks per node ... are ignored". That gives nothing to the kit's `--exclusive` form. For
  a non-exclusive job, `--ntasks-per-node` is not ignored (*measured*, C1).
- **For steps:** "By specifying --overcommit you are explicitly allowing more than one process per
  CPU". That is the one the finding quotes, and it holds (§4).
- **The kit's earlier reads.** The second adversarial read of the kit left exactly this open: "how
  `--overcommit` combines with `--exclusive` at allocation". It *recalled* that `--overcommit` drops
  the check. For cons_tres it does not.
- **No setting relieves it** (*documented*). `MaxTasksPerNode` limits a step's tasks (512).
  `OverSubscribe` is "more than one job at a time on each resource".

### 4. "The kit's form works inside an allocation": yes, and the cost differs between two ways of doing it

**One allocation a section** (the finding's fix; C1, *measured*):

- **The kit's `launch` line runs as a step, its `KIT_SRUN` unchanged.** With `--exclusive` and
  `--overcommit`, 8 tasks and 16 tasks ran on 4 CPUs, unbound (`allowed=0-3`). `on`'s form inside it
  is unbound too, alone and with `--overlap`.
- **Concurrent steps need `--overlap`:** a second step on the node waited for the first. It ended
  8,088 ms after a step of 8 s began; with `--overlap`, 1,056 ms. Without it `floor.sh`'s servers and
  clients would stall, as the second read said.
- **`launch`'s cleanup no longer works.**
  - `scancel -u USER -n osoe-kit` returned 0 and left the step named `osoe-kit` running. It matches
    job names, and the job is the allocation's.
  - Named `osoe-kit`, the allocation would itself be cancelled, and every later step with it
    (inferred: run 3 shows `scancel -n` cancelling a job by that name).
  - An `srun` killed by `SIGKILL` (status 137, as `timeout -k` gives) leaves its step. The next step
    without `--overlap` waited for its tasks: 17,463 ms for a `sleep 15` killed at 3 s. With
    `--overlap` it did not wait.

    later `launch`es until its tasks end, or, with `--overlap`, runs beside them. A stalled wait
    ends itself after the kit's `OSOE_NO_PROGRESS_TIMEOUT=60`; a busy hang does not.

- **It keeps the kit's other assumptions:** each `launch` is still a job named `osoe-kit`, `floor.sh`'s

- **Two details for whoever writes it** (*documented*):
  - `salloc`'s `-K` is `--kill-command`, not `srun`'s `--kill-on-bad-exit`, so `KIT_SRUN` cannot be
    handed to `salloc` whole.

## The changes

**The fix.** The investigator's variant marks every 1 ms slot from a call's start to its
return. Measured against the exact count:

- **At 8 PEs a node and the VM's rate it is close:** 3.75-4.32 against 3.43-4.12.
- **It overcounts wherever a block lasts only a few slots:**
  - 2.08-2.28 at two PEs a node, above the two peers they can be in calls toward;
  - 4.55-5.15 against 3.43-4.12 at 8 × 8 at 23 Gbit/s, where a 1 MiB block lasts about
    3 ms;
  - at 64 KiB, the kit's figure again (6.60-6.72).
- **It counts the quiets as idle.** Put streams spent 11-37% of their PEs' time in quiets
  at 1 MiB and 22-48% at 64 KiB, with data still going out. Gets spent 1-3%.
- **Its error runs the safer way.** It can hide a mild convoy, not invent one, so it is
  much better than the figure as built. But it is not the model's quantity, and §5 compares
  it to the model's numbers.

A better fix, in two parts:

1. **Count the time exactly.** Either:
   - slots of about 50 µs, 200,000 words for a 10 s window: a 1 MiB block at 23 Gbit/s
     then spans about 60 slots, and the union's overcount becomes a sixtieth; or
   - each PE's (start, return, peer) kept locally and swept on the node's first PE after
     the window, which is what `analyze.py` does offline.
2. **Report the quiets.** Count each quiet toward the nodes whose puts it waits on, or
   report the time in quiets apart.

Either way, §5 should name the quantity and set only that quantity beside the model's
four, five and six. It should also keep saying that 64 KiB rows are unions.

**Optional: print each helper's CPU.** `thread_cpu` already reads each `osoe-helper-N`
thread; printing each one's CPU over the window would show directly whether H helpers are
fed, which is what §5's "three quarters busy" is about.

**The evidence.** The gets' 3.2-3.4 peers in calls at 5 × 8 measured 2.35-2.65 here from
the investigator's own variant, and 2.30-2.70 exact. The finding's second column is itself
a 1 ms union, so its put figures sit near the exact count only at 8 PEs a node.

## Claim by claim

### 1. The mechanism - holds

Each job of more than one node measures the link at the end of `shmem_init`
(`link-measure.c:222-283`): the root's lead, against its first child, the hop
from fifteen round trips, the bandwidth from the slope of a 512 KiB stream over
a 128 KiB one, three tries each, medians; the message cost from a fan. Every PE
takes the root's numbers, and `init.c:446-448` hands the bandwidth to the
transport, whose limit is the bandwidth times 128 µs, at least 16 KiB, at most
1 GiB, unless `OSOE_WIRE_UNSENT_BYTES` is set (`wire-settings.c:90-102`). A
hand-set limit is applied at the same moment as the rule's and changes nothing
else (`transport-internode.c:290-293`; `unsent_set` has no other reader). The
measurement's puts go on the data wire - the control wire carries "nothing
with a payload" (`progress.h:283-285`) - whose owner is helper 1 + slot mod H
from H = 1 (`owner-map.h`), as the finding says (*observed in source*).

### 2. "Recorded nowhere" - wrong for §7 and §9; right for §5 and §8, and for §10 too

  prints every node-scope metric (`stat.c:1134-1151`), among them
  `node.link.measured_hop_ns`, `_message_ns` and `_bytes_per_second`, which every
  node's lead stores from the link in force (`link-measure.c:273-282`,
  `metrics.c:393-397`). The limit is the rule applied to that bandwidth.
  - *Measured* (experiment A): two §7-style and two §9-style jobs, as the
    scripts launch them, under `SHMEM_DEBUG`. In all four the dump's three

- **On the VM, the machine's noise swamps any limit effect** (experiment B,
  *measured*): `multistream put` at 1 MiB and 64 KiB, at no helpers and two,
  with the limit held at 16,384, 164,929 and 810,167 bytes and left to the rule,
  the eight cases rotated, three rounds. An arm whose limit was held still
  ranged up to twofold over its rounds (two helpers, 1 MiB, 16 KiB: 1,605 to
  3,137 MiB/s), and the arms' medians did not order by the limit: at no helpers
  and 1 MiB, 5,188 at 16 KiB, 2,982 at 164,929, 3,617 at 810,167 and 5,532 under
  the rule - whose own limits (160,355 to 361,934) bracket the 164,929 arm's. At
  two helpers the 810,167 arm was the fastest at both sizes; at none it was not.
  The progress threads' CPU a GiB moved inversely with the rate, not with the
  limit. In each of the rule's four groups the highest draw came with the
  highest rate, while the arms whose limit was held varied as much: here the
  draw is a symptom of the machine's state at the start, not a cause shown. The
  VM can neither show nor exclude an effect on a NIC.
- **The sweeps the finding names are multi-peer, where a connection's limit
  binds least.** The limit is sized to the whole link's bandwidth, but each of a
  node's connections carries a share: at the three to six peers in progress at
  once that the runbook's model gives at eight nodes (`fast-link.md:238-240`)
  and the investigator's interval measure about three at five nodes of eight
  PEs, a connection's
  limit holds three to six times 128 µs of its own traffic, so a draw at half
  the true bandwidth still leaves it 190 to 380 µs (*inferred*). §9's senders
  each feed one connection into a receiver shared by every other node, the
  same. The two-node parts - §6, §8's `get-pieces` - are where a draw could
  bite, and §8 sets a get's time beside a put's measured in the same jobs,
  under the same draws (*observed in source*, `summarize.py:263-273`), which
  partly cancels it.
- **Rotation does not average a per-job draw; three rounds' medians blunt one
  outlier.** The finding is right that the rotation answers drift, not this.
  A draw that tracked the helper count would not average at all - but would then
  be part of what helpers do to the default configuration, which measures at
  every start, and a pinned sweep would not see it.
- **§6 runs 33 jobs under `SHMEM_DEBUG`** on the cluster: a sample of the
  draw's spread between the first two nodes, and its arms say whether the limit
  matters. If both say it does, the session plan keeps the fourth session for
  "whatever the first three left to repeat" (`fast-link.md:93`), so §5 could be
  run again with the limit held. The loss is recoverable - but §6's draws are
  two nodes of two PEs, not §5's eight nodes of 8 to 32, so §5's own draws would
  still be unknown.

### 5. The fix - the minimal one, everywhere; pinning optional

- **`SHMEM_DEBUG=1` on every job costs nothing at run time.** It is read once
  (`bootstrap.c:515`) and used only for start-up lines: `init.c:462`,
  `listener.c:803`, `progress-host.c:534` and `:548`, and the limit's line,
  printed once - `say_unsent` runs every agent pass either way and returns at
  once (`progress-host.c:498`, `:1514`) (*observed in source*). In `common.sh`'s
  `launch` it covers every section in one line; `summarize.py`'s patterns
  (`multistream `, `summary mailbox `, `fan-in `, `startup `, the floor's
  ratios) match none of its lines. Its write lands inside `shmem_init`, which
  §10's start-up probe times - microseconds against 27 ms and more.
- **`summarize.py`** should print, a row at a time, node 0's limit and PE 0's
  link from those lines - or for §7 and §9 from the dumps'
  `node.link.measured_*`, which it already parses.
- **Pinning** (the finding's "better") holds the treatment clean, but it
  measures a configuration other than the default the section decides, which
  measures at every start, and it hides whether a helper count moves that
  measurement. Taken from "one measured start", it would also carry that one
  start's draw into every job: take the median of several starts' lines - §3's
  start-up probe run a few times under `SHMEM_DEBUG`, say - and use `OSOE_WIRE_UNSENT_BYTES`
  where only the limit is in question (§5, §7, §8, §9) and `OSOE_LINK_*` where
  the shapes are (§10, and §5 if S3's collectives join it). Record either way.

### 6. Severity

*Fix before release* - before renting - holds, but for a narrower reason than
the finding gives: not because the helper table *would* mix the draw with the
helper count, which nothing shows, but because a covariate the kit's own rule
says to keep ("a number without them is not comparable with another", §2; the
ladder's note 17) is lost with the machines at §5's and §8's layouts, and keeping
it is one line with no cost. Of the scale review's three, it ranks third: S1
misreads what it measures, S3 omits a workload the decision needs, and S2 leaves
out a covariate whose weight §6 will show.

## What survives, as the finding should read

**S2. §5 and §8 - and §10 - keep no record of the link each job measured or
the unsent limit it set; §7's and §9's dumps keep it, but no summary prints it -
*fix before release*.** Each job measures its own link at start-up and sets
every data wire's limit from it. On the VM, starts spread fivefold to eightfold
in minutes, which the project knew as the VM's ("no link"); on the Pi's real
link fifteen starts' bandwidths agreed within 3%; a fast NIC's spread is
unknown, and so is whether
the limit moves a stream's rate there, which is §6's question. If it does, §5's
rows carry an unrecorded draw beside the helper count, and §10's collectives a
shape chosen from it. Fix: `SHMEM_DEBUG=1` in `common.sh`'s `launch`, and
`summarize.py` printing each row's limit and link (from the start-up lines, or
the dumps' `node.link.measured_*`); optionally, hold the limit or the link at
the median of several starts where it is not the question. Confidence: high on
the mechanism and the record; low that the draw would move a NIC's comparisons -
untested.

## Verdict: stands with changes

The gap is real, and nothing in the plan closes it. §5, the sweep the runbook names as what decides

## What I tried to refute it with

### 1. "The default is a decision about streams, by design": fails

- The proposal's measurements on a fast link are "a put stream and the mailbox rate at H = 0, 1, 2, 4

- The brief's Part 4 asks for the same measurements, "against `echo-uring`'s bare stream", and "a
  rule for the default count if the numbers give one" (`docs/prompts/done/v0.2-step4-progress-helpers-prompt.md:254-261`).
  So does the arc's gated item (`docs/prompts/task-v0.2.md:85-88`).
- §5's four workloads are those two plus the get stream: the kit is faithful to its brief.

Why it fails:

- **The plan was set before anyone had timed a collective at a helper count.** The proposal, brief and
  task were written on 2026-10-05 and amended on 2026-10-07 (*documented*). The Pi's collective lines
  at two helpers were in Part 3's run of 2026-10-08, but they were left out of its record until round
  eight's S4 found them (`docs/decisions/2026-10-08-helpers.md:322-328`, *documented*).
- **The kit was written after that evidence.** The README's sentences from S4 are in `4f1014d`
  (2026-10-10 08:57); the runbook is `d4b0e6b` (19:27) (*observed in source*, `git log`).
- **A default applies to every program, not only to a stream, and the README's own reason for "none"
  names the collectives.** The row reads: "on four nodes of the Pi cluster two of them made
  broadcasts and alltoalls slower, bound or not, ... which is why the default is none" (`README.md:1517`).
  "What does not scale" says helpers "cost broadcasts and alltoalls more than they bought"
  (`:826-828`). §11 says §5's numbers replace or confirm both (`docs/fast-link.md:375-378`)
  (*documented*). Nothing in §5 can speak to either sentence's collective half.
- **§5's stated test looks at the gain side only:** "whether a helper count raises the rate a node
  reaches toward that share, at what CPU, and whether that holds at every PE count"
  (`docs/fast-link.md:260-264`, *documented*).

### 2. "§10 already measures the collectives at each count": partly, not enough

What §10 does give (*observed in source*):

- `osoe-bench` with no argument runs the barrier and every collective line: reduce and broadcast at 8
  bytes and 64 KiB, and fcollect and alltoall at 8-byte and 4 KiB blocks. Each line is 2,000 trips
  after 200 of warm-up (`tools/bench/osoe-bench.c:58`, `:181-236`).
- §10 runs it at no helpers and at §5's count (`docs/fast-link.md:353-354`).
- The sessions run §5 second and §10 fourth (`:87-93`), and every decision is the author's (`:38-39`).
  So a large effect would be in front of the author before anything is decided (*documented*).

What it does not give (*observed in source*, `docs/fast-link/scale.sh:18-25`):

- **One job a side, in a fixed order.** The no-helper job runs first, then ten minutes of `mix`, then
  the job at N.
- **Only the count §5 chose** ("`HELPERS="0 N"` with §5's best"). So it cannot show which count the
  collectives favour.
- **8 and 16 PEs a node only**, not 32.
- **No summary.** `summarize.py` prints a `bench-` file's first sixty lines raw: no medians, no

What one run a side can and cannot show:

- **It would show an effect the size of the Pi's under binding.** There, two helpers cost 20 to 35%,
  and "each run of two helpers [was] within 3% of the other" (round eight's
  `docs/reviews/archive/v0.2-step4-scale-and-performance.md:265-267`, *documented*).
- **It would not separate an effect the size of the Pi's unbound one** (2 to 3% on the alltoall, 8 to

  as a helper count's" (`docs/fast-link.md:248-249`). The helpers record said it of the Pi's single

And if §10 does show a cost at N, a smaller count can only be tried on machines that are deleted at

### 3. "The mailbox stands in for the small-message work": fails, and this is the finding's best evidence

- **On the Pi, two helpers moved §5's workloads and the collectives in opposite directions**

- **No record ties S4 to Part 4's plan.** Round eight's synthesis took S4 to the README's sentences

### 5. "0.2's default stays off whatever §5 finds": narrows the scenario, does not refute the gap

- **The author's record keeps helpers off.** In the answer that put Part 4 in 0.2: "Helpers stay off

## What changes

**The scenario.** Replace "the default becomes two ... can slow every collective-bound program" with
the two harms above:

- §11's README sentences on helpers rewritten from the gain side alone, read by users who set the
  count themselves;
- a rule for the count, if the author wants one after 0.2, designed either without the data or after
  another session. At the runbook's $0.79 a node-hour, four hours of eight `c4-standard-16` cost about
  $25, plus the half hour of setup each session repeats (`docs/fast-link.md:80-82`, `:96-98`,
  *documented*).

**The ground.** Drop the decisions index's rule (`docs/decisions/README.md:166`) as the reason §10's
runs cannot be compared:

- **It is a rule about the Pi's barrier and 8-byte reduce** under `--cpu-bind=none`, which land in
  one of two modes from job to job, about 25 µs apart. In the same session, the broadcasts pooled
  within 1% (`docs/decisions/2026-10-04-step-e-merge-point.md:72-83`, *documented*). It does not
  cover the 64 KiB broadcast and 4 KiB alltoall, where the helpers cost.
- **The kit's rotation rule and the helpers record's sentence carry the point instead** (item 2).
- **The rule does bear on the fix.** If the Pi's modes recur on these nodes, three unbound rounds a
  side "can draw them unevenly" for the small lines. So read the barrier and 8-byte lines pooled or
  by mode, and decide on the 64 KiB and 4 KiB lines.

**The fix.** Keep the investigator's: a collectives workload in `helpers.sh`, in the counts' rotation
and rounds, and a sentence in §5 that the default weighs it beside the streams. Add three things:

- **Use `osoe-bench quick barrier collectives`, not the full trips.** `quick` is 200 trips a line
  after 200 of warm-up, instead of 2,000 (`tools/bench/osoe-bench.c:58`, `:346`, *observed in
  source*). At eight nodes of 32 PEs, the full 4 KiB alltoall alone would be about 2,200 calls. Each
  sends 28 MiB out of every node, some ten milliseconds at 23 Gbit/s, so that one line would take over
  twenty seconds (my arithmetic from those counts, not measured). The investigator's "36 jobs of about
  ten seconds" holds with `quick`, not without it.
- **Teach `summarize.py` the bench's lines.** It should report `barrier`, `reduce`, `broadcast`,
  `fcollect` and `alltoall` at each size, by workload, PE count and helper count, with the median and
  range over the rounds, as it does the mailbox's. As written it parses none of them, and a §5 file
  not named `bench-` would go unread (`docs/fast-link/summarize.py:150-191`, `:206-207`, *observed in
  source*).
- **Rewrite the "Not measured by the kit" paragraph** so that the barrier keeps its own reason for
  being left out and the paragraph is no longer silent on the data collectives.

The alternative the finding names, `osoe-pacer collectives`, does time one case a round, five calls,
and reports the slowest PE's median (`tools/pacer/collectives.c:12-17`, *observed in source*). With
200 or 2,000 trips a line, `osoe-bench` is the steadier measurement.

**The severity.** *Fix before release* stands, in the sense the investigator defined: a defect of the
kit, to fix before the machines are rented, since the tag waits for Part 4
(`docs/decisions/2026-10-10.md` item 3).

- The fix is minutes of editing and, by the investigator's count with `quick`, about ten minutes of
  the helpers' session.
- Leaving it out cannot be undone without renting again.
- It is not a defect of the library, and 0.2's default does not depend on it.

**The confidence.**

- **High** that the plan has no rotated measurement of the collectives at helper counts, and that §10
  can show only a large effect, and only at one count.
- **Medium** that a fast link's collectives move with helpers as the Pi's did. The Pi's cost came
  from a gigabit link and four cores; with 16 vCPUs, the alltoall's apply might gain from helpers
  instead. That uncertainty is the reason to measure them, not a reason not to.

## What I tried to refute it with

### 1. "The README already says it": partly, and not where a user looks

  reason. "The same install on each" literally forbids a node left at 0.1.0, so the requirement is
  there in substance. But:
  - it names no release or version;
  - it sits in no Limit and in no section about diagnosing a failure;
  - it says nothing of what happens when the installs differ.

  The user who meets the hang did not knowingly break it, and nothing they read from the notice
  leads back to it.
- **The note's fact-check read it the same way, and let it pass**: "'and run the same osoe' is the
  draft's own addition (no README sentence; README:358-360 asks the same install on every node)"

**Result:** "never says" is overstated. The substance stands.

### 2. "The wait is bounded": by what a user sets, and the notices then blame the network

*Observed in source*, in both releases:

- **Each listener drops the other's hello.** The hello's structure is the same size in both
  (`listener.c:48-64`; v0.1.0's :47-63), so each side reads the other's hello whole and drops it;
  neither waits for missing bytes.
- **Each caller then records** "no answer to the hello on a candidate port" and dials again
  (`listener.c:863-867`; v0.1.0's :859-863).

**What ends the wait, and what each bound prints:**

- **`OSOE_NO_PROGRESS_TIMEOUT`**:
  - It is `0` by default ("No wait gives up by default", README:1107). The README asks for 60
    "while a cluster is new" (:451-453).
  - It ends the job with "node 0 is waiting for node 1, its child in the rendezvous tree, to connect
    to its port N" (`listener.c:533-534`), or with "this node's lead has not finished the job
    rendezvous" (`job.c:233-234`).
  - *Measured* by the investigator at 20 s, both ways round
    (`<repo>/build/scratch/review-nine/readiness/e-upgrade.log`).
- **Under `srun`, the step's time limit.** No task fails, so `-K1` never fires. Until the limit, the
  notices come at 30 s and then every minute (README:1664-1666).
- **`osoe-launch -t`** (60 s by default) ends it with "osoe-launch: timeout after 60 s; killing ...
  -t sets the timeout" (`tools/launch/launch.c:549-551`). But `osoe-launch` cannot make a mixed job
  by itself: its logical nodes run one program on one machine. The investigator needed a wrapper
  script that chose the binary by `OSOE_NODEID`.

**What the notices tell the user** (*measured*, the same log):

- the caller: "no answer to the hello on a candidate port";
- the listener: "waited N s for node M ... to call it on port P (1 caller part-way through the
  hello)".

**The README glosses neither.**

- "How a job starts" lists "no answer to the hello" among a calling lead's last errors, with no
  cause (README:1669-1671).
- Its Trust paragraph names other causes of a strange port (:1681-1690).
- `osoe-stat`, where the README sends a hang, reads either release's segments (*measured* by the
  investigator). It shows no release: `tools/stat/stat.c` prints one only for `--version`
  (:1725-1726).

**The one clue is `SHMEM_VERSION=1`**, whose lines name each PE's release (*measured*, the same
log). But the README asks only for "the line `SHMEM_VERSION=1` prints" in a report (README:186-187):
one line, not a comparison between nodes.

**Result:** the wait ends only where the user has set a bound, and nothing ever names the cause.
This does not refute the finding.

### 3. How 0.1.0 treated mixing: it had nothing to mix with

*Documented*:

- **0.2 is the first tag at which the case exists**: `git tag -l` gives `v0.1.0` alone.
- **0.1.0's README says nothing on releases.** It has the same install sentence and the same
  architecture item, comparison list included (`git show v0.1.0:README.md`, :266-268, :886-891).
- **0.2's note added the clause.** 0.1.0's note says: "The README's Limits list every limit a
  program can meet; in short: ... every node of a job must have the same architecture"
  (`git show v0.1.0:docs/release-notes/0.1.0.md`, :52-57). 0.2's note keeps that frame and adds ",
  and run the same osoe" (`docs/release-notes/0.2.0.md:167-172`), a clause with no README line
  behind it.

So there is no precedent either way, and no record that the omission was chosen.

### 4. Severity: should a missing sentence whose substance is in the note come before the tag?

**For *minor*** (each *documented* or *observed in source*):

- **The note says it, at the moment most mixes happen**, an upgrade (0.2.0.md:91-96). The tag links
  the note from the README's Status (`docs/release-checklist.md:149-152`).
- **Installing states the requirement** (section 1).
- **It fails safe.** The job never forms, so nothing is misread; no layout crosses between nodes
  (the fact-check, :222-227).
- **An MPI programmer expects** one library release per job.
- **Its one route is node-local installs out of step**, or node images:
  - `srun` runs one path on every node (README:425-426), and a program's run path is its prefix.
  - So a program built against a prefix left at 0.1.0 is a 0.1.0 job on every node, unless that
    prefix differs between nodes.
  - The finding's third scenario is therefore its first, not a third route.

**For *fix before release*, which I find decisive:**

- **As drafted, the tag's two documents disagree.** The note says the README's Limits carry "run
  the same osoe" (0.2.0.md:167-172), and they do not. The checklist's note item, "made true of the
  tree tagged" (`docs/release-checklist.md:143-148`), has to change one of them before the tag
  anyway.
- **The README sets a wrong expectation**, not just a gap: the architecture item and §3.13's "clear
  message" (section 1).
- **The README's own audience is who meets it.**
  - The README offers "the same install on each" for clusters without a shared file system, such as
    boards that each boot from their own card.
  - A node left at 0.1.0, or reimaged later, makes every job that lands on it wait, and the README
    sends its user to firewalls and port ranges.
  - The note helps at the upgrade, not a month later.
- **This review's precedent**: round seven kept a one-sentence README fix at *fix before release*
  through its refutation (`docs/reviews/archive/v0.2-step1-review.md:52-64`, :189-192).
- **The cost** is a sentence or two, and the tag waits for Part 4 regardless.

So *fix before release* holds, as a documentation gate and not a code change. The lead should not
weigh it as more than that.

### 5. The fix, amended

- **Put it in the architecture item (README:1068), as the note's own line has it**: "Every node of a
  job must have the same architecture, and run the same osoe." Then qualify the item's comparison:
  - Two builds of one release that differ are refused by name ("the nodes are running different
    binaries").
  - Nodes of releases whose hellos differ, 0.1.0 and 0.2, do not recognize each other's hello. The
    start waits, its notices saying "no answer to the hello", until `OSOE_NO_PROGRESS_TIMEOUT`, the
    launcher, or under `srun` the step's time limit ends it.
  - `SHMEM_VERSION=1` shows each node's release.

  A separate Launching entry, as the investigator proposes, would leave the comparison list
  implying the opposite.
- **In "How a job starts"** (README:1669-1671), where the README lists "no answer to the hello":
  say that it is also what a node of another release gets. A user who searches the README for the
  notice's words lands there, not in Limits.
- **In "When a job fails or hangs"**: half a line under "A start that waits" (:558-561), as the
  investigator proposes.
- **The code, after release, as the investigator has it** (their Q5-8): a listener that meets a
  hello of this job and step but another version could name both versions. Done before the tag, it
  would help in one direction only:
  - 0.1.0's listener cannot change;
  - in a job of two nodes with 0.1.0 at node 0, no 0.2 listener ever sees a 0.1.0 hello.
- **The least the tag needs**, if the author wants no README change: drop "and run the same osoe"
  from the note's Known limits. That leaves the architecture item's implication in place, so the
  README sentence is the better fix.
