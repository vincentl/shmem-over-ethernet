## Verdict

**Nothing fatal.** The fallback is right on every path I traced:

- a refusal with `IORING_CQE_F_MORE`, and one without;
- a refusal behind notifications the buffer's earlier parts still owe;
- the copy's completion before the refused send's notification has come;
- the abort, and a peer's reset;
- a refusal that comes at submission, as the Pi's 6.18 gives it, rather than at issue, as 6.12 and
  6.14 do (finding 2; by my trace, not a run).

The stream cannot lose or repeat a byte. No buffer is written while the kernel may read it. No pass
waits for work that nothing brings.

**Four findings are rated *should fix*.**

1. **The two refused tests skip under AddressSanitizer and ThreadSanitizer.** The sanitizers' runtimes
   make `mlock` return 0 without locking, so `osoe_test_no_locked_memory` takes every process for one
   with `CAP_IPC_LOCK`. The skip line then names that capability.
2. **The record's Pi pass of the refused internode test is not in its evidence.**
   - The cited directory holds the failing first build.
   - The Pi's 6.18 refuses at submission, which stops the submission at that entry. That path through
     the engine is in no saved run.
3. **The model never checks BOTH LENT for a refusal.** With the check on, the refusal holds, but the
   main two-writer case passes the liveness cap and loses its liveness check.
4. **No test holds the same-pass re-offer, the first read's finding 3.** The lead's mutant that offers
   the bytes again only at a later pass passes both tests.

Eight notes follow. The one closest to a finding is N2: the model's new x86-TSO case runs in 506 s
against the engine's 600 s limit.

### Should fix

**1. The refused tests skip under AddressSanitizer and ThreadSanitizer: their runtimes make `mlock`
succeed without locking, and the skip line blames `CAP_IPC_LOCK`** (*observed in source* in compiler-rt
and GCC's libsanitizer; the runtime's string *observed* on the Mac; older GCC releases *recalled*; not
run in either preset).

- **Where**:
  - `shmem/tests/locked-memory.h:37-44`, the probe. The decisive line is `:40`:
    `bool locked = mlock(p, (size_t)page) == 0;`.
  - The callers: `shmem/tests/test-wire.c:344` and `shmem/tests/test-internode.c:127`.
  - The skips: `shmem/tests/CMakeLists.txt:281` and `:1433`.

  - The wire's test is registered in both presets (`:279-282`, under `OSOE_INTERNODE` alone). The
    internode test is registered in the asan preset (`:1420`).
- **What, the interceptor**:
  - compiler-rt's common interceptors define `mlock` (and `munlock`, `mlockall`, `munlockall`) as
    `INTERCEPTOR(int, mlock, ...) { MlockIsUnsupported(); return 0; }`.
  - The comment above it: "Linux kernel has a bug that leads to kernel deadlock if a process maps TBs
    of memory and then calls mlock()".
  - The kernel is never called.
  - `INIT_MLOCKX` is in `InitializeCommonInterceptors`, which both runtimes install.
  - `SANITIZER_INTERCEPT_MLOCKX` is `SI_POSIX` in LLVM's tree and in GCC's libsanitizer alike.
  - The Mac's `libclang_rt.asan_osx_dynamic.dylib` and `libclang_rt.tsan_osx_dynamic.dylib` both carry
    its message, "%s ignores mlock/mlockall/munlock/munlockall".
- **What, the effect**: in those presets the probe's `mlock` succeeds with the limit at nothing, so
  `osoe_test_no_locked_memory` returns false.
  - `shmem.wire.zero-copy-refused` prints "SKIPPED: this process may lock memory whatever its limit
    (CAP_IPC_LOCK)" and returns. This happens in asan and in tsan.
  - `shmem.internode.zero-copy-refused.0-1-2`, in asan, follows a longer path:
    - each PE has already lowered its limit when the probe answers;
    - the reduce's own sends by reference are refused, and each node's notice prints;
    - the max-reduce then says skip, PE 0 prints the skip line, and every PE finalizes;
    - ctest reports the test skipped, since it checks the SKIP expression before the PASS one
      (CMake's order, *recalled*).
- **Why it matters**:
  - In two of the four presets neither test does what it is registered to do. The wire's counts and
    the engine's refusal path run in debug and release alone. AddressSanitizer is the preset that
    poisons the provided buffers, and the one that would see a lent buffer misused.
  - The skip line blames a capability the process does not have.
  - The verification scripts look for "tests passed", "(Failed)" and "(Timeout)" (`verify-final.sh:20`,
    `verify-keepalive-final.sh:31` and the like), so a skip reads as green there.
  - The record's verification was in the release preset alone (`zero-copy-refused-check.sh` builds
    `--preset release`), so no run has met this yet.
- **Fix**:
  - Probe with the system call, which no sanitizer intercepts: `syscall(SYS_mlock, p, (size_t)page) == 0`,
    and `SYS_munlock` after.
  - That keeps io_uring's own criterion:
    - io_uring charges unless `ns_capable_noaudit(&init_user_ns, CAP_IPC_LOCK)` (`io_uring_create`,
      v6.14, *observed in source*);
    - `mlock` with the limit at nothing succeeds only with `capable(CAP_IPC_LOCK)`, which asks the same
      initial namespace (`can_do_mlock`, *recalled*).
  - Do not read `/proc/self/status`'s `CapEff` instead. It reports the process's own user namespace:
    root in a rootless container has the capability there, and io_uring still charges it.
  - Then run both tests once in asan and tsan, and have the presets' verification look for "Skipped".

## What is sound

- **The refusal's count.**
  - `F_MORE` is counted (`ring.c:269-275`) before the refusal is handled (`:276`).
  - At v6.18, `io_sendrecv_fail` sets `F_MORE` on a failed send by reference whenever
    `REQ_F_NEED_CLEANUP` is set. Prep sets that flag before it takes the charge, and
    `io_send_zc_cleanup` flushes the notification (*observed in source*).
  - The completion is posted before the request is freed, and the notification comes from that free
    (*recalled*). So owed goes up before it comes down, and the fatal for a notification that "owed
    none" (`:260-262`) cannot fire.
  - A refusal without `F_MORE` - the notification's allocation failed - owes nothing and gets nothing.
- **Nothing moved.**
  - The charge comes before `sock_sendmsg`: at issue on 6.12 and 6.14, at prep on 6.18.
  - `done_io` grows only under `MSG_WAITALL`, which this library never sets.
  - So `-ENOMEM` means nothing was taken, and the bytes are offered again from where they were:
    - `flush` re-offers `base + c->sent` (`progress.c:1243`);
    - `flush_aborting` re-offers the same pointer, by copy (`:1151`).
- **The wire freed, and the same pass.**
  - With `sending` false and `sent` -1, `send_from` starts a copy, since `zero_copy` is false
    (`wire.c:305`), and returns 0.
  - The copy is submitted at the pass's end (`progress.c:1850`), or by the idle wait's own submit, and
    its completion ends the wait.
  - The wire is visited in that pass even without the mark, since `c->sending` keeps its busy bit
    (`:1669`).
  - The mark makes `receive` run on a wire with nothing queued. That receive peeks nothing and excuses
    or judges nothing new (`:841-869`).
- **At most one buffer lent.**
  - The refused send went by reference only while the other buffer owed nothing (`wire.c:305-306`).
    That buffer had been released at the top of the same `flush` (`progress.c:1232-1237`), since owed
    counts change only at the reap.
  - The wire never lends again, so BOTH LENT (`:1257-1259`) cannot arise.
  - The refused buffer is LENT until its notifications come, busy meanwhile (`:1672`), and released at
    owed 0.
- **The queues' bounds.**
  - A refusal costs one completion and one notification, within the 16 a lending wire is allowed.
  - Entries left in the submission queue by 6.18's stopped submissions cannot pass its size, however
    the submits go:
    - each wire has at most one send outstanding (`sending` runs from the entry's preparation to its
      completion);
    - each wire has at most one re-arm outstanding;
    - the ring has at most one futex wait.
  - A stopped submit returns at once in liburing's wait, with a completion to reap (*recalled* for
    liburing's loop).
- **The rest of the reap.**
  - A peer's reset during the copy is handled.
  - A receive failure is handled.
  - Control wires never lend (`wire.c:175`).
  - A copied send's `-ENOMEM` is still the connection's failure (`ring.c:304-312`).
  - The once-flag:
    - a file-scope `_Atomic bool` with a `seq_cst` exchange, in the tree's style for process-private
      atomics;
    - it passed the static checks, 12 of 12 in the lead's run;
    - `publish_ring`'s early return cannot skip a refusal, since a refusal is a completion.
- **The messages.**
  - `locked_memory_note` adds the limit only on `-ENOMEM` with a finite limit.
  - Their buffers hold them: 192 bytes, 160, and the caller's 512 (`transport-am.c`).
  - The start-up check's errno is positive and `ring.c`'s negative, and each is compared with its own
    sign.
- **The kernel claims** (*observed in source*):
  - **The charge.** It is `(len >> PAGE_SHIFT) + 2` pages (v6.18 `notif.h`), on `user->locked_vm`,
    against `rlimit(RLIMIT_MEMLOCK) >> PAGE_SHIFT`, refused with `-ENOMEM` (v6.18 `rsrc.c`).
  - **No `-ENOBUFS`.** No send by reference's path returns it (v6.18 `net.c`).
  - **The notification.** It says copied when the kernel did not lend (`zc_report && (zc_copied ||
    !zc_used)`, v6.18 `notif.c`). So a refused send's notification counts as copied, as the README says.
  - **Rings from 6.14.** At v6.14, `io_allocate_scq_urings` makes the rings with `io_create_region`,
    which calls `__io_account_mem` under `ctx->user` before it allocates (`memmap.c`). At v6.13 the
    rings came from `io_pages_map`, with no charge.
  - **`CAP_IPC_LOCK`.** `ctx->user` is set only without it (v6.14).
- **The tests' design.**
  - A limit of nothing lowered after the rings refuses every send by reference on every kernel: the
    page limit 0 is below 2 pages.
  - The wire's test counts exactly two refusals and pins the end of lending; the keeps-lending mutant
    fails it (*measured* by the lead).
  - "left behind" is in the FAIL list.
  - The internode test is out of ThreadSanitizer. The wire's test has one thread.
  - Both registrations are inside `OSOE_INTERNODE`, so the single-node build registers neither.
- **The limit drop.**
  - Every ring is made in `shmem_init` (`progress-host.c`, `osoe_wires_open`), and enabling one
    charges nothing.
  - The limit is the process's, read at each charge. So a race with the lead's agent or its helpers
    moves only which send is refused first. The sends that `shmem_init` itself lent were charged under
    the old limit and are given back at their notifications.
- **The reduce at the start of `test-internode.c`.**
  - `deferred_at_init` is read after the block (`:141`), so the reduce's deferred wakes stay out of
    `put_signal`'s count (`:387`).
  - The dirty-peer checks take a total and a difference, and are unaffected.
  - The freed block becomes the inbox's.
  - The skip is agreed by a max-reduce, so the PEs end alike.
  - The flags are on the heap.
- **The model's old cases are unchanged** (*measured*). The eight `zero_copy` cases and the four
  breakage cases have the states and depths of the committed run of 2026-10-08
  (`docs/design/evidence/v0.2-step4/2026-10-08-zero-copy/reservation-model-full.txt`) to the state,
  for example 1,229,467 and 4,199,187.
- **The refusal in the model is the C's**, where it is checked:
  - nothing moves, and the rest goes again from `first`;
  - owed and the pending notification rise together, and the kernel posts that notification before or
    after the buffer's earlier parts';
  - `nolend` stops lending for the connection, so there is one refusal a connection;
  - a refusal is offered only where the C would send by reference;
  - `zc_refused_owes_none` fails the way the C would corrupt: the refused notification takes an
    earlier part's place, and the buffer is released and written again.
