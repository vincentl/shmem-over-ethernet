## Verdict

**Tag after the named changes - all three made the same day. Nothing blocks.**

- **Correctness**: correct as far as the investigator could run and read. P1 held on three to
  eight nodes in 108 runs, beyond its model's two - goodbye orders forced, a node outranked through
  a third's adopted word, helpers on, off and differing by node, data wires on demand, every PE
  streaming, an abort mid-connect, every PE of eight nodes calling - one rank nonzero each time,
  nobody killed. Its three rule breakages the record's C mutants had not built are each caught by
  P1's tests. All 52 model runs the build registers pass, every breakage failing; the internode
  suite 633 of 633 beside four busy loops.
- **Conformance**: OpenSHMEM 1.6 as far as the changes reach, and the README's Limits true of the
  tree. The SOS suite with the collectives' check on by default, which no SOS run before had: 161
  of 165 on every map, the two refused programs each undefined behaviour. The check compares only
  what the specification requires alike, and cannot fail a conforming program - a threaded probe
  of six teams at once 18 of 18, its mutant caught.
- **Scale and performance**: the scaling table matches the code at hundreds of nodes of 256 PEs;
  nothing added since round nine grows with the job's PE count. Every fast-link number the README
  and the release note quote traces to its record and raw output, but one (S1).
- **Portability and readiness**: it runs where round nine said; 19 bad values of the new settings
  refused by name; mixed releases refused at once; ready to be public after the release note and
  the evidence's names.

## The changes made before the tag, ranked

### 1. The account names in tracked evidence (PR10-2, portability and readiness; confirmed, fixed)

The 2026-10-12 tsan reports' tarball held, 2,926 times, a home path whose name is the cluster's
OS Login name - which spells the author's address; 34 files of B10's evidence and the kit's dry
run's `pack.log` named the VM's account. Every audit since had been a text grep, which reads no
compressed file. Fixed in `f5cbc2fc`: each written `<user>`, the tarball rebuilt, and every
tracked file scanned with compressed ones read through, the old tarball the scan's control - no
name left but the 2026-10-04 decision's own line on the commits' address. **The files are still
in the history `origin` holds**: rewriting it, or keeping it, is the author's.

### 2. The release note, false of the tree in seven places (PR10-1, portability and readiness; C2, conformance; fixed)

Unmarked "at the tag", so the tag's pass would have kept them: the headers "byte for byte"
0.1.0's (B3 and B4 changed them, not the ABI); "tested on aarch64 only" (three sessions ran natively
on x86-64); the landing zone's default before P32; the settings' counts; its frame of a Part 4 still
to come and two review rounds; what a user meets since `5748c97` - the data wires on demand, the
mesh's ports, `collect`'s places, P4, P32 - absent; and "after its handlers" for an outranked
node, whose callers an earlier goodbye outruns more often than not. Fixed in the documents'
commit; X1 fills the "at the tag" numbers from the tag's runs.

### 3. Träff's past 512 nodes quoted at the old window (S1, scale and performance; confirmed, fixed)

The README and design §5.8 said a 1 MiB reduction is 3.2 to 4.3 times faster by Träff's past 512
nodes, 2.7 to 2.9 by the simulation - true at the window of 4, the default until P37. At the
default of 8 the lead's run of the model's own functions gives the simulation's best tree 22,265
µs against Träff's 18,712 on 513 nodes, and 21,564 against 18,331 on 1,024: 1.19 and 1.18 times;
the closed form 2.05 to 2.47. The model's checks were pinned at 4, so nothing failed. Fixed: the
checks of the choice at the default (`e42db9c2`, the bound 1.1 times where it was twice; the model
passing, every broken variant failing), and the numbers in the README and §5.8.
