## Findings

### S1. The application thread sets an option on sockets the design says only the agent owns

**Severity: should-fix** (the rules as written; no runtime hazard found).

Scenario:
1. `shmem_init` starts the lead's agent (`init.c:377`), measures the link through it
   (`init.c:431`), then calls `osoe_transport_link` (`init.c:437`) on the lead's
   application thread.
2. That thread runs `osoe_progress_host_cap_unsent` (`progress-host.c:670-676`), which calls
   `setsockopt(TCP_NOTSENT_LOWAT)` on every wire (`wire.c:215`) while the agent submits sends
   on the same sockets.

Evidence: invariant 19 (design line 7863) - "Only the local lead's agent submits, and it
alone owns rings and sockets." §3.12 (design 1272-1274) - "The lead's agent owns the node's
network state: every io_uring ring, every node-pair socket"; and (1292-1294) "Application
threads never submit. They ... ask the lead for everything else". `wire.h:34-35` - "Only
the node's lead touches a wire (§3.12, invariant 19), on the thread that drives the ring."
The new §3.3 paragraph (design 371-378) and `wire.h:126-133` say the opposite of those three
for this one option. The step 4 brief's adversarial-read rule, "every structure has one
owner", reads the same way: the socket is the agent's.

Refutation tried, and it holds - there is no race today:
- `fd` and `peer` are written only by `osoe_wire_attach` inside `osoe_wires_open`
  (`progress-host.c:485`), on this same thread, before `pthread_create`; the only other
  write of `fd` is `osoe_wire_close` (`wire.c:285-290`) from `close_connections`
  (`progress-host.c:599`), which runs in the agent's exit, reached only after
  `stop_requested` (`agent.c:186`, `:252`), which only `shmem_finalize` sets (`init.c:493`).
  The agent's abort path (`agent.c:211-216`) ends the process without closing a wire.
  So no closed or reused descriptor can be reached, and the agent writes only other members
  of `struct osoe_wire` - distinct memory locations, no C11 race, nothing for TSan.
- In the kernel, `TCP_NOTSENT_LOWAT` is one word, written with `WRITE_ONCE` in
  `do_tcp_setsockopt` under the socket lock that `tcp_sendmsg` also holds, and read with
  `READ_ONCE` in `tcp_notsent_lowat()`; the option's `sk_write_space` call can only wake the
  agent's armed poll, whose task work runs on the submitting task, the agent. Set mid-send,
  a send in progress meets the new value at its next new skb at the latest; nothing it has
  copied is affected.

So the defect is that a load-bearing invariant is now false as stated, and step 4's next
parts make it matter: once helper threads own the data wires (proposal §3), an application
thread setting options on them crosses owners that may attach or close wires on their own
schedule.

Fix, either:
- (preferred, and what helpers will need) the application thread publishes the cap - a
  request word in `osoe_am`, release store, then the agent's wake - and the owner applies it
  on its next pass and says it under `SHMEM_DEBUG` (which also makes the debug line report
  what was set, see S2); or
- amend invariant 19, §3.12 and `wire.h:34-35` to name the exception and why it is safe
  (written once before the agent exists, closed only after it is joined, serialized by the
  kernel). `wire.h:129-132` should also say it reads `peer`, not only `fd`.

### S2. `shmem.unsent.*` passes against a lead that capped no socket

**Severity: should-fix** (a check that cannot fail on the property it is named for).

Scenario:
1. A later change - helpers attaching their wires on their own threads, a slot renumbering, a
   loop bound by another count - leaves some or all wires with `fd < 0`, or out of the loop,
   when `osoe_transport_link` runs.
2. `osoe_wire_cap_unsent` returns silently for `fd < 0` (`wire.c:212`).
3. `osoe_internode_backend_link` prints "caps each connection's unsent bytes at N" whatever
   happened (`transport-internode.c:281-291`): the line reports the arithmetic, not the
   sockets.
4. `unsent.sh` (lines 40-54) counts and compares the lines only. Every case stays green.

Evidence: `unsent.sh` driven by a fake launcher that only prints the expected lines, with no
socket anywhere, prints `UNSENT OK` in all seven modes (measured, set, floor, fixed, by-hand,
none, one-node); `test-wire.c`'s `unsent_cap` does check the option with `getsockopt`, but on
one socket in one process, not on a lead's wires. CLAUDE.md's audit rule is the same lesson:
check that the check can find what you know is there.

Fix: at this point every wire is open by construction, so a negative `fd` is a defect: make
it a fatal by name, or count the wires actually capped (read back with `getsockopt`) and
print the count - "node 1 caps its 2 connections' unsent bytes at 16384" - and have
`unsent.sh` require `nodes - 1`. A `node.am.unsent_cap` metric would give `osoe-stat` the
same (§3.14).

### S3. The STREAM pin's comment claims a protocol the new numbers were not measured under

**Severity: should-fix** (question 7: the placement is right, the comment is not wholly
true, and the margin the project's own runs need is unmeasured).

Placement: 0.3 sits at the geometric middle of the two medians measured -
sqrt(0.164 x 0.581) = 0.309 - 1.94 times below the healthy low (0.581) and 1.83 times above
the poll's high (0.164). The figures match the evidence: `floor-tip-pairs.txt` 0.581, 0.610,
0.649; `tip-against-first-rung.txt` 0.659, 0.666, 0.661 and the poll 0.162, 0.161, 0.164.

Scenario for a false failure:
1. `test-floor.c:23-25` says each pin is the median "from twelve runs - four idle, four
   beside a `ctest -j4`, four under 16 busy loops on four CPUs - and nine with step 2's
   poll", and the STREAM bullet (`:34-42`) gives 0.58-0.67 and 0.161-0.164 under that
   sentence. The evidence holds six healthy runs and three poll runs from `tip-measure.sh`
   and `floor-tip-pairs.txt`, taken under the VM lock with nothing recorded beside them;
   none is labelled beside a `ctest -j4` or under the busy loops. Design §8.4 (line
   7644) gives the same numbers without the protocol.
2. The project's verification runs the release preset with `OSOE_TEST_PINS=ON`, where
   `shmem.floor` runs beside the suite.
3. History says load moves this ratio a long way: at the old default the protocol's healthy
   range was 0.21-0.43 (low/high 0.49), and a healthy run beside a parallel test run in a
   fresh VM measured 0.0999 against a pin of 0.10 (`test-floor.c:55-57`), 0.48 of that
   range's low. The same relative drop from 0.58 is about 0.28, under 0.3.

Refutation tried: at the new default a writer waits once every 256 KiB (`test-floor.c:36`),
where before step 4 it waited every 64 to 128 KiB, so its ratio should move less with load;
and the first rung measured 0.39 at its lowest pair beside the suite against medians of
0.43-0.47. Plausible, but not measured at the tip, and the
comment says it was. On a shaped link (tier 3, same pin) the ratio was 1.00 and the cap
should not move it, so the risk is tier 2 only.

Fix: run the stated protocol at the tip (four beside `ctest -j4`, four under the 16 busy
loops; the poll's under load will only fall) and set the pin from it; or keep 0.3 and make
the comment say what 0.58-0.67 came from (six runs, VM otherwise idle) and that the loaded
runs are owed.

### N1. Under `OSOE_COLLECTIVE_SHAPE=fixed` the cap is 16 KiB whatever the link, and a hand-set bandwidth is ignored

**Severity: note** (the author decided `fixed` gives the floor, 2026-10-07.md item 11).

`osoe_link_establish` returns under `fixed` before it looks at `OSOE_LINK_*`
(`link-measure.c:229`), so `init.c:437` passes 0 and the cap is the floor even when the user
gave the bandwidth by hand - which item 11 also promises to use ("from the hand-set bandwidth
where the OSOE_LINK_* settings give it"); the code resolves the overlap toward 16 KiB. At a
gigabit 16 KiB is right. At 10 GbE it drains in 13 us and Linux wakes the sender at half of
it (6.5 us), where the 128 us rule gives 160,000 bytes; at 25 GbE 400,000. A user who fixes the
shape on a fast link silently gets a throttled point-to-point stream, and only
`OSOE_WIRE_UNSENT_BYTES` undoes it. Suggest: under `fixed`, the hand-set bandwidth if given,
else no cap (today's behaviour) - or say it in the README's row.

### N2. `OSOE_WIRE_UNSENT_BYTES` is the lead's alone, and not agreed

**Severity: note.** Every PE reads and checks it (`wire-settings.c:49-63`), only each lead
uses it (`progress-host.c:672`): a value given to a non-lead PE (`-e 1:...`) is accepted and
ignored, and nodes may differ. Neither affects correctness - each lead caps only its own
sending side, and nothing chosen from the link reads the cap - and it matches the other
`OSOE_WIRE_*` settings, so agreement is not needed. Worth one sentence in the README's row:
"read by each node's lead; nodes need not agree."

### N3. "0 for none" means the system's default, and "start-up ran uncapped" assumes it

**Severity: note.** A per-socket value of 0 is what `tcp_notsent_lowat()` replaces with
`net.ipv4.tcp_notsent_lowat`, UINT_MAX by default; a site that has tuned that sysctl down
(16 KiB is a published web-server setting) caps every wire already, so the link measurement does not see
"the link as it is" (`init.c:434-436`) and `OSOE_WIRE_UNSENT_BYTES=0` does not uncap, though
the debug line says "uncapped" (`transport-internode.c:289`). If it matters: set `INT_MAX` at
attach (truly uncapped for the measurement) and for 0.

### N4. No refusal test for a bad `OSOE_WIRE_UNSENT_BYTES`

**Severity: note.** The settings sweep (`shmem/tests/CMakeLists.txt:801-824`) covers
`OSOE_WIRE_BYTES` but not the new variable; neither the "is not a byte count" branch nor the
new "is more than 1073741824 bytes" branch (`wire-settings.c:53-55`) is run by any test. Two
lines in the sweep: `abc`, and `1073741825`.

### N5. A by-hand value below the floor is taken as given

**Severity: note.** `OSOE_WIRE_UNSENT_BYTES=1` is accepted (`wire-settings.c:79-80` returns it
unclamped). With a lowat of 1 a send admits one skb only when nothing is unsent, and the
poll fires only at none; on a link without segmentation offload (tier 3 turns them off) that
is one MSS per acknowledgement, and with one segment in flight the peer's delayed ACK can hold
each for tens of milliseconds. Nothing hangs, but a user can make a link crawl with a small
number; suggest refusing values between 1 and the floor, or clamping to it.

### N6. An abortive goodbye to a peer stalled past the grace now stays in the library

**Severity: note** (edge case; same class of outcome).

1. Node A streams to node B; B's lead process is stalled (stopped, swapped) with its
   receive window shut.
2. A PE on A aborts. A's agent must finish the segment on the wire before the abortive
   goodbye (`flush_aborting`, `progress.c:924-964`).
3. Uncapped, the kernel held megabytes, so the whole segment and usually the goodbye were in
   A's socket; after the 10 s grace (`abort.h:68`) A exits, and its orphaned socket can still
   deliver them if B resumes. Capped, at most the cap plus one skb is in the kernel; the rest
   of the segment and the goodbye die with A.
4. B, resumed, reads a stream that ends mid-segment: "node A's stream ended in the middle of a
   segment: its lead has exited or died mid-send" (`progress.c:686-687`), and ends with that
   failure rather than the job's abort status.

The job ends either way, and design §3.15 already accepts "a peer told nothing takes its end
of stream for a death"; recorded so the abort record knows the cap made it likelier.

### N7. The cap is soft by up to one skb, which the comments call "at most"

**Severity: note.** `tcp_sendmsg_locked` checks `sk_stream_memory_free` only when it starts a
new skb and appends to the tail skb up to `size_goal` unchecked, so the kernel can hold the
cap plus one skb - about 64 KiB more with TSO/GSO on, an MSS without. The Pi's 3.3-3.9 ms
already includes it; only the wording is off: design 371-372 "may hold at most the link's
bandwidth times 128 µs", `wire-settings.h:33-41`. Suggest "about".

### N8. A node's `/dev/shm` room check now asks twice as much at the default

**Severity: note** (expected; for the README's memory rows). `connection-area.c:211-218`
compares the whole area with `/dev/shm`'s free space before a byte is touched: at 500 nodes
249.5 MiB a node where it was 124.75, so a small `/dev/shm` (a container's 64 MiB default)
refuses at about half the node count it did. The 8 GiB test VM is fine: 64 and 70 logical
nodes make 2,016 and 2,415 MiB of sparse objects, resident only where traffic fills buffers
(at most 512 KiB a used connection), and the sanitizers skip those counts already
(`CMakeLists.txt` shape and circulant loops).

### N9. Smaller items

- `test-am-size.c:98` checks `chosen == standard` where `chosen` comes from the 500-node call
  at `:87`, not from 2,049 nodes; the loop at `:79-84` does check 2,049, so the line is a
  harmless leftover of the old pattern. Calling `osoe_am_choose_buffer(..., 2049, ...)`
  there would make the boundary explicit.
- `wire-settings.c:81-83`: the product cannot overflow only because both sources clamp to
  `OSOE_LINK_BYTES_PER_SECOND_HIGHEST`; a `_Static_assert(OSOE_LINK_BYTES_PER_SECOND_HIGHEST
  <= UINT64_MAX / OSOE_WIRE_UNSENT_NS, ...)` beside it keeps that true when either moves.
- Short writes are now routine, and `flush` takes a short write's count on one pass and
  submits the rest on the next (`progress.c:1009-1033`; `osoe_wire_send` submits only for a
  new pointer). A pass is microseconds against the 128 µs budget, so this costs nothing on a
  gigabit; on fast links, offering the remainder in the same visit saves a pass per refill.
- Naming: `osoe_wire_cap_unsent` and `osoe_progress_host_cap_unsent` use "cap" as the verb,
  which is a word; CLAUDE.md's counter-example is `cap` for `capacity`, so a reader may pause.
  "limit" would not.

## The seven properties, as tried

**1. No hang, loss, reordering or fatal from the cap - held.**
- Linux since 2019 ("tcp: reduce POLLOUT events caused by TCP_NOTSENT_LOWAT", so every
  kernel osoe's futex2 floor admits): `sendmsg` starts a new skb only while unsent < lowat;
  `tcp_poll` reports EPOLLOUT only while unsent < lowat/2 and the send buffer has a third free. A nonblocking attempt over the cap
  returns the bytes it copied, or -EAGAIN having copied none; never 0.
- io_uring `IORING_OP_SEND` without `MSG_WAITALL` (`wire.c:194` passes `MSG_NOSIGNAL` only):
  a positive short count completes the request, which `ring.c:191-205` records and
  `osoe_wire_send` returns (`wire.c:174-186`); -EAGAIN under `IO_URING_F_NONBLOCK` arms an
  EPOLLOUT poll and retries in task work on the agent. -EAGAIN reaches user space only for
  `REQ_F_NOWAIT`, which only `MSG_DONTWAIT` sets. If a poll cannot be armed the request goes
  to io-wq as a blocking send, and the wires are blocking (`listener.c:506`, `:679` clear
  `O_NONBLOCK`) with no `SO_SNDTIMEO`, so it waits. Were -EAGAIN ever to arrive it would be
  `w->error` and a fatal (`ring.c:197-199`, `wire.c:170-171`); no path delivers it.
- No livelock: the retry follows EPOLLOUT at unsent < lowat/2, which is below the sendmsg
  test, and only this request writes to the socket (one send in flight, invariant 2), so it
  copies at least one skb. No lost wake: `tcp_poll` registers then rechecks (its "race
  breaker"); the wakes come from `tcp_check_space` on every ACK, after
  `tcp_push_pending_frames` has moved more bytes from unsent to in flight.
- Order and loss: the library re-offers `base + c->sent` (`progress.c:1009-1033`); `busy()`
  keeps a connection with a send in flight in every pass (`progress.c:1180-1188`), and the
  agent's ring wait returns on the send's completion. Kernel short writes were rare before
  (`OSOE_WIRE_SPLIT` truncates the submission instead) and are now routine, on the same code;
  `shmem.wire` now streams over a 64 KiB-capped socket in one direction.
- A peer that stops reading: the cap is reached sooner than a full send buffer was, which is
  the same state - a stopped peer is waited for (§3.15); `osoe_wire_silent_ms` reads 0 under
  zero-window probing, as before. Keepalive probes only with nothing in flight and nothing
  unsent, as before.
- Close and abort: `shutdown(SHUT_WR)` follows the last accepted byte of the goodbye
  (`progress.c` flush and `flush_aborting`), never a pending send; `close_connections` closes
  after the peer's end of stream with nothing unread, so no reset; `osoe_progress_aborted`'s
  `SIOCOUTQ` counts unsent bytes too. N6 is the one difference.
- The deadlock detector: `osoe_progress_quiet` (`progress.c:1465-1482`) needs the peer's
  application acknowledgement of every application segment, so bytes the kernel holds were
  never counted as delivered; `osoe_progress_idle` (`:1307-1333`) counts library state. The
  cap moves bytes from the kernel into the library, which keeps "idle" false longer: fewer
  samples, never a false declaration.

**2. Applied to every wire of every lead, once a session, never to a closed or unopened
descriptor, the same on every node - held** (N1, N2 noted).
- Once: `init.c:437` in `session_start`, after the link (`:431`) and the agent (`:377`); a
  re-init opens a new mesh, measures it uncapped, caps it again.
- Every wire: `osoe_wires_open` attaches all `node_count - 1` wires before the agent starts,
  fatal on any failure (`progress-host.c:455`, `:485`); the loop's bound matches the
  allocation (`:674`). Each end of a connection is capped by its own lead.
- Never closed: see S1's refutation.
- The same number on every node: measured links are the root's (the AND at
  `link-measure.c:269-270`); `OSOE_LINK_*` and `OSOE_COLLECTIVE_SHAPE` are agreed across nodes
  (`rendezvous.c` `agree`) and within one (`node.c:1174-1190`); one node caps nothing.
- Mid-send: see S1's refutation.

**3. Thread safety and ownership - no data race; the rule is broken in letter (S1).**
`osoe_am.wire` is allocated and filled, and the engine attached, before the agent exists.
The application thread reads `osoe_am.lead`, `osoe_am.wire`, `osoe.job.node_count`, and each
wire's `fd` and `peer`, all its own writes from before `pthread_create`.

**4. Arithmetic - held.** `bytes_per_second <= 10^13` from both sources (`bootstrap.c`'s
bounds, `link-measure.c:215-216`), times 128,000 is 1.28 x 10^18 < 2^64; clamped to [16,384,
2^30]; `(int)` of at most 2^30 is exact; 0 gives the floor. Recomputed: 116,000,000 ->
14,848 -> 16,384; 10^9 -> 128,000; 4.44 x 10^9 -> 568,320; 10^13 -> 2^30; the Pi's 116.5 MB/s
-> 14,912 -> 16,384. The static assert in N9 would keep the overflow argument local.

**5. The single-node build and the boundary - held.** `osoe_transport_link` reaches the
backend only when `internode` (`transport-am.c:161-165`), which needs `node_count > 1`, which
`osoe_internode_backend_check` refuses in that build before the node joins; the stub
(`transport-single-node.c`) is unreachable and fatal by name like its siblings. Includes:
`init.c` (API) calls through `transport.h` (on the boundary); `transport-am.c` (below) through
`internode-backend.h` (backend-facing); `transport-internode.c` (internode backend) includes
`wire-settings.h` (on the boundary). No layer list changes, no forbidden include.
`shmem.unsent.one-node.0-0` is registered in the single-node build and expects no line, which
is what it gets.

**6. The 256 KiB default - held** (N8 noted).
- Nothing assumes the default is the floor: the budget halves to the floor and the notice
  (`connection-area.c`) and refusal arithmetic follow (2,049 keep 256 KiB, 2,050-4,097 are
  halved with the lead's notice, 4,098 refused - reproduced); the pre-open drain's half
  (`progress.c:1098`) is a fraction of the buffer; reply-pool sizing (`progress-host.c:453`),
  the landing zone, the provided buffers and the CQ bound are independent of it; the parser
  takes any `total_len`; the head word holds 31 bits against a 1 GiB maximum; the payload
  limit takes the smaller of chunk and room. No `128 << 10`-style constant remains in `shmem/src`,
  `base` or the tools except echo-uring's deliberately kept `SEND_BYTES`.
- Tests that set `OSOE_AM_CHUNK` all set `OSOE_AM_BUFFER` too, so none changes meaning; the two
  refusal tests ask 524,288 now that 262,144 is the default, and each still differs in the
  direction its pattern needs.
- `test-am-size`'s new checks are right (every value recomputed), N9's leftover aside.

**7. The STREAM pin - placed well, comment not wholly true (S3).**

## Verdict

No fatal finding. The cap is applied where the design says, from numbers every node shares,
through code paths that already handled short writes, and nothing in Linux's or io_uring's
handling of `TCP_NOTSENT_LOWAT` can surface as a hang, a lost or reordered byte, or a fatal
on these sockets. The 256 KiB default changes no assumption in the code and its tests are
right.

Before merging: S1 (amend invariant 19, §3.12 and `wire.h`, or move the option to the owner -
the second is what helpers will need), and S2 (make a skipped wire visible - a few lines).
S3 before a verification run with the pins on beside the suite is trusted, or the comment
reworded now. Not seen in the evidence, and worth running with the pins on before the merge:
tier 3 at the tip, the one place the 0.3 pin meets a capped socket on a shaped link (expected
1.00 there, as before).
