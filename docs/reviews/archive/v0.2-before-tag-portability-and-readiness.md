# v0.2 before the tag: will it run elsewhere, and is it ready to be public?

Round ten of osoe's adversarial review (item T13), run 2026-10-30 against `main`
at `5cefc7fb` (the worktree `review-ten`), with
`docs/reviews/adversarial-review-prompt.md`'s fields and the round's common
brief. The question: for what changed since round nine (`3b45472`), will osoe
run elsewhere - other machines, kernels, distributions, Slurm sites, installs -
and is the tree ready to be public: its README, its release note, its failures'
messages and its repository. Round nine's answers in this area
(`v0.2-before-part4-portability.md`, `v0.2-before-part4-readiness.md`) are held
as claims to check. Labels: *documented* (a source says so), *observed in
source*, *measured* (run here, on this tree), *recalled*.

Runs were made in the `osoe` VM (Debian 13, Linux 6.12, aarch64) on a
`git archive` of `5cefc7fb` under `/var/tmp/review-ten-portability-and-readiness/`,
each under the VM's lock: the `release` preset built and installed to a prefix,
the static checks, and the programs below built by the installed `oshcc` and
run by the installed `osoe-launch`. The scripts and programs are in the round's
scratch tree, `<repo>/build/scratch/review-ten/portability-and-readiness/`
(`build.sh`, `diagnose.sh`, `mixed.sh` and `programs/`, with `last.sh`, written
and not run), which git ignores.

## Verdict

**It runs where round nine said it would, and is ready to be public after two
named changes, both an hour's work or less. Nothing blocks.**

- **PR10-1, fix before release (high):** the release note says things untrue
  of this tree - that every installed header is 0.1.0's byte for byte (two
  are not, since 2026-10-12), that osoe is tested on aarch64 only (it has run
  natively on x86-64 three times, as the README says), that the landing zone's
  default is 256 KiB (a node's 4 MiB over its PEs since P32), how many settings
  are new (fourteen and fourteen hooks, where it says eight and three), and it
  implies that the callers of a node another node outranks run their handlers
  (on two nodes, in five runs of six they did not) - and it leaves out the data wires on demand, the mesh's port range, `collect`'s
  places and the two-node choice. The checklist's item to make the note true at
  the tag would not catch most of these, since they are not marked "at the
  tag".
- **PR10-2, fix before release (high in the facts, low in harm):** a tracked
  tarball of the first cluster session's ThreadSanitizer reports names the
  author's Google account, as its OS Login home, 2,926 times, and 34 newer
  evidence files the development VM's account - where `docs/README.md` says
  both were edited out, and the author's rule keeps his address to the commits'
  author lines. Every audit since read text only; 143 compressed files went
  unread.

**What is sound, measured on this tree:** the build, the install and the
interface are 0.1.0's in kind - the soname, the same 3,595 exported names,
weak `shmem_` over strong `pshmem_`, the wrapper's refusals - with no warning;
every bad value of every setting added or changed since round nine, 19 tried,
and every disagreement that must be refused, ends the job at start-up naming
the variable and its range or both sides; the failure modes added since round
nine tell the user what failed - the on-demand wire's 30 s notice names the
node, its address and who should dial, P39's check names both PEs and both
calls, P1's every-PE exit kept the callers' status 42 runs of 42 with no rank
killed, a helper that cannot start is named - and `osoe-stat` finds the one
that hangs; a job mixing round nine's library with this one is refused at once
by name, on a node and between nodes, and each version's `osoe-stat` reads the
other's job; nothing added asks more of a kernel, a C library or a Python than
round nine's tree did; the kit's Slurm forms, binding included, are right and
said; the licence lines and the third-party boundary hold.

**Minor**: PR10-3, three messages that speak the library's words (an on-demand
wait shown as `shmem_put` inside `shmem_init`, the timeout's "turnover", a
reduction's operation by number); PR10-4, drift in the README, `docs/README.md`
and the briefs' index; PR10-5, no x86-64 machine has run anything merged after
the third session's tree, and the cluster is gone.

## Findings, ranked

### PR10-1. The release note says things that are not true of this tree (fix before release; high)

**Where.** `docs/release-notes/0.2.0.md`, lines 3 to 7, 32, 86 to 89, 127,
130 to 136, 226 and 239 to 252.

**What.** The note was drafted on 2026-10-10 against `5748c97` and
fact-checked then (`docs/reviews/archive/v0.2-release-notes-fact-check.md`).
Since, it has been edited piece by piece - P1, P2, P36's default, P37's window
and P39's check went in - so it reads as current, but these sentences are false
of `5cefc7fb` (each *observed in source* or *measured* as given):

1. **"Every installed header is 0.1.0's byte for byte"** (line 32). Two of the
   five installed headers differ from `v0.1.0`'s: `shmem.h` (28 lines added, 15
   removed - comments, and the three-argument forms of `shmem_signal_set`,
   `shmem_signal_add` and the four-argument `shmem_sync` now pass their
   arguments unparenthesized, so that a profiler can define them by their plain
   names) and `shmemx.h` (a comment) - `git diff --stat v0.1.0 HEAD --
   shmem/include`, B3's `52fa7cff` and B4's `7c4ba018`, both 2026-10-12. True
   at round nine (`3b45472`); not since. What the sentence
   is there for still holds (*measured*): the library exports the same 3,595
   names as round nine counted, every `shmem_` name weak and every `pshmem_` one
   strong, under the soname `libosoe.so.0`, and the macro changes alter no
   call a program can make.
2. **"Tested on aarch64 only. x86-64 built and ran under emulation, without an
   x86-64 kernel"** (Known limits, line 239). osoe has run natively on x86-64
   in three sessions on Google Cloud, which the README says at length (lines
   24 to 33, 228 to 235, 1214 to 1225); the note contradicts the README.
3. **The landing zone's default.** "four pieces at the default 256 KiB" (line
   88) and "four pieces of up to 64 KiB in flight at the default 256 KiB"
   (lines 250 to 251). Since P32 (decided 2026-10-12) the default is a node's
   4 MiB split among its PEs, from 1 MiB a PE (sixteen pieces) at 1 to 4 PEs a
   node to 256 KiB from 16 (README's `OSOE_GET_LANDING_BYTES` row; the library's
   own `SHMEM_INFO` text, *measured*: "default a node's 4194304 split among its
   PEs, from 262144 to 1048576 a PE").
4. **"Settings: eleven new ... and three test hooks; five defaults changed"**
   (lines 130 to 136), the eleven being eight settings and three hooks.
   Against `v0.1.0`'s README the new rows are fourteen settings - the eight
   named, and `OSOE_CHECK_COLLECTIVES`, `OSOE_COLLECTIVE_PLACES`,
   `OSOE_MESH_DATA_WIRES`, `OSOE_MESH_PORT_RANGE`, `OSOE_MESH_SLOT` and
   `OSOE_TURNOVER_WAKE`; fifteen with `OSOE_MACHINE_PES`, which `osoe-launch`
   sets - and fourteen test hooks. The defaults
   changed miss `OSOE_GET_LANDING_BYTES` (`262144` in 0.1.0); and a
   collective called differently within a node, undetected in 0.1.0, now ends
   the job by default.
5. **The note's own frame** (lines 3 to 7, 226): "with every change of v0.2
   merged but step 4's last part ... the author holds the tag while more
   hardware - a link above a gigabit, for that last part - may be had" - Part 4
   ran three sessions; "Two rounds of adversarial review, seven and eight" -
   nine has run, and ten is running. The checks section is marked provisional,
   which covers its numbers, not this.
6. **What changed since `5748c97` that a user meets is absent**: the data wires
   on demand (`OSOE_MESH_DATA_WIRES`, H23), the mesh's port range
   (`OSOE_MESH_PORT_RANGE`), `collect`'s three ways to its places
   (`OSOE_COLLECTIVE_PLACES`, A11), the two-node choice between a tree and
   Träff's (P4, which changes which shape - so which floating-point result - a
   two-node job gets), the landing zone from a node's budget (P32), and the
   collectives' check (P24), named only in Known limits.
7. **"a node that learns of a lower caller leaves with 0, after its handlers"**
   (line 127): measured below (PR10-4), the outranked node's callers mostly
   leave without them, as the README's "How a job ends" allows.

**Scenario.** A user upgrading from 0.1.0 reads that x86-64 is untested and
that the headers are unchanged, sizes a get-heavy program's memory by a landing
zone four times smaller than it gets, and does not learn of the six settings and
the on-demand wires at all.

**Why *fix before release*.** The release checklist's item says the note must
be "made true of the tree tagged ... anything merged after `5748c97` added";
these are the sentences that item must not miss, and items 1 to 3 and 7 are not
marked "at the tag", so a pass that fills in the marked numbers leaves them.
Each is a sentence's edit.

### PR10-3. Three failure messages added since round nine speak the library's words, not the user's (minor; high)

All *measured* in `diagnose.sh`, each made to happen:

- **A data wire that cannot be made on demand.** With
  `OSOE_MESH_DATA_WIRES=on-demand` and node 2's lead holding its data wires 45 s
  (`OSOE_TEST_HOLD_DATA_WIRES=2:45000`, three logical nodes), the job waits
  inside `shmem_init` - `osoe-stat` gives PE 0's phase as `mapped` and PE 1
  in `shmem_init` - on the tree's data wires to node 2, which the end of
  `shmem_init` uses (the README's row: it measures the link and hands it out).
  **The 30 s notice is right and clear**: "node 0 has waited 30 s
  for node 2 (127.0.0.3, at 127.0.0.3) to dial their data wire, which it asked
  for on their control wire; still waiting". But `osoe-stat` shows PE 0, whose
  phase is still `mapped`, "blocked in `shmem_put` (data wire to node 2,
  connecting)", and `--summary` the same - in a program whose PE 0 never calls
  `shmem_put` (`transport-internode.c:833` labels every put's wait for room
  `shmem_put`, the library's own puts included; the README says a job hung in
  its start shows each PE waiting in `shmem_init`). Under
  `OSOE_NO_PROGRESS_TIMEOUT=20` it ends with "shmem_put: no progress toward
  node 2 (PE 2) for 20 s (OSOE_NO_PROGRESS_TIMEOUT): the turnover of a
  connection whose data wire is not yet made has stayed at 0" - the node is
  named, and "turnover ... stayed at 0" is the AM layer's bookkeeping where the
  notice's own words would do.
- **Helpers that cannot start** (`ulimit -u` set a few threads above the
  user's count): "cannot start progress helper 1 of 2: Resource temporarily
  unavailable", or "cannot start the agent thread: ...", and the job ends at
  once, each node naming the next. Named, with the error; the limit that gives
  `EAGAIN` there - the user's processes, `ulimit -u` - is not.
- **A collective called differently within a node** (P39, on by default):
  "the PEs of node 0 called different collectives on SHMEM_TEAM_WORLD, or the
  same one with different arguments: PE 1 is in a reduction of 32 bytes
  (operation 5 on elements of kind 0 and 8 bytes) and PE 0 in a broadcast of 32
  bytes from team rank 0 (OSOE_CHECK_COLLECTIVES)" - right, at once, on one node
  and on two, for a different kind, count or root; but the operation and the
  element are numbers from the library's tables, where `sum` and `long` are
  what the user wrote.

None misleads about what failed; each costs a reader a step. After the tag.

### PR10-4. Small drift in the README and docs/README.md (minor; high)

- **"about 1,150"** tests run one at a time by the workflow preset (README
  line 273): the release preset has 1,214 besides the models (`ctest -N`,
  *measured*), the figure the README gives at line 1719.
- **"About 3,800 files"** of evidence (`docs/README.md`), written 2026-10-20
  when they were 3,842: `git ls-files | grep -c '/evidence/'` gives 5,108.
- **"every other caller leaves with 0, usually after its handlers"** (README,
  "How a job ends"). With every PE calling `shmem_global_exit(5)` at once and an
  `atexit` handler that prints, under `osoe-launch` without `-k`: the status was
  5 in all 42 runs, and no rank was killed in the 24 whose every line I kept
  (P1 holds); but 79 of 128 callers' handlers ran over those 24 runs, on the
  maps `0,0,1,1,2,2`, `0,0,1,1` and `0,1,2,0,1,2`; in 6 more on two nodes of two
  PEs, node 1's callers ran theirs in 1, and on one node of two PEs both
  callers' ran in 4 of 6. The README's clause after it - "a caller whose call loses the race
  with another node's end leaves as a PE that did not call" - is what happens;
  "usually" is the wrong word for it, at least on loopback, and the release
  note's "after its handlers" (PR10-1, item 7) more so. A program whose every PE
  calls on an error and relies on its handlers - a trace flushed, a file closed -
  should be told it may lose most of them.
- **The briefs' index** (`docs/prompts/README.md`) says "The open brief sits
  here; every finished one is in `done/`", but the third cluster session's plan
  (`cluster-session-3-plan.md`, run 2026-10-28) and the four cloud sessions'
  briefs of 2026-10-12 and 13 are finished and sit beside the open one, the
  plan with no row in the table; and the open brief's row gives its machines as
  "eight `c2-standard-8`", where the brief itself says `c4-standard-16` (its
  lines 28 to 29), the machines all three sessions ran on.
- **`OSOE_MESH_PORT_RANGE` under `osoe-launch`**: each lead listens on every
  address of the host, so a machine's logical nodes each take one of the
  range's ports; three logical nodes with a range of two end with "node 2 found
  no port of OSOE_MESH_PORT_RANGE=40000-40001 free for its mesh; choose a range
  this host does not use", where the job's own nodes hold them. The row could
  say so.

### PR10-5. No x86-64 machine has run this release's newest work (minor; high)

**Documented**: the third cluster session (`2dd3a623`, 2026-10-28) is the
last x86-64 run of any kind - tier 2 on one node, 1,071 of 1,071, SOS and the
pacer's `mix` across the eight; the first session's (2026-10-12) is the last
with the sanitizers, tier 3 and the single-node build on x86-64; and no suite
that checks results has run across separate x86-64 machines (the README's
Limits say so). After `2dd3a623` came the defaults of
2026-10-28 (helpers `auto`, the window of 8, the check on), P2's room count,
P4 and P1's layout 43 - none on x86-64, natively or under Rosetta, and the
cluster is gone. **Observed in source**: since `2dd3a623` no static assertion
and no architecture-conditional line changed (`base/cacheline.h` is the only
one in the library, unchanged), and layout 43's one new word sits in its
line's padding after the abort word, at 64 bytes as at 128; x86-TSO is the
stronger order, so aarch64's runs are the harder test of the new protocols. So
the risk is small. What is not said: the README's opening and Requirements give
2026-10-12's presets as x86-64's record without naming the tree. The
checklist's x86-64 item (Rosetta and the x86-ordered aarch64 build at the tag)
is what is left; the README's sentence should then say what the tagged tree
did.

## Portability

**x86-64.** *Documented* (`docs/fast-link-results.md`,
`docs/decisions/2026-10-28.md`): the third session, on eight `c4-standard-16`
(Xeon Platinum 8581C, Debian 13, Linux 6.12.113, `gve` at 23 Gbit/s, MTU 8896,
liburing 2.9) at `2dd3a623`, built on all eight without a warning, passed the
probe on every node, started 256 PEs, passed tier 2 on one node - 1,071 of
1,071, logical nodes over loopback, T35's litmus natively for the first time -
built 161 of SOS's 163 programs and passed 159 of the 161 that built at two PEs
a node on eight, and ran the pacer's `mix` across all eight and the plan's
measurements. It did not run the `debug`, `asan` and `tsan` presets, tier 3, the
single-node build or the models; it ran no result-checking suite across
separate machines; and it ran nothing merged after `2dd3a623` (PR10-5). The
first session (2026-10-12, its own tree) is the record for those: debug and
release 871 of 871 at 0, 2 and 3 helpers, ASan 856, TSan 612 with the gate,
tier 3 114, the single-node build 405, the pacer, 27 of the 40 models. The
`osoe-x86` VM was not started: what it can do - compile for x86-64 and run the
single-node build under Rosetta - would test little of what changed since
`2dd3a623` (PR10-5), and the checklist runs it at the tag.

**Kernels.** `tools/probe` since round nine (*observed in source*): an info
line for `IORING_OP_SEND_ZC` (round nine's P9-5) and the unlinked-reopen check
waiting for its child's word rather than 50 ms (T34, with `env.probe.slow-reopen`);
no check added or removed. What the library newly asks of a kernel since round
nine (*observed in source*, every added call searched): `epoll` for the data
wires on demand (`data-wires.c`), `io_uring_prep_poll_add` (5.1), `TCP_INFO`,
`sysconf(_SC_NPROCESSORS_ONLN)` for the helpers' rule, and `stat` of
`/proc/self/ns/pid` for D26 (`base/pid-namespace.c`) - which, where the file is
missing (a kernel without PID namespaces, or no `/proc`), records the
namespace as unknown and skips the comparison rather than refusing or
misjudging. It is silent there: a kernel without PID namespaces cannot split
a node's PEs among them, and a container with no `/proc` is the one case it
would miss. Nothing raises the 6.7 floor or the single-node build's 4.17. A
ring the kernel's `IORING_MAX_ENTRIES` cannot hold is refused by name
with the node count it allows at the helpers' count (`ring.c:89`).
**Locked memory**: Debian 13's hard limit is 8 MiB as well as its soft one
(*measured* in the VM: `ulimit -l` and `-Hl` both 8192 KiB, systemd's
`DefaultLimitMEMLOCK=8M`), so on Debian 13 with a 6.14 or later kernel the
raise of P9-1 gains a login shell nothing; the README says the hard limit is
what counts and an administrator raises it, and gives a Pi's counts (112
logical nodes with no helpers, 56 with two, 42 with three). Under `osoe-launch`
the helpers' `auto` counts the machine's PEs, so a job of more PEs than CPUs
takes none: the counts that matter there are the no-helper ones.

**Slurm.** The kit (*observed in source*, `docs/fast-link/common.sh`): every
job its own `salloc -J osoe-kit -N<n> --exclusive`, whose one step is
`srun -K1 --cpu-bind=none --overcommit` - round nine's P9-2, used through the
third session. Whole-node steps bind no task of one CPU unless asked: the
runbook says so (§5, from the 2026-10-28 measurement in the VM's Slurm) and
the third session's "bound" variant asked (`-K1 --cpu-bind=threads`,
`session-3.sh:86`), each job's allowed CPUs recorded first. The README's advice
(`--cpu-bind=none`, because Slurm binds a task a core "where a node runs as
many tasks as it has cores") is Slurm's automatic binding as I know it
(*recalled*: a step's tasks are bound by default only when their count times
`--cpus-per-task` equals the cores or threads the step has on the node), and its
batch script, which asks no `--exclusive`, is an allocation of exactly its
tasks' CPUs, so the `--cpu-bind=none` it carries is what unbinds it.
`OSOE_PROGRESS_HELPERS=auto` counts the CPUs the machine has online, not the
job's share of them - a shared node, a cgroup's cpuset - which the README's row
says ("whatever share of them the job may use"), with H26's measurement of what
two helpers cost bound to one CPU a PE. Distributions: the README's lists are
round nine's, and nothing since needs a newer C library (every call added
searched against glibc 2.34's, Rocky 9's) or compiler (`shmem.strict-c11`
passes, and the warning flags are unchanged and not errors). All 57 tracked
Python files parse under Python 3.9's grammar (*measured*, `ast.parse(...,
feature_version=(3, 9))`), Rocky 9's Python, and none uses a 3.10 library call
I searched for.

**Build and install** (*measured*). The `release` preset builds without a
warning (GCC 14.2); ten static checks pass (`exports`, `license-lines`,
`memory-orders`, `strict-c11`, `static-link`, `settings-documented`,
`settings-known`, `pass-expressions`, `whole-lines`, `boundary`); `ctest -N`
counts 1,261 tests, 47 of them models, 633 labelled `internode`.
`cmake --install` to a prefix gives `bin/` `oshcc`, `osoe-launch`, `osoe-stat`
and `osoe-pacer`, `include/` `shmem.h`, `shmemx.h`, `pshmem.h` and `mpp/`, and
`lib/libosoe.so.0.1.0` with `lib/osoe/osoe-statics.ld`. The installed `oshcc`
built every program here with `-Wall` and no warning, with a `RUNPATH` to the
prefix. The library: soname `libosoe.so.0`, needing `liburing.so.2` and
`libc.so.6`; 3,595 defined dynamic names, round nine's count; 1,787 `shmem_`
names, every one weak, and 1,794 `pshmem_` names, every one strong - the seven
more being the deprecated `_my_pe`, `_num_pes`, `start_pes` and the four `sh*`
allocators, each with two profiling names at one address (`p_my_pe` and
`pshmem__my_pe`) as `pshmem.h` declares; no other name. `oshcc` refuses
`-static`, `--static` and `-static-pie` by name and passes `-static-libgcc`
(`wrapper.show`, observed in source and in the suite).

**Mixed versions** (*measured*, `mixed.sh`: round nine's tree, `3b45472`,
layout 37 - the first whose rendezvous words keep their place - built beside
this one, layout 43, and given to some ranks by `-e RANK:LD_LIBRARY_PATH=`).
On one node, either way round, the joining PE refuses at once by name:
"control segment ... has layout 43; this library expects 37 (mixed library
versions?)", and the reverse - so the README's layout-37 clause holds, and the
older library refuses the newer too. Across two nodes, node 1 on round nine's
library: "node 1 sent a rendezvous report this build cannot read: the nodes are
running different osoe libraries", at once, the other node naming its lost
parent. Each version's `osoe-stat` read a hung job of the other's, the PE lines
and `--summary` both, as design §3.14 promises. Only 0.1.0 beside 0.2 waits
until a time limit, which the README says, by the author's word of 2026-10-11.

## Readiness

**The README's new and changed settings** (*measured* unless marked). Every bad
value of a setting added or changed since round nine was refused at start-up by
name, with its range or form, by every PE that read it, over three logical
nodes: `OSOE_CHECK_COLLECTIVES` (`2`, `yes`: "is not 0 or 1"),
`OSOE_COLLECTIVE_PLACES` (`fast`), `OSOE_MESH_DATA_WIRES` (`lazy`),
