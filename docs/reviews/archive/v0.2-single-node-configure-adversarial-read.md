## Findings, ranked

### Should fix

**1. "`ctest -L internode` on the full build runs exactly the tests it lacks" is false from this
commit, in the very bullet the change edits, and so is `OsoeInternode.cmake`'s statement of the
rule** (*observed in source*, and the model's set difference in every preset)

- **Where:**
  - `README.md:1330-1331`, the last sentence of "Two builds";
  - `cmake/OsoeInternode.cmake:8-10`: "So `ctest -L internode` on the full build runs exactly the
    tests the single-node build lacks, and `ctest -LE internode` the ones both run."
- **What:** the bullet now says the single-node build runs the suite less the 458 `internode`
  tests "and less the full build's check that the single-node build configures". Two lines later
  it says `ctest -L internode` runs exactly the tests it lacks. `shmem.single-node.configure` is
  registered in the full build alone (`shmem/tests/CMakeLists.txt:116-132`) and carries only
  `tier1`.
- **The model's comparison of the two builds' test sets:**

  | | debug | release | AddressSanitizer | ThreadSanitizer |
  |---|---|---|---|---|
  | Lacks, at `7a42c92` | the 458 `internode` tests | the 458 | the 443 | the 209 |
  | Lacks, at `3541411` | the 458 and `shmem.single-node.configure` | the same | the 443 and the check | the 209 and the check |

  - The full build's `-LE internode` in debug is now 400 tests, of which the single-node build
    runs 399.
  - Before this commit the property held exactly in every preset. Step 1's adversarial read
    checked it (`docs/decisions/2026-10-06-single-node-build.md:321-324`), and the step 1 brief's
    audit relies on it.
- **Why it matters:**
  - The README is to be true at every commit, and this sentence now contradicts the one before it.
  - `OsoeInternode.cmake`'s header is where the label's rule is stated for whoever adds a test.
- **The fix:** name the one exception in both places. For example:

    check";
  - in `OsoeInternode.cmake`: "... the tests the single-node build lacks but

  Or give the check a second label of its own, `full-build` say. Then
  `ctest -L 'internode|full-build'` is again exactly what the single-node build lacks, and the

### Notes

**N1. Beside the change: `blocking-gets` (`8f56d03`, WIP) already repeats the defect**
(*observed in source*; the model, with the branch's diff applied onto `3541411`)
- **Where:** `shmem/tests/CMakeLists.txt:2981-2982` on that branch:
  `osoe_tier2_map_test(get-pieces 0,1)`, then
  `set_tests_properties(shmem.get-pieces.0-1 PROPERTIES PASS_REGULAR_EXPRESSION "GET PIECES OK")`.
  Both sit in a block guarded against ThreadSanitizer alone.
- **The effect:** onto this fix, the single-node build is refused at that line in the debug,
  release and AddressSanitizer kinds.
- **How it would be caught:**
  - The new check catches it once that branch carries this commit.
  - `blocking-gets-check.sh` builds release from the branch as it stands, which has no check. So
    it would not.
- **The other branches:**
  - `loopback-keepalive` and `zero-copy-memlock` carry the unguarded RUN_SERIAL line until they
    take `main`. `fast-link-kit` is `7a42c92` itself.
  - `helper-wake-flag` (`302ba07`) makes this commit's guard change on the same line, and its
    single-node build is clean in the model.
- **So merge this branch first,** and rebase `blocking-gets` before its verification. Its
  `get-pieces` property wants the same guard.

**N2. The trap is in `osoe_tier2_map_test`, and both instances fell into it** (*observed in source*)
- **What:** the function returns silently for a map of more than one node where `OSOE_INTERNODE`
  is off (`:1593-1595`). Any property set after a call outside an `OSOE_INTERNODE` block then
  refuses the single-node build.
- **The house style allows such calls:** `:1629`'s `osoe_tier2_map_test(ack-echo 0,1)` stands at
  file level, unguarded, on the strength of that return.
- **What the check covers:** it now catches the class in three presets of four. ThreadSanitizer's
  kind skips most such blocks in both builds.
- **A fix at the source** would make the defect unwritable:
  - let the function take the properties, for example a `PROPERTIES` keyword that it applies after
    its `add_test`;
  - or set such properties under `if(TEST <name>)`.

**N3. Forwarding `OSOE_TEST_PINS` does nothing today, and would point the check at the project's
configuration rather than a user's** (*observed in source*)
- **Today:** both reads of the option (`shmem/tests/CMakeLists.txt:1085`, `:4222`) sit inside
  `if(OSOE_INTERNODE)`, so the single-node lists never read it.
- **The project's runs:** the project's verification configures every preset with
  `-DOSOE_TEST_PINS=ON` (`verify.sh`, `verify-grant-fields.sh`, `verify-integration.sh`). Every
  nested configure the project runs is therefore a single-node build with the pins on, which no
  user builds - the single-node build has no floor test.
- **The risk:** a future single-node line under `if(NOT OSOE_TEST_PINS)` would refuse every user's
  default build. The project's check would pass it, and only `verify-integration.sh`'s debug
  configure by hand would see it.
- **The add_test reads the option before it exists:** it reads `${OSOE_TEST_PINS}` at `:126`,
  while `option(OSOE_TEST_PINS ...)` is at `:1072`. On a first configure without `-D` it passes
  `-DTEST_PINS=`, and the script passes nothing on. That is the right result, but only because the
  script tests for empty.
- **The fix:** leave the pins out, so that the nested configure takes a user's default. Or say in
  the record why they are forwarded.

**N4. The nested configure runs where the full build's dependencies are installed, so it cannot
see a single-node path that asks for them** (*observed in source*)
- **The property at stake:** the single-node build "asks for neither [liburing] nor pkg-config"
  (`CMakeLists.txt:62-64`; the decisions index, "Dependencies"). It is what Rocky Linux 9 and a
  desktop rely on.
- **What the check would pass:** a `find_package(PkgConfig REQUIRED)` or a
  `pkg_check_modules(LIBURING REQUIRED ...)` that left the full build's branch would configure
  here and refuse there.
- **What else it cannot see:** it runs this machine's CMake. A construct newer than the oldest
  CMake the single-node build is built with configures here and is refused there.
- **A cheap addition:** after the configure, fail if `${SCRATCH_DIR}/CMakeCache.txt` holds
  `PKG_CONFIG_EXECUTABLE` or any `LIBURING_` entry. The single-node configure creates neither
  today: `find_package(PkgConfig)` is only in the full build's branch.

**N7. Smaller ways the nested configure differs from the preset's own** (*observed in source*; the
model for the last point)
- **The generator is not passed.** The default, Unix Makefiles, needs `make`. A machine with
  Ninja alone fails the check before it reads a line of the lists. The two model scripts share
  this; `-G "${CMAKE_GENERATOR}"` and `CMAKE_MAKE_PROGRAM` would remove it.
- **Empty flags are not passed** (`if(C_FLAGS)` and the like). The nested configure then takes
  `CFLAGS` and `LDFLAGS` from ctest's environment, where the outer build's cache had them empty.
  Testing `DEFINED` and passing the flags even when empty would pin them.
- **The toolchain file is passed as the cache holds it.** A relative one would resolve against
  the scratch directory, as in the two model scripts.
- **Not passed, and harmless today:** `CMAKE_CXX_COMPILER`, `OSOE_CXX_COMPILER`,
  `Python3_EXECUTABLE` and `OSOE_MULTIPLE_MODELS`. In the model, none changes whether the
  single-node lists configure: they are clean without Python, without a C++ compiler, with
  `OSOE_MULTIPLE_MODELS=ON`, and static, in all four kinds.
- **The name:** `shmem.single-node.*` names the single-node build's own tests there
  (`refuse-nodes`, `version-says-so`). Here it names the one test that build lacks.

## What is sound

**The fix.**
- `if(OSOE_INTERNODE AND NOT CMAKE_C_FLAGS MATCHES "sanitize=thread")` (`:1643`) skips the
  registration and the property together.
- At `3541411` the single-node build configures and generates without an error in the debug,
  release, AddressSanitizer and ThreadSanitizer kinds. It does so with the pins on or off, static,
  without Python and without a C++ compiler (the model).
- **Nothing else in the lists sets a property on, or names, a test or target that the single-node
  build lacks.** The search covered all of these:
  - every property, target and generator-expression reference in every list;
  - the guarded blocks, 44 in `shmem/tests` and 7 in `tools/`;
  - the 14 loops that `continue()` past a map of more than one node, 11 in `shmem/tests` and 3
    in `tools/pacer`;
  - the function's `return()`.
- **None of the class that configure cannot see exists today either** (N5).

**The counts** (the model, from lists whose counts it reproduced exactly at `4f1014d`,
`7a42c92` and `8e36752`).
- **Debug:**
  - the full build 858, 458 of them `internode`;
  - the single-node build 404: the full build's 399, which is 858 less 458 less the check, and its
    five;
  - without a C++ compiler, 856 and 402.
- **AddressSanitizer:** 843 and 401. **ThreadSanitizer:** 601 and 396. **Release:** 898 with the
  40 models.
- **The README's other numbers hold:**
  - "about 860" (`:255`, `:1288`) holds.
  - "about 410" and "about 680" of 858 (`:301-311`) hold: the check needs neither io_uring nor
    `/dev/shm`, and passes where those fail.
- The README's `cmake/` row and the new clause of "Two builds" are true.

**The check.**
- **It catches what it names.** At `7a42c92` the model's single-node configure fails at `:1621`,
  with the error the record quotes, in debug, release and AddressSanitizer. With the lead's mutant
  it fails at `:1645` in the same three.
- **It runs the generate step** (`cmake -S -B`), so a `$<TARGET_FILE:...>` naming a target only
  the full build has is caught as well.
- **The flags arrive intact.** A flag string with spaces, such as AddressSanitizer's, survives as
  one argument at each step:
  - the quoted `add_test` argument;
  - the CTest file;
  - `cmake -D`'s split at the first `=`;
  - a one-element list;
  - `execute_process`.
- **The script's mechanics are sound:**
  - Empty values are not passed, and `TEST_PINS` empty or `OFF` gives the same nested build.
  - The scratch directory is removed first, so a stale one does no harm.
  - It is apart from `strict-c11-check` and `static-link-check`.
- **It is safe beside the other checks:**
  - A configure of this tree writes nothing into the source tree: every `configure_file` writes to
    the binary tree, and there is no `file(WRITE)`. So `ctest -j` beside the two nested builds
    shares nothing.
  - The source-scanning checks glob `base`, `cmake`, `dev`, `docs`, `shmem` and `tools`, never
    `build`.
- **Sanitizer flags at configure time are safe.** The nested configure's compiler and Threads
  checks compile and link with the flags the outer configure already used, and nothing in the
  tree uses `try_run` or `check_c_source_runs`.
- **It is cheap:** 300 s of timeout against a configure that took about a second at `8e36752`,
  0.3 s of it the lists'.
- **No recursion:** the check is registered only `if(NOT OSOE_SINGLE_NODE)`, so the nested tree
  does not register it, and the strict-c11 tree registers it without running it.
- **Not `OSOE_TIER3`** is right:
  - the single-node build refuses it with a `FATAL_ERROR` (`:4113-4116`);
  - the tier3 test preset selects the `tier3` label, which leaves the check out.
