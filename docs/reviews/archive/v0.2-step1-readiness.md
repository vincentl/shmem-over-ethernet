## Verdict

**The single-node build can be offered to desktop users as the README
describes it. Nothing in this question blocks; one README sentence should
change first (Q5-1), and the rest are minors.** Followed literally on Rocky
Linux 9 from a clean copy, the desktop section configures with no liburing
and no pkg-config, builds in 21 s with no warning, installs thirteen files with
`osoe-launch` among them, and the installed wrapper and launcher run the ring;
`ctest --preset release -j4` passes 347 of 347 in 28 s. A job of more than one
node is refused on every PE, by name, with status 1 and nothing made in
`/dev/shm`. Every place that prints the version says `(single-node build)`.
The library needs libc alone. Every way of failing a one-node job that I could
make is loud or, where the Limits say it is silent, silent as they say.

**The full build is still what 0.1.0 was** in everything a user meets: its
requirements, its quick start, its messages - the futex and io_uring
refusals word for word, the latter now made below the seam and still telling no
one (*measured*) - and its tests: all 748 of the tag's, by name, and eleven
more, ten one-node variants and the shared-scope futex2 refusal (*measured*,
the tag's tree configured beside this one). What changed is listed in the
records and the README: `osoe-launch` is installed, the futex fixes both builds
took, a fifth heap base. But it calls itself `0.1.0`, the tag's version, so a
report from it cannot be told from one from the tag (Q5-6).

**What should change before desktop users are pointed at it** - Q5-1, and
two minors cheap enough to make with it, all sentences:

1. **Q5-1**: on a job of one node - every job of this build - `osoe-stat
   --summary` walks nothing: a team hung in a barrier reads "epoch 0/0 own no
   children 0/0 next 0", the README's way down a hang leading nowhere.
2. **Q5-2**: the section's example, eight PEs at the default heap, needs 2.1 GiB
   of `/dev/shm`, which the project's own Rocky VM does not have: it is
   refused there, by name and with the remedy. The step's verification ran its
   programs at `SHMEM_SYMMETRIC_SIZE=16m`, so the command as printed had not
   run there. The section's test count assumes a C++ compiler that its install
   line does not install.
3. **Q5-3**: the four directory READMEs the root README vouches for were not
   touched by the step; `tools/README.md` still says `cmake --install`
   installs three programs.

The seam's account for a porter (Q5-8) holds for a second internode backend of
AM's shape - the link proves the header is the whole contract - but the header
offers itself to an RDMA backend, which it does not serve: after release.

### Q5-1. `osoe-stat --summary` walks nothing on a job of one node, which is every job of the single-node build (fix before release: one sentence; the view after release; high in the facts, medium in the rating)

- **Location**: README "Looking inside a job", :493 ("`osoe-stat --summary
  1234  # each team's barrier or sync in progress, to walk a hang down`") and
  :500-502; "When a job fails or hangs", :526-528, which sends every hang to
  it; `tools/stat/stat.c:563-636` (`summary_line`), which prints, for each team,
  the tree state's epochs and arrivals - whose one writer is the lead's
  engine (`progress.c:226-227`; `node.c:1315-1316` zeroes them), which a job of
  one node never runs and the single-node build does not even compile
  (*observed in source*).
- **Scenario**: a desktop user's four-PE job hangs, one PE computing while the
  others wait in a barrier. The deadlock detector rightly never ends it. The
  user runs what the README says. `--summary` prints one line:

  > node 0   lima-osoe-rocky   4/4  live  world      epoch 0/0   own no  children 0/0  next 0    parent 0     rank 3 shmem_barrier_all (epoch 2) 4.003 s

  "epoch 0/0" says no barrier is open, while three PEs wait in epoch 2; "next
  0" points the user at the node they are on; the last column names rank 3,
  the PE blocked longest, not rank 1, the culprit. Round six's Q5-1 scenario
  exactly - "they conclude the job is not in a collective" - for a barrier.
- **Evidence** (*measured*): script B's `compute` mode on the installed
  single-node build; the same job on the full build gives the same line
  (script F), and on two logical nodes the summary walks
  ("`epoch 2/1 own no children 1/1 next -`" on the culprit's node). So it is
  not new in step 1; step 1 makes it the case of every job of a build meant for
  one machine. `osoe-stat JOB`'s PE lines find the culprit at once: PE 1 with
  its sweeps at 0 and blocked in nothing ("-"), beside three PEs at 39 sweeps
  in `shmem_barrier_all (epoch 2) for 3.999 s`.
- **Fix**: before release, the README's "Looking inside a job" - and the
  `--help` line beside it (`stat.c:1446-1450`, "walk a hung barrier or sync
  down from the root by it") - says the summary walks the tree between nodes,
  so on a job of one node, every job of the single-node build, it shows only
  the PE blocked longest, and the PE lines are the view. After release,
  `summary_line` says "one node: no tree" for a team whose record spans one
  node rather than print epochs nothing writes.
- **Confidence**: high in the facts (the source, two builds, two maps); medium
  in the rating, for round six's reason: the hang stays diagnosable from the
  default view, and what is wrong is where the README points.

### Q5-2. The desktop section's example and figures assume more than it says (minor; high)

- **Location**: README :126-164, the section "On a desktop: the single-node
  build".
- **The example** (*measured*): "here as eight PEs, which a machine of four
  cores runs too", then `~/osoe/bin/osoe-launch -n 8 -- ./ring`. On
  `osoe-rocky`, the VM the README cites ("it has run on Rocky Linux 9"),
  every PE ends at once:

  > osoe: PE 0: /dev/shm has 1822 MiB free, but this node's control segment and 8 heaps of 261 MiB - each the symmetric heap and 6 MiB of the library's own region, ... need 2100 MiB: lower SHMEM_SYMMETRIC_SIZE or those, run fewer PEs per node, or enlarge /dev/shm ...

  Seven PEs are refused too (1,838 MiB); six run. Cores are not what limits
  the example: `/dev/shm`, half the memory by default, is, and eight PEs need
  a machine of about 4.5 GiB. The section gives the 263 MiB a PE two
  paragraphs later, and the refusal names the remedy - which ran: at
  `SHMEM_SYMMETRIC_SIZE=64m` the eight lines, status 0. The step's own
  verification ran the installed programs at `SHMEM_SYMMETRIC_SIZE=16m`
  (`build/scratch/single-node/single-node-verify.sh`, whose output the final
  verification kept in `final/rocky/single-node.txt` beside it, *observed in
  source*), so the printed command was not run as printed on Rocky.
- **The suite's count** (*measured*): "345 of the full build's 729 tests ... and
  four of its own" is exact - the single-node build's list is the full
  build's 345 one-node tests name for name, plus its four (script F against
  script C) - but on Rocky after the README's `sudo dnf install gcc make cmake`
  it is 343 and four: `shmem.headers.c++11` and `c++17` register only where a
  C++ compiler is found (`shmem/tests/CMakeLists.txt:1944`).
- **The models** (*documented*): "`ctest --preset models` runs the same 30
  tests" - registered, 30 (*measured*) - but on a machine of 4 GiB at `-j4`
  the kernel kills `model.abort` for memory (1.4 GiB beside three others), as
  the step's record says; the README's Building gives `-j4`.
- **Smaller**: the section does not say that `ring.c` is the ring above or that
  the commands run from the repository root (the quick start says both); and
  the opening's "needs only the compiler and CMake" leaves out `make`, which
  the presets' default generator needs and the Rocky line installs.
- **Fix**: "here as eight PEs - about 2.1 GiB of `/dev/shm`, half the memory of
  a machine of 4.5 GiB; `SHMEM_SYMMETRIC_SIZE=64m` in front runs them on less";
  the models at `-j2` on 4 GiB; the ring's and the directory's half sentence.
  And the counts: "every test of the full build but those labelled
  `internode`, and four of its own" says the same without the three numbers,
  which every later step that adds a test - step 2 next - would otherwise have
  to change in a section a desktop user reads first; "How osoe is tested"

### Q5-5. Two of the section's claims no test would see break (minor; high)

- **"Refused at `shmem_init` by name, before anything is made in `/dev/shm`"**
  holds in the source - `osoe_transport_settings_check`, whose first step is the
  refusing backend's check, runs before `osoe_node_join` (`init.c:285-319`,
  *observed in source*) - and in every run here: nothing new in `/dev/shm`
  under `-m 0,1`, `-s -m 0,1` and `0,0,1,1` (*measured*). But the test is blind
  to the order. Break D2 made the check answer "go on" and refused instead from
  `osoe_internode_backend_advertise`, after both nodes had made their
  segments and heaps: `shmem.single-node.refuse-nodes` **passed**. Its
  `!left behind` pattern sees what is left, and a refusal after the join
  leaves nothing, the names being removed once mapped. What such a refusal
  prints that the real one does not is each PE's "control segment /osoe.… (osoe-stat
  /osoe.…, while any PE of this node is alive)" line (break E2, *measured*), so
  a `!control segment` pattern pins it. (Break D1 - no refusal at all - does
  fail the test, on the unreachable entry point's own message.)
- **"`(single-node build)` after the version, wherever it is printed"**: every
  version test compares a tool with `OSOE_VERSION_TEXT`, the same variable the
  suffix is appended to (`cmake/OsoeVersion.cmake`), so dropping the suffix
  changes both sides. Break H1 dropped it: the single-node build's
  `osoe-launch --version` said `osoe-launch (osoe) 0.1.0`, and all nine
  version tests - the library's three, the five tools', the wrapper's -
  passed (*measured*).
- **Fix**: the pattern; and one test in the single-node build that some tool's
  `--version` ends `(single-node build)`, written as a literal.

### Q5-8. The seam: `internode-backend.h` is the whole contract for a second internode backend of AM's shape, and offers itself to an RDMA backend it cannot serve (after release; high)

*Observed in source*, and at the link (*measured*).

- **What holds**: both builds' part every job uses needs exactly 30 symbols
  from an internode backend - the header's 20 entry points and
  `internode.h`'s 10 calls - and the refusing backend defines exactly those 30
  (`nm` on both builds' objects, scripts E and F); the single-node library's
  100 undefined symbols are all glibc's. So nothing reaches past the header,
  at the link as well as at the include (`shmem.boundary`'s third check). Each
  entry point names its §4.10 call, whose contract `transport.h` states; the
  refusing backend is a worked example; the CMake list is one `set()`.
- **What does not**: the header says "a second internode backend replaces those
  files without touching the first part" and "a backend on RDMA provides each
  of them" (`internode-backend.h:22-34`). Three things say otherwise, the
  first two in the first part itself:
  - `osoe_transport_set_range` and `osoe_transport_load` live there, "in the
    file a second backend replaces ... an RDMA backend has its own set_range"
    (`transport-am.c:429-436`); neither is an entry point of the header. An RDMA
    backend written to the header is never told which ranges carry atomics -
    design §4.10's "largest recoverable loss for an RDMA backend" (:3775).
  - Every node-mate's rmw goes to a CPU atomic by PE (`transport-am.c:350-361`,
    `job.h:182-185`), where design §4.10 has a NIC whose atomics are not
    coherent with the CPU route on-node atomics through the NIC, "dispatch per
    (pe, operation class), not per PE" (:3585-3594), and the README's RoCE
    sketch has the NIC's atomics "serve node-mates too" (:1129-1130). Kept
    with such a NIC, that dispatch breaks spec §3.2's exclusivity between a
    node-mate's and a remote PE's fetch-add on one word of the same atomicity
    domain.
  - The backend's counters are the control segment's `am.*`, laid out by
    `node.h` and `metrics.c` in every build: a second backend writes AM's names
    or edits both and `osoe-stat`.
- **What a porter needs** that the header does not list: the runtime services
  the AM backend calls - 38 symbols of the rest of `libosoe` (the `osoe` state,
  the blocked record, fatal and notice, the node's abort, the rank map, the
  shared-memory helpers, metrics, `osoe_transport_notify`, the generic phase)
  and 21 of `base/` (*measured*, script F). `cmake/CheckBoundary.cmake`'s lists
  define the layers; nothing says which of their functions a backend may call.
- **Fix**: the header and §4.10's note say that it is AM's own division - a
  second internode backend that keeps the node-mate path, as the refusing one
  does - and that an RDMA backend implements `transport.h` and `internode.h`
  whole under `OSOE_BACKEND`, replacing `transport-am.c`; and name the runtime
  a backend may call.
