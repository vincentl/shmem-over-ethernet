## Findings

### F1. The deadlock detector's proof no longer holds: the tree's messages are application work nothing acknowledges

**Severity: fatal** - a job that would complete is ended with status 1 as deadlocked; §3.15's rule
that no wait gives up because time has passed, and the proof §3.15 and `deadlock.h` give, no longer
hold. It is also the brief's stop-and-ask in substance: not a control message ordered against a
data message, but the premise the proposal rests the planes on - "the detector reasons about
counters, not messages" (proposal §3.1, `progress-helpers-proposal.md:185`; design `:266`) - is
false.

The detector declares when every node's two samples bracket t* and nothing moved; the proof's step
is "a message in flight at t* was sent before its sender's first sample ended, so was acknowledged
by then - applied before t*" (`deadlock.h:39-42`; design `:2081-2086`). `node_quiet` is what makes
it true: "has every segment this node sent that carried application work been applied by its peer?
... the acknowledgements are what make a message in flight visible to the detector"
(`transport.h:272-276`). *(documented)*

At 95f3339 ARRIVE and RELEASE rode the data connection: `drain_into` wrote them into its buffer
(`:800-830`), `finalize` counted every kind but DEADLOCK as application work and set
`last_application_seq` (`:950-956`), and `osoe_progress_quiet` refused quiet until the peer had
acknowledged that segment, asking with the late request (`:1592-1605`). At 3d30d1c they ride the
control wire: `seal_control` records no sequence for application work and sends `ack` 0
(`progress.c:1304-1336`); `segment_applied` notes only a control segment's goodbye (`:722-727`);
the receiver still counts both kinds in `application_applied`, the activity (`:530-531`);
`osoe_progress_quiet` looks at the data connections alone (`:1917-1934`), and
`osoe_progress_idle` only at whether a control segment is queued or not yet taken by the kernel
(`:1738-1743`). `progress.h:281-284` states the premise: "nothing on it asks for an
acknowledgement, since nothing waits for a control message to be applied". The proof does.
*(observed in source)*

Scenario: ten nodes, the world team's tree at the default fan-out of 8, node 9 a child of node 1.
Every PE enters `shmem_barrier_all`; node 9's agent seals its ARRIVE toward node 1, the kernel
takes it, and node 9's control wire is idle at once. The 1↔9 path drops the segment - an ECMP
member link that blackholes the flow until the fabric reroutes, a flapping port - while node 0
reaches both. TCP retransmits at about 0.2, 0.6, 1.4, 3.0, 6.2 and 12.6 s. From about 1 s node 0's
node has looked quiet for a second (`deadlock.c:40`) and the root samples and probes: node 9 is
idle and quiet (its barrier's quiet emptied the data wires; its control wire is empty), node 1 is
unmoved, every PE waits; t* ≈ 1 s. The root waits `OSOE_DEADLOCK_SECONDS`, 10, probes again at
about 11 s - every node quiet, nothing moved - and the job ends with status 1, every node listing
its PEs as waiting in `shmem_barrier_all`. The ARRIVE lands at 12.6 s. At 95f3339 node 9 reports
busy in both collections - its segment unacknowledged, its request queued behind it on the same
stream - and the barrier completes when the path recovers. Any outage of a path between two nodes
that are not node 0 whose next retransmission falls after the root's second collection does it -
at the defaults, any that outlasts the 6.2 s retransmission - as can a whole-link outage of one
node that ends between the two connections' retransmission times; with `OSOE_DEADLOCK_SECONDS=1`,
a second or two of backoff. An edge to or from node 0 is protected by
accident: the probes and reports ride the same control wires, FIFO behind the tree's message.
*(the model run; the times are TCP's backoff from a 200 ms RTO, reasoned, not measured)*

Evidence: `model/deadlock-control-wire-all.out`, `control_wire`: VIOLATION, "declared, but PE 2 is
not blocked for good", its trace ending "node 2 reports: quiet ; node 2 applies a arrive from node
1 ; ... nothing moved: the root declares"; `control_wire_acked` holds with liveness. No test over
loopback can show it: the kernel puts the bytes in the receiver's socket at the send, and the
receiver's sample has a pass between its halves. *(run)*

Fix - the author's to choose, since it changes the control plane's protocol and a sentence of the
proposal:
- (a) acknowledge the control segments that carry ARRIVE or RELEASE as a data wire's are:
  `struct osoe_progress_control` keeps `applied`, `acked`, `last_application_seq` and
  `detector_wanted`; `segment_applied` records a control segment's sequence; every control
  segment carries `ack`; `osoe_progress_quiet` treats each control wire as a connection and asks
  with a header-only `ACK_REQUESTED` segment that the peer answers header-only (`ack_model.py`'s
  late request). The file above's `control_wire_acked` is this design.
- (b) make the proposal's sentence true: each REPORT carries its node's cumulative counts of
  control application messages sent and applied (two 64-bit words; the message's `reserved` is 32
  bits), and the root declares only if the sums agree in both collections - each node's counts
  are constant over its two samples, which bracket t*, so equal sums mean none was in flight at
  t*. Needs its own model case.

Either way, add `control_wire` to `deadlock_model.py` as a breakage, and amend §3.15, invariant 22
and the README's "with nothing in flight" (`README.md:526-527`, `:1053-1056`). The kernel's
acknowledgement alone (`SIOCOUTQ` at 0 on every control wire, as `osoe_progress_aborted` asks)
narrows the window to bytes in the receiver's socket not yet reaped, and leaves the proof needing
an argument that the receiver's sample reaps them - not recommended alone.

### S2. The zero-copy completion budget counts the control wires: `OSOE_WIRE_ZERO_COPY=on` refuses jobs above 1,819 nodes, not 3,638, naming twice the peers

**Severity: should-fix** (a stated limit halved, and a fatal that misnames its count; off by
default).

`osoe_wire_ring_open` sizes the completion queue as `buffers + (2 + OSOE_WIRE_ZERO_COPY_OWED_MOST)
× count + 1` and refuses it above 65,536 (`wire.c:50-56`), with `count` now the ring's wires,
`osoe_ring_wires(0)` = 2(n - 1) at no helpers (`wire.c:240-241`; `ring.c:70` the same bound). A
control wire never sends by reference - `flush_control` calls `osoe_wire_send`, whose region is
`OSOE_WIRE_LENT_REGIONS` (`wire.c:301-304`, `:280`) - so it never owes a notification, yet
reserves 16. Scenario: a 2,000-node job with the setting on, which 95f3339 started (36,047
completions), is refused: 72,029 completions, the fatal saying "3998 peer nodes". *(run:
`zero-copy-limit.out`)* Fix: size the notifications term by the data wires (give `osoe_ring_open`
the count of wires that may lend), and print peers; or keep it and say 1,819 in the README and
design §3.3.

### N1. The planes are refused only after a misrouted message's payload has landed, and no test sends one

**Severity: note** (the refusal is a diagnostic; the job ends either way).

`destination()` resolves a PUT's target and a GET_REPLY's landing piece, and the parser copies the
payload there (`am.c:245-246`), before `complete()` refuses the kind on a control wire
(`progress.c:515-518`): a PUT misrouted onto a control wire writes its bytes into the heap, then
ends the job. At a helper count, a GET_REPLY's fatals there name `peer_of(o, i)` of a control
slot, which is no peer (`progress.c:97-103`; `osoe_owner_slot(0, i, H)` underflows). And no test
puts a message on the wrong wire: deleting the check at `:515-518` passes every test (property 11).
Fix: refuse in `destination()` when `a->control`, and a test in `test-progress.c` that commits a
`BARRIER_ARRIVE` into a data connection buffer and expects the fatal naming both. *(observed in
source)*

### N2. With no helpers the planes share the agent's pass, data first, and the abort is judged per wire

**Severity: note** (latency, an overstated sentence, and an unmodelled corner).

The pass receives, applies and flushes every data wire before it looks at a control wire
(`progress.c:1668-1685`, then `:1689-1701`): at H = 0 an ARRIVE reaped beside a megabyte of puts
is applied after them, and a forward it causes is submitted after the data sends the pass queued,
which the kernel copies first; the control wires also draw on owner 0's provided buffers, so a data
flood's `ENOBUFS` ends their receives too until the next pass. So "they share only the link"
(`README.md:668-672`; design `:266-269`) overstates it at H = 0 - and the README's "and nothing
else" leaves out the goodbyes, which the design's version names. Visiting the control wires first
costs nothing - no ordering joins the planes - and puts the barrier's sends ahead in the
submission.

The same order touches the abort: a peer's abort read on its control wire excuses an error only
on that wire (`receive_wire`, `:793`) until this node's agent sets `aborting` at its next turn, so
a reset on the peer's data wire reaped in the same pass - the data loop runs first - ends this
node with "the connection to node X failed" instead of the peer's status. It needs the peer's
data-wire goodbye unacknowledged past `OSOE_ABORT_GRACE_SECONDS` while this node did not run;
`abort_model.py` has no two-wire case. Treating a peer whose abort has arrived on either wire as
aborted on both closes it. *(observed in source)*

### N3. A message queued on a control wire after its goodbye stays queued

**Severity: note** (harmless today).

Once a control wire's goodbye is sealed, `flush_control` returns before sealing anything
(`progress.c:1416-1417`) while `control_busy` stays true on a non-empty queue (`:1435`): a detector
message sent during the close - a veto from a node with detection off, or DECLARED, both sent from
`osoe_deadlock_message` (`deadlock.c`) - holds its descriptor and keeps the slot visited every pass
until the close ends. `osoe_progress_closed` ignores the queue, so nothing hangs. And
`seal_control` marks the goodbye by `count == 0` (`:1324`), which would also be true of a queue
whose first message did not fit; none can, at 24 bytes against 4 KiB. Refuse (or count and drop)
an enqueue after the goodbye, and seal the goodbye on `o->closing` with an empty queue rather than
on an empty segment. *(observed in source)*

## The properties, one by one

### 1. Ordering between the planes

What each control message's receiver concludes, and whether it needs a data message applied first:

- **`shmem_barrier_all`, a team barrier, `shmem_finalize`'s barrier**: a quiet on the default
  context before `sync_team`'s arrival (`barrier.c:146-155`, `:158-163`, `:181-192`), and an
  acknowledgement means applied (`segment_applied` sets `applied` after every message of its
  segment, `progress.c:742`). The release concludes "everyone arrived", which already implies the
  data. Held.
- **`shmem_sync_all`, `shmem_team_sync`, `shmem_sync`** (`barrier.c:205-243`): no quiet, and the
  specification orders no data. The library's own syncs: `team.c:1377`, the split's sync over its
  parent - each node's record and each member's counters are its own node's memory (`finish`,
  `team.c:1068-1105`; `osoe_internode_number_taken`, the PE's own region), stores before its
  arrival, nothing on a data wire; and `team.c:1490`, destroy, after its contexts' quiets
  (`:1489`), with nothing of the team's last collective in flight once its members have returned
  (`circulant_model.py`'s QUIET). The data collectives use puts and fenced adds, never the tree:
  `osoe_internode_arrive` has one caller, `barrier.c:70`. At 95f3339 a put to a node and an
  ARRIVE to the same node were FIFO by accident; nothing relied on it. Held.
- **Team-block reuse**: every message that names a block is ARRIVE or RELEASE (`barrier_team`,
  `progress.c:485-502`), FIFO on one control wire each way, so the late-message argument in
  `known_team` (`:432-437`) is the control plane's alone; `releases_queued` now falls at the seal
  into the private buffer (`:1318-1319`), and the local release waits for it (`:1607-1611`). Held.
- **`shmem_finalize`'s last barrier and the close**: the goodbye seals only with the queue empty and
  nothing on the wire (`:1416-1422`), so a RELEASE leaves before it on the same wire, and the close
  begins only once `flush_before_close` has every control wire idle (`progress-host.c:706`). Held.
- **The abortive goodbye**: on each wire after that wire's segment in flight (`:1356-1369`); its
  receiver concludes "this peer is ending" for that wire. Held, with N2's same-pass corner.
- **The deadlock detector's messages**: their receivers sample and report; the root's conclusion,
  "nothing in flight at t*", needed every application message acknowledged, and ARRIVE and
  RELEASE no longer are. **F1.**

### 2. The control wire's send path

Held. One send in flight: `seal_control` runs only once `c->bytes` is 0 (`:1400-1418`), which only
a completion's return makes it, and `send_from` refuses another buffer while one is in flight
(`wire.c:252-257`). Short sends: `c->sent` accumulates and the rest is offered from `c->buffer +
c->sent` (`:1400-1406`); `OSOE_WIRE_SPLIT=2000` and `3000` in `shmem.barrier-am.*` and
`shmem.owners.*` exercise it. The goodbye: sealed only closing with the queue empty and nothing on
the wire, the stream ended after its completion (`:1409-1413`). A peer's reset or abort: nothing
more sent (`:1397-1398`); idle skips a reset wire, closed tolerates one. The abort's visit:
finishes the segment, then the abortive goodbye, or nobody to tell (`:1344-1380`), as
`flush_aborting`. `control_busy` against every change: `c->bytes` (the seal `:1334`, completions
`:1407`, `:1361`), `queue.depth` (`enqueue_control` sets the bit itself, `:283`; the seal pops,
`:1320`), `closing` and `aborting` (each marks every slot, `:1783-1784`, `:1814-1815`),
`abort_done` (`receive_wire :794`, `flush_control_aborting`) - each followed by `settle_control` in
the loop (`:1698`) or in `release_local` (`:1605`). A message queued for a slot the loop has passed
keeps its bit, and the pass returns moved - it came from a receive (`:1696`) - so the agent passes
again without sleeping (`agent.c:240`); a RELEASE is sealed by the end-of-pass `release_local`
(`:1705-1706`). Stranded only after the goodbye: N3.

### 3. The ring's split between data and control ranges

Held *(run: `ring_check.out`)*: at every layout checked, including 32, 63, 64, 65, 127 and 128
peers and helper counts 1 to 64, the data loop takes exactly owner 0's data wires' bits and the
control loop exactly the control wires', each once, nothing left set, including ranges that start
mid-word and spill. `readable` has a spare word (`ring.c:93`); only the reap sets a bit
(`ring.c:155`), once a pass before both loops; every bit taken is received and its wire emptied
(`progress.c:779-787`). No path to a buffer held across a reap was found. The spill is exercised
only by the tests of 34 nodes or more (the 64- and 70-node ones).

### 4. The close and the abort per wire

Held for the close. Against `two_wires`: each wire's goodbye after its own last bytes (data
`:1218-1222`, control `:1416-1422`), its end of stream after the goodbye's completion
(`:1171-1174`, `:1409-1412`), and the sockets closed only once every wire has ended
(`osoe_progress_closed :1870-1889`, then `progress-host.c:761-764`) - stricter than the model,
which closes each wire on its own peer's end. `_idle` (`:1738-1743`), `_aborted` (`:1839-1847`),
`_peers_ended` (`:1860-1866`), `_check_silent` (`:1904-1914`) and `_closed` cover the control
wires, and the close's stall watch counts them (`progress-host.c:749-759`). A peer that dies
between its two goodbyes: the wire whose goodbye did not come ends without it, a fatal naming
that wire (`:816-820`). The model is a pair; an interior node's forwarding in the close is the
one-wire three-node case's, and the C sends a RELEASE before its close begins. The abort mirrors
the one-wire abort per wire, unmodelled with two (N2).

### 5. The planes refused on each other's wire

Held, with N1. `complete()` refuses any kind but ABORT on the other plane's wire, naming node, kind
and wire (`:515-518`). Nothing legitimate is ever on the wrong one: a control segment is built only
by `seal_control` from `forward` and `osoe_progress_deadlock_send` (`control_message`,
`:1276-1297`); a data segment by the PEs and `drain_into` (RMW_REPLY `:892`, GET_REPLY `:929`);
goodbyes are header-only, and the abortive goodbye is exempt by kind, also during the close and
the abort.

### 6. The reply pool bound

Held. Per team block at most one ARRIVE or its k RELEASEs are queued: the local release waits for
its RELEASEs' seal (`:1607-1611`), and the members' next arrival for that release; the detector has
at most one message a peer queued (`reply.h`'s note, `deadlock.c`'s protocol). A send in flight
lengthens a descriptor's life, not the count, and the seal frees it (`:1320`); owner 0 still
reserves `peers + degree × teams` (`progress-host.c:501-508`). Only N3's messages outlive their
use, at the close, where the detector's tick no longer runs.

### 7. The mesh

Held. Two calls a pair, control first, each blocking until confirmed (`wire.c:221-238`); accept by
the set of both purposes (`:201-203`); `c->purpose` stored only for an ACCEPTED hello and so below
32 (`listener.c:460-462`, `:476`); a duplicate is fatal naming the wire (`wire.c:211-213`); a lower
node that connects one wire and dies is waited for under the no-progress rule, the notice naming it
(`lacks`, `:174-197`); version 4 drops a version-3 hello as a stranger (`listener.c:446-448`); the
rendezvous has its own listener and accepts RENDEZVOUS alone (`rendezvous.c:324`, `:356`). The
timing reproduces *(run: `mesh-timing.out`)*. Two small things: the notice's `lacks` is recomputed
for every accept whether or not a notice is due - O(n) an accept, O(n²) a lead, 2 x 4,096 accepts
on the last lead at the node ceiling; and the brief has the listener tell the wires apart "by the
first message's kind", where the build uses the hello's purpose - the better choice, unlisted in
the record's departures.

### 8. Counters and `osoe-stat`

Held. The data counts are written only for data wires (`complete :523-529`, `segment_applied
:728-734`, `flush :1175-1179`), the control plane's into its own words (`:524`, `:723`, `:1408`),
each word one writer. The connection record stays 128 bytes (104 rounded to a 64- or 128-byte
line). `node.h` and `segment.h` both say 35; `osoe-stat` reads `valq` by name and prints 0 for an
older segment. `shmem.work-discovery` checks only `segments_sent`'s sum
(`test-work-discovery.c:112`) - which a control segment counted into the node's would fail, the

### 9. The segment lookup

Held. `/proc/self/fd/<n>` reopens the object the descriptor refers to, linked or not; it is asked
only when `shm_open` finds no object of the name (`segment.c:285-288`) and matches it exactly
(`match_name`, `:245`); a process holds its own job's, session's and node's segment, so no stale
object of the name is among its descriptors. `osoe-stat`, a process of its own, finds nothing in
its descriptors - `shm_open` sets close-on-exec *(documented, shm_open(3))*, so a `popen`'d
`osoe-stat` inherits none - and walks `/proc` as before: `shmem.unswept-wait` and the team-storage
test, which `popen` it against a live job (`test-unswept-wait.c:79`, `test-team-storage.c:384`),
still run the cross-process walk. The race between `readlink` and `open` is the existing walk's.

### 10. Helpers > 0

Held *(run: `ring_check.out`, 1 to 64 helpers)*; `shmem.owners` at H = 2 and 3 runs a barrier over
owner 0's control wires. A control index taken for a data one collides with a helper's wire
("connected twice") or trips the planes check, which any barrier finds; a control range from
`first` rather than `o->count + first` (`:1691`) is invisible at H > 0, where `count` is 0, and
fails every multi-node test at H = 0. `limit_unsent` reaches `o->count`, owner 0's data wires, none
at a helper count (`progress-host.c:432-437`): Part 3's.
